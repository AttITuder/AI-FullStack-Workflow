# 文档写作规范

> 所有章节文档必须遵循本文档，确保知识库长期可维护、风格统一。

---

## 1. Markdown 规范

### 标题规范

- 一级标题 `#` 仅用于文档标题，且每篇只使用一次。
- 章节用二级标题 `##`，小节用三级标题 `###`。
- 标题层级不跳跃（不出现 `#` 直接到 `###`）。
- 每个标题上下各空一行。

```markdown
# 文档标题

## 章节

### 小节
```

### 列表规范

- 无序列表用 `-`，有序列表用 `1.`。
- 同一层级列表保持句式一致。
- 列表项过长时拆分为多个短项。

### 表格规范

- 表格用于对比、参数、清单等结构化信息。
- 表头行与分隔行之间必须有 `---`。
- 单元格内容不要过长，保持对齐。

### 强调规范

- 行内代码、文件名、命令用反引号 `` ` `` 包裹。
- 重点内容用 **加粗**，避免全篇大写。
- 强调层级从低到高：加粗 → 引用 → 警告块。

## 2. 代码规范

- 代码统一使用带语言标识的围栏代码块：

````markdown
```dart
void main() {
  print('Hello');
}
```
````

- 支持的语言标识至少包含：`text`、`bash`、`dart`、`kotlin`、`java`、`python`、`json`、`yaml`、`markdown`。
- 命令类内容用 `bash`，纯文本结构用 `text`。
- 代码块内部不要使用行号。

## 3. 图片规范

- **禁止使用网络图片**（外链失效会导致文档残缺）。
- 所有图片统一存放在：

```
assets/images/
```

- 引用格式：

```markdown
![描述文字](../assets/images/example.png)
```

- 图片命名：`章节-序号-描述`，例如 `opencode-01-install.png`。
- 图片必须有关键性描述文字，辅助理解。

## 4. 引用规范

- 引用用于强调、来源说明、金句展示：

```markdown
> 未来工程师的核心竞争力 = 系统设计能力 × AI 管理能力。
```

- 多行引用每行以 `>` 开头。
- 引用后空一行再接正文。

## 5. 统一文档结构

每一篇章节文档按以下顺序组织：

1. **为什么要学习** — 本章解决什么问题
2. **基础概念** — 核心名词与定义
3. **工作原理** — 运行机制与设计思路
4. **实战案例** — 可复现的完整示例
5. **最佳实践** — 经验与建议
6. **常见问题** — FAQ 与踩坑记录
7. **Prompt** — 本章可直接复用的 Prompt
8. **总结** — 要点回顾
9. **参考资料** — 链接与延伸阅读

## 6. Prompt 规范

- 每个 Prompt 独立成文，遵循 `templates/prompt-template.md` 结构。
- Prompt 放在围栏代码块内，语言标识用 `text`，便于直接复制。
- 必须包含：适用场景、使用说明、期望输出、验收清单。
- 占位符统一使用 `【】`，例如 `【页面名称】`。

## 7. Rule 规范

- 每条规则必须**可执行、可检查**，避免模糊表述。
- 每个 Rule 文件开头声明适用范围（语言 / 项目 / 场景）。
- 规则编号格式：`R-<编号>-<简述>`，例如 `R-01-命名`。
- 规则与对应 Prompt、Agent 保持引用同步。

## 8. Agent 规范

- 每个 Agent 一个目录，至少包含 `README.md`、`prompt.md`、`workflow.md`。
- `README.md`：Agent 职责与能力简介。
- `prompt.md`：系统提示词，语言标识用 `text`。
- `workflow.md`：工作流程定义（需求 → 设计 → 生成 → 自检 → 交付）。
- Agent 名称用 `kebab-case`，如 `flutter-agent`。

## 9. 文件命名规范

- 一律小写短横线命名（`kebab-case`）。
- 文档名与用途对应，如 `01-ai-era.md`、`generate-page.md`。
- 目录命名遵循 `docs/` 下的章节编号前缀。
- 图片命名：`章节-序号-描述`。

## 10. Git Commit 规范

统一格式：

```text
类型: 中文描述
```

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| `docs` | 文档 | docs: 新增 AI 开发时代章节 |
| `feat` | 新功能/新增内容 | feat: 新增 Flutter Agent |
| `fix` | 修复 | fix: 修复 README 链接错误 |
| `refactor` | 重构 | refactor: 优化 Prompt 目录结构 |
| `style` | 格式调整 | style: 统一 Markdown 标题格式 |
| `chore` | 杂项 | chore: 更新项目配置 |

规范要点：

1. 采用 **Conventional Commit + 中文描述**。
2. **Commit 不要太大**，一次只做一件事：
   - ❌ 不建议：`docs: 更新所有文档`
   - ✅ 建议：`docs: 新增 AI 开发时代章节`、`fix: 修复 MkDocs 导航错误`

## 11. 目录规范

- 每篇文档在 `docs/<章节>/` 下，配套资源统一命名：

| 文件 | 用途 |
| --- | --- |
| `index.md` | 原理与教程 |
| `architecture.md` | 架构说明 |
| `prompts.md` | 本章 Prompt 汇总 |
| `checklist.md` | 操作检查清单 |
| `faq.md` | 常见问题 |
| `examples.md` | 案例集 |

## 12. 文本规范

- 中英文之间加一个空格（如：`使用 Git 管理`）。
- 中文标点统一使用全角（`。`、`，`、`：`）。
- 数字与单位间加空格（如：`Flutter 3.24`）。
- 避免口语化表达，保持书面、精确。

## 13. 写作原则

1. 先写初稿，再迭代，不追求一次完美。
2. 每个知识点配一个可运行的案例。
3. 每个文档必须能独立阅读，不依赖其他文档的隐式前提。
4. 每日增量更新（3~5 个文件），长期维护。

## 14. 合规检查清单

写作完成后对照检查：

- [ ] 标题层级正确，无跳跃
- [ ] 中英文之间有空隙
- [ ] 图片存于 `assets/images/`，无网络图片
- [ ] 代码块带语言标识
- [ ] Prompt 遵循模板，占位符使用 `【】`
- [ ] 章节结构符合 9 段式
- [ ] 涉及规范处与 `rules/`、`templates/` 一致
