# Rules FAQ

> Rules 使用中的常见问题整理。按基础概念、规则分类、设计问题、生效问题、技术栈规则、流程协同、管理维护分类。

---

## 基础概念问题

## Q1: Rules 是什么？

### A

Rules 是约束 AI Coding Agent 长期行为的结构化规则集，以文件形式声明在特定范围内 AI 必须遵守的行为准则：代码怎么写、流程怎么走、什么不能做。它让 AI 产出从"看运气"变成"可预期"。

## Q2: 为什么需要 Rules？

### A

Coding Agent 的行为链路长（分析 → 修改项目 → 执行工具 → 产生代码），每一步的不确定性会被放大：理解偏差导致改错文件、风格漂移导致全库不一致。没有约束时产出质量不可预期、审查成本高。Rules 把团队要求前置成文件，让约束自动生效。

## Q3: Rules 和 Prompt 有什么区别？

### A

Prompt 告诉 AI"这一次做什么"，Rules 告诉 AI"长期应该怎么做"。Prompt 每个任务不同、任务结束即失效；Rules 低频演进、对所有任务持续生效。判断标准：对未来每个任务都成立的要求放 Rules，只针对当前任务的写 Prompt。

## Q4: Rules 和 Context 有什么区别？

### A

Context 是模型可见的动态信息（代码库内容、会话历史），帮助 AI 理解现状；Rules 是静态沉淀的约束条款，规定 AI 的行为方式。两者都占用上下文空间，所以 Rules 必须精炼——冗长规则会挤占真正有用的代码上下文。

## Q5: Rules 和 MCP 有什么区别？

### A

MCP 解决"AI 能不能触达外部系统"，是能力层；Rules 解决"AI 用这些能力时必须遵守什么"，是约束层。例如 Git MCP 给了提交代码的能力，Git Rules 约束提交信息的格式。能力越大越需要约束：没有 Rules 的 MCP 是敞开的大门。

## Q6: Rules 和 Agent 是什么关系？

### A

Agent 是规则的载体和执行者。Agent 配置定义角色（"你是 Flutter 专家"），Rules 定义纪律（"严格遵循三层结构"）。同一个 Agent 在不同项目可以加载不同 Rules——角色不变、纪律按项目定制，这是团队复用 Agent 资产的基础。

## 规则分类问题

## Q7: 项目级 Rules 和全局 Rules 怎么区分？

### A

项目级 Rules 描述某个具体项目的约定（分层架构、特有命名），跟随项目仓库管理；全局 Rules 描述跨项目通用的纪律（安全红线、通用工作习惯）。全局层应远少于项目层——只保留真正普适的条款。

## Q8: 技术栈 Rules 怎么组织？

### A

按语言或框架独立组织。本项目 `rules/` 目录规划了八个分类：android、kotlin、java、dart 管语言与平台约定，flutter、vue 管框架组织，git、review 管跨栈流程。归类原则：语言层面归语言目录，框架层面归框架目录，一条规则只出现在一个分类下。

## Q9: 团队 Rules 和个人偏好冲突怎么办？

### A

团队规则优先。规则的价值在于一致性，个人例外会让约束体系失效。认为规则不合理就走修订流程提出调整，而不是私下绕过。规则管共性约束，个案分歧通过沟通解决。

## Q10: 多个层级的规则同时存在时，以哪个为准？

### A

按具体程度裁决：项目 Rule > 技术栈 Rule > 团队通用 Rule > 全局默认。越具体的约束优先级越高。上层只定默认值，下层显式覆盖。优先级机制本身要写成文档并全员对齐，不依赖各自直觉。

## Q11: 一个任务会同时受多少条规则约束？

### A

一个典型任务是多层规则叠加的结果。例如开发 Flutter 页面同时受四层约束：`flutter/`（页面结构）、`dart/`（语言写法）、`git/`（提交规范）、`review/`（验收标准）。按需加载对应规则即可，不需要一次加载全部资产。

## 设计问题

## Q12: 一条 Rule 应该包含哪些部分？

### A

六个组成部分：适用范围（管什么语言/项目/场景）、目标（为什么存在）、约束（核心条款）、行为要求（工作方式约束）、示例（对的样子）、禁止事项（硬边界）。配合编号格式 `R-<编号>-<简述>`，详见 `03-rule-structure.md`。

## Q13: Rule 太长了怎么办？

### A

通常是粒度失衡：把多个主题塞进了一条规则。处理方式：按主题拆分成多条规则，各自归位到对应分类目录。单条规则保持一个主题、3~6 条可检查约束。另外 Linter 能机械检查的内容不要写进规则正文，一句话引用即可。

## Q14: Rule 太多了怎么办？

### A

执行最小化原则清理：长期无人违反且已成习惯的条款合并或移除；反复被违反的条款改表述或补工具检查；僵尸条款直接退役。健康信号是规则数量趋稳而非持续膨胀。每条规则入库前先问：这个问题高频吗？不写会发生什么？

## Q15: 两条 Rule 打架了怎么办？

### A

分三种形态处理：跨层级冲突按优先级裁决，上层补注合法覆盖说明；同层级冲突补边界条件消解或合并重写；规则与 Prompt 冲突时 Prompt 不突破红线。预防靠入库查重和定期交叉审读，发现后立即修复，不能留给 Agent 猜。

## Q16: 怎么判断一条 Rule 写得好不好？

### A

三问检验法：Agent 能照做吗？Reviewer 能判定通过与否吗？违反了能被发现吗？任何一问答不上来就需要改写。表述上避免"保持优雅""合理组织"这类无法判定的措辞，能量化的量化，不能量化的给判定标准。

## 生效问题

## Q17: 规则写了但 Agent 完全不遵守怎么办？

### A

按顺序排查三件事：一查加载——确认规则文件确实被 Agent 加载进上下文（路径、配置是否正确）；二查表述——条款是否模糊导致 AI 自行解释；三查冲突——是否与其他指令矛盾导致行为摇摆。完全没效果多数是加载问题。

## Q18: 规则时灵时不灵怎么办？

### A

常见原因：规则总量过大被上下文稀释、条款与其他指令存在隐性冲突、任务描述中出现了引导性更强的相反暗示。处理方式：精简规则总量、消除冲突条款、必要时在 Prompt 中用编号显式引用关键规则强化权重。

## Q19: 如何验证修改后的规则真的生效了？

### A

冒烟验证：用一个新旧规则会产生不同产出的任务测试 Agent；对照检查：逐条核对产出是否符合新条款；回归观察：后续迭代留意旧模式残留。注意部分 Host 需要重启会话才能加载更新后的规则文件。

## Q20: 本次任务想临时突破某条规则可以吗？

### A

不可以单方面绕过。若确属合理例外，走规则修订流程评估是否正式调整；若是任务确有特殊性，在评审同意后于项目级规则中显式声明该场景的处理方式，而不是靠口头豁免。红线的价值就在于不被随意突破。

## 技术栈规则问题

## Q21: Android Rules 应该重点管什么？

### A

平台层约定：组件使用方式、生命周期安全、资源命名与管理。语言层面的写法（协程、空安全）归 `kotlin/` 或 `java/` 管，Android 规则不重复语言规则的内容。两层各司其职，避免同一条款出现在两个目录。

## Q22: Flutter Rules 最重要的一条是什么？

### A

钉死状态管理选型与页面分层结构。Flutter 生态方案多样（GetX、Riverpod、Bloc……），是风格漂移的重灾区，团队必须明文固定选型与 Controller / Binding / View 分层约定，这通常是 Flutter 类规则中的第一优先级条款。

## Q23: Kotlin 和 Java Rules 可以合并吗？

### A

不建议合并。两种语言的惯用法差异明显（协程 vs 线程、空安全机制不同），混在一起会导致条款适用范围混乱。混合项目中两套规则并存，各自作用于对应语言的文件；纯 Kotlin 新项目只需加载 Kotlin 规则。

## Q24: Dart Rules 和 Flutter Rules 怎么分工？

### A

`dart/` 管语言细节：异步模式、类型标注、包管理等，脱离 Flutter 场景依然成立；`flutter/` 管框架组织：分层、状态、路由，必然涉及 Widget 概念。发现一条规则既讲语法又讲 Widget 结构，通常应该拆成两条各自归位。

## Q25: Vue Rules 有什么特殊之处？

### A

聚焦前端特有问题：组件拆分粒度、props 定义、状态归属、路由组织。移动端 + Web 并存的团队要注意：Vue 与 Flutter 共享同一套 `git/`、`review/` 流程规则，这是流程规则保持技术栈中立设计的直接收益。

## Q26: Git Rules 应该包含什么？

### A

版本控制的行为契约：提交信息格式（Conventional Commit + 中文描述）、一次提交只做一件事、分支命名规范、合并策略。它是所有技术栈共享的公共底座，条款中不得出现任何技术栈专属词汇。

## Q27: Review Rules 解决什么问题？

### A

把审查从"凭感觉"变成"对照清单"。它定义固定的检查维度（规范、安全、性能、逻辑）、明确的通过标准、结构化的输出格式，成为 AI 初审与人工复核的共同契约：AI 承担机械性检查，人聚焦业务正确性。

## Q28: 新增一种技术栈时要做什么？

### A

三步：在 `rules/` 下建立对应分类目录；从零沉淀或从相近技术栈改造规则（如从 Kotlin 改造 Dart 规则）；确认公共规则（git、review）无需为新技术栈修改——如果需要改，说明公共规则的技术栈中立性被破坏了，应重新审视。

## 流程协同问题

## Q29: Rules 在 Git 工作流中如何发挥作用？

### A

三个环节：提交前——规则约束改动范围与测试要求；提交时——Git 规则格式化提交信息与分支命名；追溯时——规范的提交历史让变更可读可查。当 Agent 通过 Git MCP 自动提交时，这些约束是不让自动化失序的前提。

## Q30: Rules 如何提升 Code Review 效率？

### A

AI 初审按 review 规则逐维度输出问题清单，承担风格、命名等机械性检查；人把注意力集中在业务逻辑正确性上。反向回流同样重要：review 中反复出现的问题类别，固化为新的编码规则，让问题在生成前就被拦住。

## Q31: Rules 可以自动化检查吗？

### A

部分可以。格式类、命名类条款可映射到 Linter / CI 工具（ktlint、dart analyze、ESLint 等），规则条文中一句话引用即可；行为类条款（先分析再动手）目前依赖 Agent 自身遵循加 Review 兜底。理想状态是"能自动的自动化，需判断的人工化"。

## 管理维护问题

## Q32: Rules 如何做版本管理？

### A

规则文件纳入 Git 管理，修改即提交、历史可追溯。编号一经分配不复用，废弃标记 `[已废弃]` 并保留迁移期而非直接删除。重要修订在文件内附简短变更说明，大版本调整记录到 CHANGELOG。

## Q33: 企业落地 Rules 的路径是什么？

### A

存量先行：把已有编码规范改写为可执行条款 → 按技术栈归入规则库 → 接入 Agent 配置自动生效 → 从真实踩坑持续沉淀新规则。已有的 Checkstyle、ktlint 等工具配置不必抛弃，作为可检查部分的技术底座。治理上统一入口、评审准入、定期回顾。

## Q34: Rules 需要多大的维护投入？

### A

四个频率：每次 PR 时留意现行规则缺口；每迭代回顾高频问题；每季度交叉审读防冲突、清僵尸条款；每半年审视整体结构。日常维护成本很低，关键是形成节奏。健康的标志是规则数量趋稳、风格类 Review 意见下降。

## 总结

- 概念辨析：Rules 管长期行为，Prompt 管单次任务，Context 给信息，MCP 给能力。
- 分类体系：项目 / 全局 / 技术栈 / 团队四层，越具体优先级越高。
- 设计标准：六要素齐备、单一主题、3~6 条可检查约束、三问检验过关。
- 生效保障：先查加载、再查表述、后查冲突；修改后必须冒烟验证。
- 技术栈分工：语言归语言、框架归框架、流程中立共享。
- 管理要点：Git 版本管理、废弃留迁移期、四个频率的维护节奏。
