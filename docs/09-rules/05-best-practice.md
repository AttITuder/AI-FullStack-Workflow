# Rules 最佳实践

> 面向长期维护项目的实战经验总结。围绕规则的设计、治理与协同，沉淀让 AI Coding 真正稳定可预期的落地做法。

---

## 为什么需要了解

写出一条规则容易，让一套规则体系在团队中**长期稳定生效**很难。本章把实战中验证过的经验固化为最佳实践，帮助团队避开常见陷阱：规则越堆越多、互相打架、形同虚设。

## 1. Rules 最小化原则

### 原则

只保留真正必要的规则，每条规则都要有存在的理由。

### 为什么重要

- 每条规则都占用 Agent 上下文，冗余规则挤占有效信息空间。
- 规则越多，单条规则的"注意力权重"越低，遵循率反而下降。
- 规则之间冲突的概率随数量上升。

### 落地方法

- 新增前先问：这个问题是否高频出现？不写规则会发生什么？
- 定期清理：长期无人违反且已成习惯的条款合并或移除。
- 用工具能解决的（格式、命名），交给 Linter，Rules 里一句话引用即可。

## 2. Rules 明确性

### 原则

条款表述必须无歧义，AI 和人读到的是同一个意思。

### 对比示例

| 模糊表述 | 明确表述 |
| --- | --- |
| 保持代码简洁 | 单个函数不超过 50 行 |
| 合理处理异常 | 禁止空 catch；捕获后必须记录或上抛 |
| 尽量复用组件 | 相同结构出现两次以上必须抽组件 |

### 判定标准

把规则交给两个不同的人独立验收同一份产出，如果结论可能不同，说明表述不够明确。避免双重否定、"建议尽量酌情"这类弱化词——要约束就写"必须 / 禁止"。

## 3. Rules 可执行性

### 原则

每条规则都能被 Agent 执行、被人检查通过与否。

### 三问检验法

1. **Agent 能照做吗？** 条款对应的动作是明确的吗？
2. **Reviewer 能判定吗？** 有客观的通过与不通过标准吗？
3. **违反能发现吗？** 靠人工审查还是工具检查？

三问中任何一问答不上来，这条规则就需要改写。无法落地的规则不如不写——它消耗上下文却不产生约束力。

## 4. Rules 单一职责

### 原则

一条 Rule 只管一个主题，一个主题只由一条 Rule 管。

### 违反的信号

- 规则标题里出现"以及""同时""和"连接的两个主题。
- 同一目录下两条规则的条款有明显重叠。
- 修改一个约定时需要同时改动多条规则。

### 处理方式

发现职责混杂时拆分：按 `03-rule-structure.md` 的分类原则归位到各自目录，各自编号。宁可条目多而清晰，不要条目少而混沌。

## 5. Rules 分层

### 推荐分层

```text
全局层   跨项目基本纪律（少量）
团队层   git / review 等流程规范 + 各技术栈细则
项目层   本项目差异覆盖（精简）
```

### 分层纪律

- 上层写默认值，下层做覆盖，禁止下层重复上层内容。
- 层级间用优先级机制裁决（见下节）。
- 内容放错层是常见病：通用纪律藏在技术栈文件里、项目特例混进团队资产——定期审读时重点检查归属。

## 6. Rules 优先级

### 显式声明优先级顺序

```text
项目 Rule > 技术栈 Rule > 团队通用 Rule > 全局默认
```

### 工程要点

- 把优先级机制写成团队文档并全员对齐，不依赖各自的直觉。
- 允许覆盖但要求显式：项目想偏离团队基线，在项目规则中明确声明，而不是沉默不加载。
- 覆盖点要在被覆盖的上层条款处留痕说明，方便后续项目了解"存在合法偏离场景"。

## 7. Rules 冲突处理

### 处理路径速查

| 冲突类型 | 处理方式 |
| --- | --- |
| 跨层级冲突 | 高具体度胜出；上层补注合法覆盖说明 |
| 同层级冲突 | 补边界条件消解，或合并重写 |
| 规则 vs Prompt | Prompt 不突破红线；确需例外走修订 |

### 预防机制

- 新规则入库前检索相近主题。
- 每季度一次规则交叉审读。
- 发现冲突立即修复，绝不留给 Agent 自行猜测。

## 8. Rules 与 Prompt 配合

### 配合模式

```text
Rules：长期约束（自动生效）
Prompt：本次任务指令（每次编写）
```

### 实践要点

- Prompt 不复述规则全文，用编号引用："遵循 R-03 页面分层"。
- Prompt 只补充任务特有信息：目标、范围、边界、验收标准。
- 任务级临时要求不要顺手写进 Rules——判断标准见 `01-overview.md` 第 4 节。
- 反向配合：反复出现在 Prompt 里的同类要求，是规则化的候选信号，应提炼入库。

## 9. Rules 与 MCP 配合

MCP 给能力，Rules 划边界。结合 `docs/08-mcp/` 的实践：

- **工具调用行为入规**：如"生产库查询前必须确认环境""提交代码前必须跑通测试"。Git MCP、数据库 MCP 的使用纪律都应落在对应规则里。
- **高危操作双人制**：MCP 的写入类工具（创建 PR、更新文档）在规则中声明需人工确认。
- **能力清单同步**：新增 MCP Server 时，评估是否需要配套新增或修订规则；下线 MCP 时同步清理相关条款。

## 10. Rules 与 Agent 配合

### 结合方式回顾

- 引用式：Agent 配置声明加载规则目录（主力）。
- 内嵌式：关键约束写进 Agent 系统提示词（随角色分发）。

### 实践要点

- Agent 定义角色，Rules 定义纪律，两者内容不重复。
- 一个 Agent 在不同项目加载不同 Rules——角色复用、纪律定制。
- Agent 变更时检查其引用的规则是否仍然准确；规则变更时反向检查各 Agent 引用（写作规范的同步要求）。

## 11. Rules 与 Git 配合

`rules/git/` 是所有开发流程的公共底座：

- 提交信息采用 Conventional Commit + 中文描述（与 `docs/00-roadmap/writing-style.md` 一致）。
- 一次提交只做一件事，Commit 不要太大。
- 分支命名、合并策略形成明文条款，Agent 创建分支和提交时按此执行。

工程收益：当 Agent 通过 Git MCP 自动提交时，规范的提交信息让变更历史保持可读可追溯——这是自动化流程不失序的前提。

## 12. Rules 与 Code Review 配合

`rules/review/` 让审查从"凭感觉"变成"对照清单"：

- 定义固定检查维度：规范、安全、性能、逻辑。
- 定义通过标准：哪些问题阻塞合并、哪些可以后续处理。
- 定义输出格式：结构化意见 + 严重级别，便于修复闭环。

实践要点：AI 初审按 review 规则输出问题清单，人工复核聚焦业务逻辑；review 中反复出现的问题类别，回流为新的编码规则——审查数据驱动规则演进。

## 13. 团队 Rules 管理

### 治理机制

- **统一入口**：所有成员与 Agent 加载同一份 `rules/`，禁止个人私藏。
- **评审准入**：新规则走评审，确认必要性、明确性、无冲突后入库。
- **定期回顾**：每个迭代复盘一次——哪些问题反复出现？哪条规则形同虚设？
- **责任到人**：每个分类目录有维护负责人，负责该域规则的时效性与一致性。

### 新成员引导

入职清单包含：阅读本章节 → 浏览 `rules/` 资产 → 观察一次真实任务的规则生效过程。规则体系的理解成本应控制在一小时以内——做不到说明规则本身需要精简。

## 14. Rules 版本管理

- 规则文件纳入 Git 管理，修改即提交，历史可追溯。
- 编号不复用：废弃标记 `[已废弃]` 并保留迁移期，不直接删除。
- 重要修订在文件内附简短变更说明（何时、为何）。
- 规则大版本调整（如分层结构调整）在 CHANGELOG 中记录。

## 15. Rules 长期维护

### 维护节奏

| 频率 | 动作 |
| --- | --- |
| 每次 PR | Review 时留意现行规则是否被违反或有缺口 |
| 每迭代 | 回顾高频问题，评估是否规则化 |
| 每季度 | 交叉审读防冲突，清理僵尸条款 |
| 每半年 | 整体审视分层结构与分类合理性 |

### 健康度信号

健康：规则数量趋稳、Review 中风格类意见占比下降、新人上手快。
不健康：规则持续膨胀、同类问题反复出现、成员经常绕过规则——分别对应需要清理、需要补强、需要检视合理性的信号。

## 16. 常见错误

### 错误一：照搬网上模板

拿来一份热门 Rules 清单全量入库，与团队实际脱节，大量条款形同虚设。

**修正**：从团队真实踩坑出发沉淀，外部模板只作参考视角。

### 错误二：规则大而全

试图用一份文档覆盖所有情况，条款互相稀释，Agent 记不住也做不到。

**修正**：最小化 + 分层 + 分类，按 `03-rule-structure.md` 的粒度标准裁剪。

### 错误三：模糊表述

"保持优雅""合理组织"式条款，无法执行也无法验收。

**修正**：用三问检验法改写，能量化量化，不能量化给判定标准。

### 错误四：只增不减

规则只进不出，两年后膨胀到没人读完。

**修正**：建立退出机制，定期清理合并僵尸条款。

### 错误五：改了规则没同步

规则变了，引用它的 Prompt 和 Agent 还在按旧口径工作。

**修正**：规则变更时强制检查引用方联动更新（写作规范的明确要求）。

### 错误六：用规则替代沟通

把所有分歧都试图塞进规则条文，规则变成战场。

**修正**：规则管共性约束，个案靠沟通；规则争议回到目标层面讨论而不是抠字眼。

## 总结

- 设计侧：最小化、明确性、可执行性、单一职责，Linter 能查的不进规则。
- 结构侧：三层分级（全局 / 团队 / 项目）、显式优先级、三类冲突各有处理路径。
- 协同侧：Prompt 用编号引用不复述、MCP 边界入规、Agent 引用双向同步、Git 与 Review 以规则为契约。
- 治理侧：统一入口、评审准入、定期回顾、责任到人。
- 版本侧：Git 管理、编号不复用、废弃留迁移期。
- 维护侧：四个频率的维护动作 + 两组健康度信号。
- 六个常见错误的核心教训：从实战出发、保持精炼、确保生效、持续修剪。
