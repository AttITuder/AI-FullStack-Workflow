# Rules 使用与接入

> 面向实际团队的 Rules 接入指南。重点不是编写某条具体规则，而是说明 Rules 如何进入 Coding Agent 的工作环境并持续生效。

---

## 为什么需要了解

Rules 写出来只是第一步，让它**稳定地被 Agent 加载、正确地生效、可控地演进**才是工程化落地的关键。本文覆盖 Rules 的使用方式、存放位置、加载机制、优先级与验证方法。

## 1. Rules 的使用方式

Rules 在 AI Coding 工作环境中有三种典型使用方式：

### 方式一：Agent 配置引用

在 Agent 配置（如 `agents/flutter-agent/`）中声明加载规则文件。Agent 启动时自动读取，对委派给它的所有任务生效。

### 方式二：会话启动加载

部分 Coding Agent 支持项目级规则文件约定（如在项目根目录放置特定命名的规则文件），会话启动时自动注入上下文。

### 方式三：Prompt 显式引用

在 Prompt 中显式要求"遵循 `rules/flutter/` 的规范"。这种方式最灵活，但依赖人记得写，适合作为前两种方式的补充而非主力。

### 选择建议

| 方式 | 可靠性 | 适用场景 |
| --- | --- | --- |
| Agent 配置引用 | 高 | 团队主力方式，约束自动生效 |
| 会话启动加载 | 高 | 项目级通用约定 |
| Prompt 显式引用 | 中 | 临时强调、特定任务补充 |

工程实践推荐以**前两种为骨架、第三种为补充**：核心约束靠配置保证生效，个别任务的特别要求靠 Prompt 强调。

## 2. Rules 文件放在哪里

结合当前项目结构，Rules 相关内容分布在三个位置，职责不同：

### 规则资产：`rules/`

```text
rules/
├── android/   # Android 编码规范
├── dart/      # Dart 语言规范
├── flutter/   # Flutter 编码规范
├── git/       # Git 提交与分支规范
├── java/      # Java 编码规范
├── kotlin/    # Kotlin 编码规范
├── review/    # 代码审查规范
└── vue/       # Vue 编码规范
```

这是**实际可复用的规则资产库**，按技术栈与场景分类。Agent 配置、团队协作都以这里的内容为准。

### 知识文档：`docs/09-rules/`

本章节是方法论知识体系，回答"怎么设计、怎么管理"的问题。**不要**把具体规则条文写进 docs 章节——那是 `rules/` 的职责。

### Agent 内置约束：`agents/`

`agents/` 目录下各 Agent 的配置中包含该角色的关键约束（如 flutter-agent 固化的分层要求）。这些约束通常是对 `rules/` 对应技术栈规则的提炼或引用。

### 三者关系

```text
docs/09-rules/     方法论（怎么写规则）
       ↓ 指导编写
rules/             规则资产（规则的正文）
       ↓ 引用/提炼
agents/            Agent 配置（规则随角色生效）
```

判断一段内容放哪里：讲道理的放 docs，定规矩的放 rules，跟角色走的放 agents。

## 3. Rules 如何被 AI Agent 使用

从 Agent 视角看，Rules 的生效链路如下：

```text
Agent 启动 / 接收任务
   ↓
加载已配置的 Rules
   ↓
规则进入模型上下文
   ↓
规划任务时参考规则
   ↓
生成产出时遵循规则
   ↓
自检时对照规则
```

理解这个链路有三个工程含义：

1. **规则必须在上下文中才能生效**：没有加载的规则等于不存在。接入后要验证规则确实进入了上下文。
2. **规则占用上下文空间**：规则越长，留给代码和任务描述的空间越少。这是 Rules 要精炼的根本原因。
3. **规则影响规划而不只是输出**：好的规则应该在 Agent "决定做什么"的阶段就发挥作用（比如先分析再动手），而不是只在"写代码"阶段纠正风格。

## 4. 项目级 Rules

项目级 Rules 描述**某个具体项目的约定**，例如：

- 项目的分层架构与目录组织。
- 本项目特有的命名约定。
- 与其他系统集成的注意事项。
- 本项目的禁止事项。

### 特点

- 跟随项目仓库版本管理。
- 只对该项目的 Agent 会话生效。
- 内容与项目强耦合，跨项目复用价值低。

### 建议

- 新项目初始化时就建立 Rules 骨架，而不是等项目变大后补。
- 项目级规则优先声明"本项目与通用规范的差异"，避免重复通用内容。

## 5. 全局 Rules

全局 Rules 描述**跨项目通用的行为准则**，例如：

- 通用编码原则（可读性优先、防御性编程）。
- 通用安全红线（不硬编码密钥、不删除不确定的文件）。
- 通用工作习惯（先给方案再动手、改动最小化）。

### 特点

- 通常放在用户目录或团队共享配置中，对所有项目生效。
- 变更频率低，评审更严格。
- 数量应远少于项目级规则——只保留真正普适的条款。

### 分层建议

```text
全局 Rules（少量，普适纪律）
   +
项目级 Rules（中等，项目约定）
   +
技术栈 Rules（按需，语言细节）
```

## 6. 技术栈 Rules

技术栈 Rules 按**语言或框架**组织，对应本项目的八个分类：

| 分类 | 管什么 |
| --- | --- |
| `android/` | Android 平台的架构、生命周期、组件使用 |
| `kotlin/` | Kotlin 语言层面的写法约定 |
| `java/` | Java 语言层面的写法约定 |
| `dart/` | Dart 语言层面的写法约定 |
| `flutter/` | Flutter 框架的页面、状态、路由组织 |
| `vue/` | Vue 项目的组件、状态、路由组织 |
| `git/` | 提交信息格式、分支命名、合并策略 |
| `review/` | 代码审查的检查维度与通过标准 |

技术栈 Rules 是复用价值最高的一层：在一个 Flutter 项目验证过的规则，可以直接用于下一个 Flutter 项目。

### 组合使用

一个实际任务是多层规则叠加的结果。例如"开发一个 Flutter 页面"同时受 `flutter/`（页面结构）、`dart/`（语言写法）、`git/`（提交规范）、`review/`(验收标准) 四层规则约束。

## 7. 团队 Rules

团队 Rules 是**团队共识的制度化形态**，它的特殊性不在内容而在治理：

- **来源**：从团队真实踩坑中沉淀，而非照搬网上模板。
- **变更**：走评审流程，任何人不能单方面修改。
- **同步**：规则变更需同步更新相关 Prompt 与 Agent 引用（写作规范明确要求）。
- **告知**：新成员入职清单中包含"阅读团队 Rules"一项。

### 治理节奏建议

- 每个迭代回顾一次：哪些问题反复出现？是否需要新增规则？
- 规则条目有编号（如 `R-01-命名`），废弃的规则标记而非直接删除，保留演进痕迹。
- 用 Git 管理规则文件本身，规则的每次修改都有提交记录可追溯。

## 8. Rules 加载与优先级

当多个层级的规则同时存在时，需要明确的优先级机制。

### 典型优先级（高 → 低）

```text
1. 项目级 Rules        （本项目特例）
2. 技术栈 Rules        （本栈通用约定）
3. 团队 / 全局 Rules   （跨项目纪律）
4. Agent 默认行为      （工具自带约定）
5. 模型默认行为        （无约束时的自然倾向）
```

逻辑依据：**越具体的约束优先级越高**。项目级规则是对通用规则在本项目语境下的细化或覆盖。

### 冲突示例

假设全局规则说"函数注释必须完整"，而某项目的规则说"仅公共 API 写注释，内部实现靠命名自明"——按优先级，该项目内的 Agent 应遵循项目级规则。

### 工程要点

- 优先级机制要写成文档并在团队内对齐，避免各成员理解不一致。
- 尽量避免让同一条款出现在多个层级；如果出现，高层级只保留"默认值"，由低层级覆盖。
- Coding Agent 的具体优先级行为以其官方实现为准，接入时应实测验证。

## 9. Rules 修改后的验证

规则不是改完就完事，必须验证新规则真的生效。

### 验证方法

1. **冒烟验证**：用一个已知会被新旧规则产生不同产出的任务测试 Agent，观察行为是否符合新规则。
2. **对照检查**：检查 Agent 产出是否逐条符合修改后的规则条款。
3. **回归观察**：接下来的一两个迭代内，留意相关类型任务是否还有旧模式残留。

### 常见"规则不生效"的原因

| 现象 | 可能原因 |
| --- | --- |
| 完全没效果 | 规则文件没有被 Agent 加载（路径错、配置漏） |
| 时灵时不灵 | 规则太长被上下文稀释，或与其他指令冲突 |
| 部分遵守 | 条款表述模糊，AI 自行解释 |
| 反向执行 | 条款含双重否定等歧义表述 |

排查顺序：先确认加载，再确认表述，最后确认冲突。详细排查见 `06-faq.md`。

## 10. 常见问题

### 规则越多越好吗？

不是。每条规则都消耗上下文，过多规则互相干扰反而降低遵循率。保持最小必要集合，见 `05-best-practice.md` 的最小化原则。

### 规则应该用中文还是英文？

以团队沟通语言为准，保证人类能顺畅评审。多数模型对两种语言的理解都不构成障碍，关键是表述精确。

### 规则和 Linter 配置重复了怎么办？

Linter 能机械检查的部分（格式、命名），Rules 里一句话引用即可（如"遵循项目 ktlint 配置"），不要把 Linter 规则全文复制进 Rules。Rules 重点写 Linter 查不了的行为约定。

### 个人可以绕过团队规则吗？

不可以。规则的价值在于一致性，个人例外会让约束体系失效。认为规则不合理就走修订流程，而不是私下绕过。

## 本章总结

- 三种使用方式：Agent 配置引用（主力）、会话启动加载、Prompt 显式引用（补充）。
- 三个存放位置的分工：docs 讲方法、rules 存资产、agents 随角色生效。
- Rules 生效链路：加载 → 进上下文 → 影响规划 → 约束产出 → 对照自检。
- 四层规则体系：全局、项目级、技术栈、团队治理，越具体优先级越高。
- 规则修改后必须验证：冒烟验证 + 对照检查 + 回归观察。
