# Rules 概述

> 定位：不是编码规范合集，而是 AI FullStack Workflow 知识库。目标读者：Android 开发者、Flutter 开发者、全栈开发者、企业研发人员。

---

## 1. Rules 是什么

### 定位

Rules 是约束 AI Coding Agent 行为的**结构化规则集**。它以文件形式存在，声明在特定范围内（语言 / 项目 / 场景）AI 必须遵守的行为准则：代码怎么写、命名怎么起、流程怎么走、什么不能做。

它不是一份"给 AI 看的建议文档"，而是让 AI 产出**可预期**的工程机制。

### 相关概念辨析

围绕 "Rules" 有几个相近概念，在本项目中的含义如下：

| 概念 | 含义 | 本项目对应 |
| --- | --- | --- |
| AI Coding Rules | 约束 AI 编码行为的规则集合 | 本章讨论的核心主题 |
| 项目规则 | 约束某个具体项目的规则 | 项目级 Rules（如架构约定、目录规范） |
| Agent Rules | 写进 Agent 配置的行为约束 | 各 Agent 引用或内置的规则 |
| Coding Standards | 传统软件工程中的编码规范 | Rules 的内容来源之一 |

四者的关系：Coding Standards 提供内容素材，项目规则限定作用范围，Agent Rules 决定生效方式，AI Coding Rules 是它们的统一形态——**写成 AI 可理解、可遵循的结构化文本**。

### 解决的问题

没有 Rules 时，AI Coding 存在三类典型问题：

1. **产出不稳定**：同样的需求，今天生成 GetX 架构，明天生成 Provider 架构，风格随机。
2. **不符合团队标准**：AI 默认按通用最佳实践写代码，与团队的既有约定冲突。
3. **审查成本高**：每个 AI 产出都要人工纠正一遍风格问题，重复劳动。

Rules 把这些"每次都要口头纠正的事"固化为文件，让约束自动生效。

## 2. 为什么 AI Coding Agent 需要 Rules

### 普通 AI 与 Coding Agent 的行为差异

普通对话式 AI 的行为链路很短：

```text
用户提问
   ↓
AI 回答
```

回答错了、风格不对，影响有限——用户可以忽略或追问。而 Coding Agent 的行为链路长得多：

```text
需求
   ↓
分析
   ↓
修改项目
   ↓
执行工具
   ↓
产生代码
```

Agent 会真实地修改文件、执行命令、产生大量代码。行为一旦偏离预期，代价是返工、引入 Bug、污染代码库。

### 长链路放大了不确定性

链路越长，每一步的不确定性会被逐步放大：

- 分析阶段理解偏差 → 改错文件。
- 执行阶段命令不当 → 构建失败。
- 产出阶段风格漂移 → 全库代码风格不一致。

对单次问答来说风格漂移是小问题，对一个持续被 Agent 修改的长期项目来说是大问题。

### 因此需要稳定的行为约束

Coding Agent 需要一套**始终在场**的约束，而不是每次对话都靠人提醒：

- 约束必须在任务开始前就生效，而非事后补救。
- 约束必须对所有任务一致，而非因人而异。
- 约束必须可版本化、可演进，而非散落在聊天记录里。

Rules 正是这样一种机制：**把团队对 AI 的所有要求前置成文件，让 Agent 在任何任务中都自动遵守**。

## 3. Rules 在 AI FullStack Workflow 中的位置

在完整工作流中，Rules 承担**约束层**的角色：

```text
Model（能力来源）
   ↓
Agent（规划与执行）
   ↓
MCP（工具连接）
   ↓
Rules（行为约束）
   ↓
Workflow（稳定流程）
   ↓
Code（最终产出）
```

各层的分工：

- **Model** 决定 AI 有多聪明。
- **Agent** 决定 AI 怎么干活。
- **MCP** 决定 AI 能触达哪些外部工具。
- **Rules** 决定 AI 干活时必须遵守什么。
- **Workflow** 把以上能力组织成稳定可复现的流程。

一个关键认知：Model 越强，越需要 Rules。模型能力强意味着它能做更多事；如果不加约束，它也会以更多种"意想不到的方式"做事。Rules 不限制模型的能力上限，只约束行为的边界。

在知识库层面，Rules 章节处于 MCP 章节（`docs/08-mcp/`）之后、Prompt 与 Agent 章节（`docs/10-prompts/`、`docs/11-agent/`）之前，承接"MCP 让 Agent 能做事"，引出"Prompt 让 Agent 会做事""Agent 配置固化做事方式"。

## 4. Rules 与 Prompt 的区别

这是最容易混淆的一对概念，核心区别一句话：

> **Prompt 告诉 AI"这一次做什么"，Rules 告诉 AI"长期应该怎么做"。**

| 维度 | Prompt | Rules |
| --- | --- | --- |
| 生效范围 | 单次任务 | 长期、所有任务 |
| 内容重点 | 本次的目标、上下文、输出要求 | 编码规范、行为边界、禁止事项 |
| 变更频率 | 每个任务不同 | 低频演进 |
| 存放位置 | 对话输入或 `prompts/` 模板 | 规则文件或 Agent 配置 |
| 失效方式 | 任务结束即失效 | 直到被显式修改 |

两者是配合关系而非替代关系：

- 一个新功能任务的完整输入 = **Rules（长期约束）+ Prompt（本次任务指令）+ Context（项目现状）**。
- Prompt 中不需要重复 Rules 已有的内容（如命名规范），只需引用"遵循项目 Rules"。
- Rules 中也不应写入具体任务的指令，那是 Prompt 的职责。

判断一条内容该放哪里，可以用这个标准：**如果这条要求对未来的每个任务都成立，放进 Rules；如果只针对当前这一次任务，写进 Prompt。**

## 5. Rules 与 Context 的区别

Context 是模型可见的上下文信息，包括代码库内容、会话历史、用户指令等。

| 维度 | Context | Rules |
| --- | --- | --- |
| 性质 | 信息（是什么） | 约束（应该怎样） |
| 来源 | 动态采集：读文件、读会话 | 静态沉淀：人工编写、评审入库 |
| 作用 | 帮助 AI 理解现状 | 约束 AI 的行为方式 |
| 大小控制 | 按需加载、够用即可 | 保持精炼、最小必要 |

两者的关系：Rules 本身也占用 Context 空间，所以 Rules 必须**精炼**——冗长的 Rules 会挤占真正有用的代码上下文。这也是"Rules 最小化原则"的由来（详见 `05-best-practice.md`）。

另一个配合点：Rules 可以指导 AI **主动获取 Context**，例如规定"动手前先读取模块 README 和数据模型"，这比把所有信息塞进 Context 更高效。

## 6. Rules 与 MCP 的区别

MCP（见 `docs/08-mcp/`）解决的是"AI 能不能触达外部系统"，Rules 解决的是"AI 用这些工具时必须遵守什么"。

| 维度 | MCP | Rules |
| --- | --- | --- |
| 属性 | 协议 / 连接机制 | 行为约束 |
| 回答的问题 | 能做什么 | 允许做什么、禁止做什么 |
| 形态 | Server + Tools | 结构化文本 |
| 失控风险 | 工具误调用 | 行为偏离规范 |

两者必须配合使用。典型场景：

- Git MCP 给了 Agent 创建分支、提交代码的能力，Git Rules 则约束提交信息的格式、分支命名规范。
- 数据库 MCP 给了 Agent 查询数据的能力，Rules 则约束"生产环境只读""查询前确认表名"。

**能力越大，越需要约束。** 没有 Rules 的 MCP 是敞开的大门，有了 Rules 的 MCP 才是有门禁的通道。

## 7. Rules 与 Agent 的关系

Agent 是规则的**载体和执行者**。Rules 通过三种方式与 Agent 结合：

1. **引用式**：Agent 配置中声明"加载某目录下的 Rules"，规则独立维护。
2. **内嵌式**：关键约束直接写进 Agent 的系统提示词，随 Agent 分发。
3. **混合式**：通用约束内嵌，技术栈细则引用外部文件（本项目采用的方式，参考 `agents/flutter-agent/` 的组织思路）。

Agent 与 Rules 的分工：

- **Agent 定义角色**："你是 Flutter 专家，负责页面开发"。
- **Rules 定义纪律**："严格遵循 Controller / Binding / View 分层"。

同一个 Agent 在不同项目可以加载不同的 Rules——这正是团队能复用同一套 Agent 资产的原因：角色不变，纪律按项目定制。

## 8. Rules 与代码规范的关系

传统软件工程的代码规范（Coding Standards）是 Rules 最重要的内容来源，但两者不等价：

| 维度 | 传统代码规范 | AI Coding Rules |
| --- | --- | --- |
| 读者 | 人类工程师 | AI Agent（兼人类） |
| 表达形式 | 文档 + Linter 配置 | 结构化自然语言 + 可检查条款 |
| 执行方式 | 人记忆 + 工具检查 | Agent 加载后自动遵循 |
| 覆盖范围 | 主要是代码本身 | 代码 + 流程 + 行为 + 禁止事项 |

三个关键差异：

1. **范围更广**：传统规范管代码怎么写，AI Rules 还要管 Agent 的行为——比如"先分析再动手""禁止未经确认删除文件"。
2. **表达不同**：人类可以理解"保持代码简洁"这类模糊表述，AI 更需要"单个函数不超过 50 行"这种可执行的明确条款。
3. **落地更快**：传统规范靠 Code Review 事后兜底，AI Rules 在生成前就生效，把问题消灭在源头。

企业落地时的推荐路径是：**存量代码规范 → 改写为可执行的条款 → 按技术栈归入 Rules → Agent 自动遵循**。已有的 Checkstyle、ktlint、dart analyze 等工具配置不必抛弃，而是作为 Rules 中"可检查部分"的技术底座。

## 9. 本项目中的 Rules

本项目将 Rules 分为两个层面：

### 规则资产：`rules/`

项目根目录的 `rules/` 存放实际可复用的规则资产，按技术栈与场景组织为八个分类：

```text
rules/
├── android/   # Android 编码规范
├── dart/      # Dart 语言规范
├── flutter/   # Flutter 编码规范
├── git/       # Git 提交与分支规范
├── java/      # Java 编码规范
├── kotlin/    # Kotlin 编码规范
├── review/    # 代码审查规范
└── vue/       # Vue 编码规范
```

规则资产的编写遵循 `docs/00-roadmap/writing-style.md` 中的 Rule 规范：

- 每条规则必须**可执行、可检查**，避免模糊表述。
- 每个 Rule 文件开头声明适用范围（语言 / 项目 / 场景）。
- 规则编号格式：`R-<编号>-<简述>`，例如 `R-01-命名`。
- 规则与对应 Prompt、Agent 保持引用同步。

目前 `rules/` 各分类已完成目录规划，具体规则内容按 Sprint 节奏持续建设中。

### 知识体系：`docs/09-rules/`

本章节不存放具体规则，而是回答方法论问题：

- Rule 应该怎么设计？（`03-rule-structure.md`）
- Rules 如何接入 Agent 工作环境？（`02-install.md`）
- 规则如何驱动真实开发流程？（`04-workflow.md`）
- 团队如何管理 Rules？（`05-best-practice.md`）

两者的关系类比：`docs/09-rules/` 是"立法法"，`rules/` 是"法律条文汇编"。前者教你怎么写出好规则，后者是规则本身的集合。新增或修改规则资产时，应以本章节的方法论为准绳。

## 10. Rules 的价值

### 稳定性

同样的任务，无论谁发起、何时发起，Agent 的行为方式一致。消除"看运气"的随机性，是 Rules 最直接的价值。

### 一致性

多人团队中，不同成员使用的 AI 产出的代码风格一致。新人加入时不需要重新磨合 AI 习惯，克隆项目即获得全部约束。

### 可复用

Rules 是一次编写、处处生效的资产。在一个项目验证过的规则，可以直接复制到同类项目，团队经验快速扩散。

### 团队协作

Rules 让团队拥有统一的"AI 行为契约"：审查者知道 AI 产出必然符合哪些标准，可以把注意力集中在业务逻辑上；管理者知道质量下限由规则保证，而非依赖个人自觉。

### AI 行为约束

明确划出 AI 的行为边界：哪些操作允许自主执行、哪些必须人工确认、哪些绝对禁止。这是安全使用 Agent 的前提，尤其在接入 MCP 之后（参见 `docs/08-mcp/05-best-practice.md`）。

### 项目长期维护

项目演进过程中，Rules 记录着"我们为什么这样约定"。规则变更走评审、有版本记录，新成员通过阅读 Rules 就能快速理解项目约定，降低维护成本。

## 总结

- Rules 是约束 AI Coding Agent 长期行为的结构化规则集，是工作流中的"约束层"。
- Coding Agent 行为链路长，不确定性被放大，必须有前置、一致的稳定约束。
- 层级关系：Model 定能力，Agent 定执行，MCP 定连接，Rules 定纪律，Workflow 定流程。
- 与 Prompt 区别：Prompt 管一次任务，Rules 管长期行为；与 MCP 区别：MCP 给能力，Rules 划边界。
- 本项目双层结构：`rules/` 存规则资产（八个分类），`docs/09-rules/` 存知识体系。
- Rules 的价值在于稳定性、一致性、可复用、团队协作、行为约束与长期维护。
