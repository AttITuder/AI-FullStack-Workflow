# Rules Workflow

> 本 Sprint 核心文章。从真实研发流程出发，讲解 Rules 如何驱动 AI 开发：让约束在流程的每个环节自动生效，而不是靠人肉把关。

---

## 为什么需要了解

Rules 单独看只是文本，它的真正价值体现在**流程中**：需求进来时规则先行，Agent 执行时规则约束，产出验收时规则对照。本文按任务类型和技术栈给出标准工作流，让团队把 Rules 组织进"需求 → 编码 → 测试 → 审查 → 合并"的完整链路。

## 1. Rules 驱动的 AI 开发流程

一切任务共享同一个主循环：

```text
需求
   ↓
Rules（约束前置生效）
   ↓
Agent（在规则边界内规划执行）
   ↓
MCP（按规则使用外部工具）
   ↓
代码
   ↓
测试
   ↓
Review（对照规则验收）
```

与无 Rules 流程的本质区别在三个环节：

- **起点**：约束在任务开始前就进入上下文，而非产出后人工纠正。
- **过程**：Agent 的规划、工具调用都在规则边界内进行。
- **终点**：Review 有明确的规则清单可对照，通过与否有客观标准。

### 步骤详解

1. **需求**：明确要做什么，写出可验收的目标。
2. **Rules**：确认本次任务涉及的规则层——技术栈规则、Git 规则、Review 规则是否已在 Agent 上下文中。
3. **Agent**：委派任务。Agent 按规则要求的方式工作（如先分析再动手）。
4. **MCP**：需要外部工具时（构建、提交、查询），按 Git / 工具类规则的约定操作。
5. **代码**：产出符合技术栈规则的代码。
6. **测试**：验证行为，失败则迭代修复。
7. **Review**：按 `review/` 规则逐项检查，人工复核后合并。

## 2. 新功能开发 Workflow

### 流程

```text
1. 需求拆解 → 明确页面 / 模块 / 接口范围
2. 方案对齐 → 确认遵循的分层架构与技术选型
3. 遵循技术栈规则生成代码 → 分层、命名、状态管理按规范
4. 自检 → 对照规则清单逐条检查
5. 测试 → 构建 + 用例验证
6. Review → review/ 规则验收
7. 提交 → git/ 规则格式化提交信息
```

### Rules 的作用点

| 环节 | 起作用的规则 |
| --- | --- |
| 方案对齐 | 项目级架构约定 |
| 生成代码 | 技术栈规则（分层、命名、组件使用）|
| 自检 | 规则中的禁止事项清单 |
| Review | `review/` 通过标准 |
| 提交 | `git/` 提交信息与分支规范 |

关键实践：**Prompt 中引用规则编号**（如"遵循 R-03 页面分层"），比复述规则全文更省上下文且指向明确。

## 3. Bug 修复 Workflow

### 流程

```text
1. 现象输入 → 报错信息、复现步骤
2. 定位根因 → 先读代码再下结论，禁止猜着改
3. 最小修改 → 只改必要代码，不夹带重构
4. 验证闭环 → 复现场景 + 相关测试通过
5. 记录说明 → 根因与修复逻辑写入提交信息
```

### Rules 的作用点

Bug 修复最容易失控的是"顺手改"，行为要求型规则在此处最有效：

- "先定位根因再修改"约束分析阶段。
- "最小改动、不夹带重构"约束执行范围。
- "提交信息写清根因"约束记录环节（`git/` 规则）。

修复类任务的 Prompt 可以很短，因为长期约束已由 Rules 承担——这正是 Rules 与 Prompt 分工的价值。

## 4. 重构 Workflow

### 流程

```text
1. 明确范围 → 重构目标与预期收益
2. 建立基线 → 确保现有测试通过
3. 小步执行 → 每步改动独立可验证
4. 行为不变 → 对照测试确认语义未变
5. 回归验证 → 全量测试 + 构建检查
6. Review → 重点审查一致性
```

### Rules 的作用点

重构对规则的依赖集中在两条纪律：

- **行为不变原则**：只允许改变内部结构，不允许改变外部行为。这条必须写成硬约束，因为模型天然倾向于"顺便优化一下"。
- **小步提交纪律**：每步提交独立可回滚（`git/` 规则）。大爆炸式重构一旦出错无法定位。

重构前还应检查：目标代码是否违反现行规则？如果旧代码不符合新规则，重构是让它们合规的机会；但要区分"本次重构范围内顺手合规"与"全库扫荡式整改"——后者应立项单独做。

## 5. Code Review Workflow

### 流程

```text
1. 变更输入 → diff、关联需求、变更目的
2. AI 审查 → 按 review/ 规则逐维度检查
3. 输出意见 → 结构化问题清单 + 严重级别
4. 人工复核 → 判断意见合理性，聚焦业务逻辑
5. 修复迭代 → 按意见修改并复验
6. 通过合并 → 满足 review/ 通过标准
```

### review/ 规则的核心地位

`rules/review/` 是 AI 与人类审查者之间的**共同契约**：

- 对 AI：规定了审查的检查维度（规范、安全、性能、逻辑）和输出格式。
- 对人：规定了通过标准，避免"每个人心里一把尺"。

有了这份契约，AI 初审承担机械性检查（风格、命名、明显缺陷），人把注意力放在业务正确性上——审查效率与质量同时提升。

## 6. Android Workflow

Android 任务涉及四层规则叠加：平台规则、语言规则、版本控制规则、审查规则。

```text
需求
   ↓
android/ 规则（组件、生命周期、资源管理）
   +
kotlin/ 或 java/ 规则（语言写法）
   ↓
Agent 生成代码
   ↓
构建验证（配合 Gradle MCP）
   ↓
真机验证（配合 ADB MCP）
   ↓
review/ 规则验收
   ↓
git/ 规则提交
```

### 各层分工示例

| 层 | 管什么 | 不管什么 |
| --- | --- | --- |
| `android/` | Activity/Fragment 使用方式、生命周期安全、资源命名 | 语言语法 |
| `kotlin/` | 协程作用域、空安全处理、扩展函数使用 | 平台 API |
| `java/` | 集合与并发写法（遗留模块适用） | Kotlin 特性 |
| `git/` | 分支命名、提交格式 | 代码内容 |
| `review/` | 验收标准 | 具体实现 |

一个 Android 任务通常只需加载三份规则文件（android + kotlin + git），review 规则统一在验收环节生效——按需加载本身就是规则体系的设计成果。

## 7. Flutter Workflow

```text
需求
   ↓
flutter/ 规则（分层、状态管理、路由）
   +
dart/ 规则（异步模式、类型标注）
   ↓
Agent 生成页面三件套
（Controller / Binding / View）
   ↓
静态检查（flutter analyze）
   ↓
运行验证
   ↓
review/ 规则验收
   ↓
git/ 规则提交
```

### Flutter 规则的特殊价值

Flutter 生态的状态管理方案多样（GetX、Riverpod、Bloc……），是风格漂移的重灾区。`flutter/` 规则最重要的使命就是**钉死本团队的状态管理选型与分层结构**——这通常是 Flutter 类规则中优先级最高的一条。

配合关系：`dart/` 管语言细节（async 写法、类型标注），`flutter/` 管框架组织，两者不重叠。若发现一条规则既涉及 Dart 语法又涉及 Widget 结构，应考虑拆分归属。

## 8. Vue Workflow

```text
需求
   ↓
vue/ 规则（组件拆分、状态管理、生命周期）
   ↓
Agent 生成组件
   ↓
构建与 lint 验证
   ↓
review/ 规则验收
   ↓
git/ 规则提交
```

### 要点

- `vue/` 规则聚焦前端特有问题：组件粒度、props 定义、状态归属、路由组织。
- 前端项目常与后端联调，涉及接口约定的部分由项目级规则补充（如接口封装位置），不要塞进 `vue/` 通用规则。
- 移动端 + Web 并存的项目（本项目典型场景），Vue 与 Flutter 团队共享同一套 `git/`、`review/` 规则——这是流程规则独立于技术栈设计的直接收益。

## 9. 多技术栈项目 Workflow

一个仓库同时包含 Android、Flutter、Vue 模块时，规则的组织与调度：

```text
任务进入
   ↓
识别技术栈 → 决定加载哪套技术栈规则
   ↓
公共规则始终生效（git/、review/）
   +
对应技术栈规则按需加载
（flutter/ 或 android/ 或 vue/）
   ↓
跨栈任务 → 各栈规则分别作用于各自产出
   ↓
统一 Review → 统一验收标准
```

### 三条工程纪律

1. **规则按目录物理隔离**：技术栈规则绝不互相引用具体条款，避免跨栈耦合。
2. **公共规则保持中立**：`git/`、`review/` 中不得出现任何技术栈专属词汇。
3. **跨栈任务的 Prompt 显式声明范围**："本次只改 Flutter 模块"，防止 Agent 越界加载或越界修改。

## 10. 团队协作 Workflow

多人团队中 Rules 的协作流转：

```text
新成员入职
   ↓
阅读 docs/09-rules/ + rules/ 资产
   ↓
配置本地环境（含 Rules 引用的工具链）
   ↓
日常开发（规则自动约束 AI 产出）
   ↓
发现问题 → 提出规则修订
   ↓
评审 → 更新 rules/ → 同步 Prompt / Agent 引用
   ↓
团队同步（变更记录周知）
```

### 协作机制要点

- **统一的规则入口**：所有成员、所有 Agent 加载同一份 `rules/`，禁止个人私藏规则文件。
- **修订走流程**：任何人发现规则不合理，提出修订建议走评审，不私下绕过。
- **知识回流**：每次踩坑复盘的结论，判断是否需要固化为新规则——团队的规则库随实战持续生长。

## 11. AI Agent + MCP + Rules 综合 Workflow

最终形成三者协同的完整工作流：

```text
需求
   ↓
Rules（约束前置：怎么做事有边界）
   ↓
Agent（理解与规划：做什么事有章法）
   ↓
MCP（能力触达：用哪些工具有通道）
   ↓
执行（生成代码 / 调用工具 / 操作系统）
   ↓
验证（测试 / 构建 / 真机 / 数据核对）
   ↓
Review（review/ 规则验收 + 人工复核）
   ↓
交付（git/ 规则提交合并）
```

### 三者的协同关系

| 角色 | 职责 | 失去另两者会怎样 |
| --- | --- | --- |
| Rules | 定边界、定标准 | Agent 能力越强偏得越远 |
| Agent | 理解、规划、执行 | 没有 MCP 只能空想，没有 Rules 放飞自我 |
| MCP | 连接真实工具与数据 | 没有 Rules 就是敞开的大门 |

### 一个综合场景走读

以"修复线上崩溃并发布热修版本"为例：

1. **需求**：崩溃日志 + 影响范围。
2. **Rules 生效**：Bug 修复纪律（根因先行、最小改动）+ Kotlin 规则 + Git 发布分支规范。
3. **Agent 规划**：分析堆栈 → 定位文件 → 给出修复方案待确认。
4. **MCP 执行**：ADB 拉取设备日志佐证根因 → 修改代码 → Gradle 构建 → ADB 安装验证。
5. **验证**：复现场景不再崩溃 + 相关用例通过。
6. **Review**：按 `review/` 标准初审，人工确认修复思路。
7. **交付**：按 `git/` 规范在热修分支提交，提交信息包含根因说明。

整个过程中，人只在两个点介入：确认修复方案、最终 Review。其余环节的秩序全部由 Rules 维持——这就是"约束层"的意义。

## 总结

- 主循环：需求 → Rules 前置 → Agent 执行 → MCP 触达 → 代码 → 测试 → Review 验收。
- 新功能靠技术栈规则管形态，Bug 修复靠行为规则管纪律，重构靠"行为不变 + 小步提交"兜底。
- Code Review 的效率来自 `review/` 规则这个共同契约：AI 管机械检查，人管业务正确性。
- 各技术栈工作流 = 公共规则（git/review）+ 该栈规则（android/kotlin/java、flutter/dart、vue）按需组合。
- 多栈项目的三条纪律：目录隔离、公共中立、任务声明范围。
- 团队协作的关键是统一入口与修订流程，规则库随实战生长。
- Agent + MCP + Rules 的终局：人只在关键决策点介入，秩序由约束层维持。
