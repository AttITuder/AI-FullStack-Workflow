# Rules 结构设计

> 本章节核心基础文章。讲解一条 Rule 应该如何设计：结构、粒度、分类、优先级与可维护性。所有 `rules/` 资产的建设都应以本文为准绳。

---

## 为什么需要了解

规则写得好不好，直接决定 Agent 遵循得好不好。模糊的规则等于没有规则，冗长的规则互相打架，过细的规则维护不动。本文给出一套 Rule 结构设计方法，让每条规则**可执行、可检查、可维护**。

## 1. Rule 的基本结构

本项目遵循 `docs/00-roadmap/writing-style.md` 中定义的 Rule 规范，一条 Rule 的基本骨架如下：

```text
# 规则标题（编号 + 简述）

适用范围：<语言 / 项目 / 场景>

## 约束内容

<明确的行为要求>

## 示例 / 禁止事项

<对的样子与错的样子>
```

三个必备要素：

1. **声明适用范围**：每个 Rule 文件开头必须声明这条规则管什么语言、什么项目、什么场景。范围不明的规则无法被正确应用。
2. **编号格式**：`R-<编号>-<简述>`，例如 `R-01-命名`。编号让规则可被引用——Prompt、Agent 配置中可以写"遵循 R-01"，而不是复述全文。
3. **可执行、可检查**：条款必须是 AI 能照做、人能验收的表述，避免"保持优雅""合理组织"这类无法判定的措辞。

## 2. Rule 应该包含什么

一条完整的 Rule 通常由六个部分组合而成：

### 适用范围

声明规则的生效边界：

- 语言 / 框架：如"仅适用于 Kotlin 文件"。
- 项目阶段：如"仅适用于发布分支代码"。
- 场景：如"仅适用于新增页面时"。

范围声明让多条规则可以并存而不冲突——两条规则只要适用范围不相交，就不会打架。

### 目标

说明这条规则为什么存在，一句话即可：

```text
目标：统一状态管理写法，降低跨模块阅读成本。
```

目标不是废话。当 Agent 在边界情况下需要自行判断时，目标提供了裁量依据；当团队成员质疑规则合理性时，目标提供了讨论基础。

### 约束

规则的核心条款，用祈使句写明确要求：

```text
约束：
- 页面状态必须通过 Controller 暴露，View 不持有业务状态。
- 一个 Controller 只服务一个页面路由。
```

写约束的技巧：

- 一条约束只说一件事。
- 用"必须 / 禁止 / 优先"表达强度，不要用"建议尽量酌情"。
- 能量化的量化（行数、数量、层级），不能量化的给判定标准。

### 行为要求

约束 Agent 的工作方式而不只是产出物形态的部分：

```text
行为要求：
- 动手前先阅读现有页面的分层实现。
- 新增依赖必须在提交说明中列出并说明理由。
```

这部分是 AI Rules 区别于传统编码规范的关键——传统规范假设执行者是人，AI Rules 必须额外约束执行过程。

### 示例

给出"对的样子"。示例是规则中最有效的部分：一段符合规范的代码片段，胜过十条抽象描述。示例应从团队真实代码中提炼（脱敏后），保证贴近实际场景。

### 禁止事项

明确划出红线：

```text
禁止：
- 禁止在 View 层直接发起网络请求。
- 禁止绕过 Route 注册手动 new 页面。
```

禁止事项的价值在于它消除了解释空间。"不建议""尽量避免"会被模型理解为可选建议，"禁止"才会被当作硬边界。

## 3. Rule 的粒度

粒度是最考验设计能力的维度。用同一个例子（错误处理）对比三种粒度：

### 过大的 Rule

```text
R-XX-代码质量：写出高质量、可维护、健壮的代码，注意异常处理和资源管理。
```

问题：什么都想说，什么都没说清。"高质量"如何检查？Agent 收到后只能按自己的默认理解行事，规则形同虚设。

### 过小的 Rule

```text
R-XX-catch括号：catch 块的左括号单独占一行。
R-XX-log冒号：日志冒号后必须有一个空格。
```

问题：把 Linter 能机械检查的内容搬进规则，浪费上下文，维护成本高，且这类格式问题交给 ktlint / dart analyze 更可靠。

### 合理的 Rule

```text
R-05-异常处理

适用范围：Kotlin 业务代码。

目标：异常不吞、上下文不丢、崩溃有据可查。

约束：
- 禁止空 catch 块；捕获后必须记录日志或向上抛出。
- 网络与 IO 操作必须显式处理失败分支，不允许隐式吞掉。

禁止：
- 禁止 catch (Exception) 后仅打印堆栈继续执行关键流程。

说明：格式类细节以项目 Linter 配置为准，本条只约束行为。
```

### 粒度判断标准

| 判断 | 过大 | 合理 | 过小 |
| --- | --- | --- | --- |
| 可检查性 | 无法判定 | 有明确通过标准 | 可被工具替代 |
| 条款数量 | 笼统一两句 | 3~6 条聚焦同一主题 | 碎片化大量微条款 |
| 维护成本 | 低但无效 | 可控 | 高 |
| 工具重叠度 | 无 | 无重叠 | 与 Linter 重叠 |

经验法则：**一条 Rule 管一个主题，一个主题内 3~6 条可检查的约束，Linter 能查的不写进来。**

## 4. Rule 分类

结合当前项目 `rules/` 的八个分类，说明各类规则的职责边界：

| 分类 | 职责 | 典型主题 |
| --- | --- | --- |
| `android/` | Android 平台约定 | 组件使用、生命周期、资源管理 |
| `kotlin/` | Kotlin 语言约定 | 协程使用、空安全、扩展函数 |
| `java/` | Java 语言约定 | 集合操作、并发处理、流式 API |
| `dart/` | Dart 语言约定 | 异步模式、类型标注、包管理 |
| `flutter/` | Flutter 框架约定 | 分层架构、状态管理、路由注册 |
| `vue/` | Vue 项目约定 | 组件拆分、状态管理、生命周期 |
| `git/` | 版本控制流程 | 提交信息格式、分支命名、合并策略 |
| `review/` | 审查标准 | 检查维度、通过标准、审查输出格式 |

### 归类原则

- 语言层面的归语言目录，框架层面的归框架目录——例如"协程作用域管理"归 `kotlin/`，"页面状态暴露方式"归 `flutter/`。
- 流程性约束独立于技术栈——`git/` 和 `review/` 对 Android、Flutter、Vue 项目通用。
- 一条规则只出现在一个分类下；如果发现需要同时属于两类，通常说明应该拆成两条。

## 5. 通用 Rule 与技术栈 Rule

### 通用 Rule

跨技术栈成立的行为准则，例如：

- 提交信息规范（任何语言的仓库都需要）。
- "先分析后动手"的工作方式要求。
- 安全红线（密钥不硬编码）。

通用 Rule 放在跨栈位置（如 `git/`、`review/`），或在全局层维护。它的特点是**不引用具体语法**，换一种语言依然成立。

### 技术栈 Rule

绑定特定语言或框架的细则，例如 Flutter 的分层约定、Vue 的组件命名。它们必然引用具体技术概念，只在对应项目中生效。

### 判断方法

把规则里的技术名词替换成"某种语言"后仍然成立 → 通用 Rule；替换后语义崩塌 → 技术栈 Rule。

### 不要混放

常见反模式是把通用纪律塞进技术栈文件（如把"提交前跑测试"写在 `flutter/` 里）。后果是其他技术栈的项目看不到这条纪律。发现此类内容应上移到通用层。

## 6. 项目 Rule 与团队 Rule

### 团队 Rule

团队级共识，跨项目复用：

- 存放在团队共享资产库（本项目的 `rules/` 即承担此角色）。
- 变更走团队评审。
- 表述上不包含具体项目的路径、模块名等私有信息。

### 项目 Rule

单个项目的特化约定：

- 存放在项目仓库内。
- 声明"本项目相对团队规范的差异"，而非重复团队已有内容。
- 由项目维护者管理，变更随项目代码评审。

### 关系

```text
团队 Rule（基线）
   ↓ 项目继承
项目 Rule（差异覆盖）
```

项目 Rule 只写"与基线不同的部分"。例如团队规定提交信息用 Conventional Commit，某遗留项目因工具链限制采用旧格式，则该项目只需在项目 Rule 中声明这一处差异。

## 7. Rule 优先级

多层规则叠加时，按以下顺序裁决（高 → 低）：

```text
1. 项目 Rule        本项目显式约定
2. 技术栈 Rule      本栈通用细则
3. 团队通用 Rule    git / review 等流程纪律
4. 全局默认         跨项目基本纪律
```

优先级设计的两条工程要点：

1. **显式声明优于隐式推断**：在规则文件的适用范围声明中写清楚层级关系，让加载方无需猜测。
2. **高层级留白**：上层规则只定"默认值"，为下层留出覆盖空间。例如团队规则说"默认使用 GetX"，Flutter 项目可以声明"本项目使用 Riverpod"完成覆盖，而无需修改团队资产。

## 8. Rule 冲突处理

冲突的三种典型形态与处理方式：

### 形态一：不同层级冲突

例：团队规则要求全量注释，项目规则要求最小注释。

处理：按第 7 节优先级，项目规则胜出。同时在团队规则的该条款旁注明"存在已知的合法覆盖场景"，提示后续项目注意。

### 形态二：同层级冲突

例：`flutter/` 中两条规则分别要求"Controller 保持轻量"与"业务校验逻辑前置到 Controller"。

处理：合并审视两条规则的表述，通常通过补充适用条件消解——"简单校验前置到 Controller，复杂校验下沉到 UseCase 层"。同层级冲突多数源于条款缺少边界条件。

### 形态三：规则与 Prompt 冲突

例：规则说"禁止自动升级依赖版本"，本次 Prompt 说"顺便把依赖升到最新"。

处理：**Prompt 不应突破 Rules 红线**。遇到此类请求，Agent 应指出冲突并由人确认是否属于例外；若确需例外，走规则修订而不是单次口头豁免。

### 冲突预防机制

- 新增规则入库前，检索现有规则中是否有相近主题。
- 定期做一次规则间的交叉审读，重点检查同目录下的条款。
- 冲突一旦发现立即修复，不要让 Agent 自行"猜哪个对"。

## 9. Rule 可维护性

规则资产的生命周期远长于单次任务，设计时就要考虑长期维护：

### 可追溯

- 规则文件纳入 Git 管理，每次修改有提交记录。
- 重要修订在文件内附简短变更说明（何时、为何调整）。

### 可引用

- 编号稳定：`R-01-命名` 这类编号一经分配不再复用，废弃就标记废弃。
- 引用同步：修改规则时检查 Prompt 库、Agent 配置中的引用是否需要联动更新（写作规范的明确要求）。

### 可度量

- 记录每条规则的实际效果：遵循率、相关问题的复发情况。
- 长期无人违反且已成习惯的规则，考虑精简合并；反复被违反的规则，要么改表述，要么补工具检查。

### 可退出

- 废弃规则标记 `[已废弃]` 并保留一段时间，而不是直接删除，给仍在引用它的 Prompt 和 Agent 配置留出迁移窗口。

## 10. Rule 示例分析

以下用两个结构示意说明设计要点。**这些是为讲解结构而写的示意骨架，不是 `rules/` 目录中的现有资产**——具体规则条文以 `rules/` 各目录的实际建设为准。

### 示意一：技术栈 Rule（Flutter 类）

```text
R-03-页面分层

适用范围：Flutter 新增页面。

目标：页面结构一致，新人可预测任何页面的代码位置。

约束：
- 每个页面交付 Controller / Binding / View 三件套。
- View 只负责渲染，不包含业务逻辑。

禁止：
- 禁止在 View 内直接调用网络接口。

示例：（此处附一段符合分层的最小代码骨架）
```

设计点：范围收窄到"新增页面"（存量页面另行处理）；三条约束全部可对照检查；禁止事项堵住最常见的越界行为。

### 示意二：流程 Rule（Git 类）

```text
R-02-提交信息

适用范围：所有仓库的代码提交。

目标：提交历史可读、可追溯、可生成变更日志。

约束：
- 采用 Conventional Commit 格式：类型: 中文描述。
- 一次提交只做一件事。

禁止：
- 禁止 "update"、"fix bug"、"临时" 这类无信息量描述。

说明：格式细节见 docs/00-roadmap/writing-style.md 的 Git Commit 规范。
```

设计点：这是通用 Rule，不含任何技术栈概念；给出了正反两面的判定标准；与既有规范文档建立引用而非复制。

### 从示意到资产的路径

将一条新规则落地为 `rules/` 资产的步骤：

1. 按 `templates/rule-template.md` 建立文件骨架。
2. 填入适用范围、目标、约束、示例、禁止事项。
3. 对照本章第 3 节检查粒度，对照第 8 节检查与既有规则的冲突。
4. 提交评审，合并后同步更新 Prompt / Agent 中的引用。
5. 在后续迭代中观察遵循率，按第 9 节持续维护。

## 总结

- Rule 骨架 = 适用范围 + 目标 + 约束 + 行为要求 + 示例 + 禁止事项，编号格式 `R-<编号>-<简述>`。
- 粒度标准：一条规则管一个主题，3~6 条可检查约束，Linter 能查的不写。
- 八个分类各司其职：语言归语言、框架归框架、流程独立于技术栈。
- 替换技术名词仍成立的是通用 Rule，否则是技术栈 Rule；项目 Rule 只写与团队基线的差异。
- 优先级：项目 > 技术栈 > 团队通用 > 全局；Prompt 不得突破 Rules 红线。
- 冲突三类形态各有处理路径，预防靠入库查重与定期交叉审读。
- 可维护性四要素：可追溯、可引用、可度量、可退出。
