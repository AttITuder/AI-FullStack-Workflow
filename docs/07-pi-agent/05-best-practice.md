# Pi Agent 最佳实践

> Agent 工程化实战经验。围绕 Agent 设计原则、Prompt 设计、Context 管理、Tool 设计、MCP 集成、Extension 扩展、企业内部 Agent 建设与常见错误，沉淀可直接落地的做法。

---

## 为什么需要了解

Pi Agent 是 Agent 框架，产出质量取决于"工程化水平"而非模型单一因素。把 Agent 当作软件来设计：明确原则、管理上下文、设计工具、控制扩展、建设治理，才能让 Agent 稳定产出、可维护、可演进。

## 1. Agent 设计原则

### 目标明确

- 每个 Agent 有清晰的目标与边界。
- 明确"做什么、不做什么、何时停"。

### 小步闭环

- 任务拆小，每步可观察、可验证。
- 循环收敛而非一次性大动作。

### 工具驱动

- 用工具获取真实信息，减少猜测。
- Agent 的能力边界由工具决定。

### 人机分工

- Agent 承担执行，人承担决策与验收。
- 关键动作留人工确认。

### 可观测可回滚

- 记录执行过程与决策依据。
- 每步可回退，失败可排查。

## 2. Prompt 设计

### 结构化委派

- **角色**：说明 Agent 的身份与职责。
- **背景**：项目类型、技术栈、现状。
- **任务**：目标、范围、边界。
- **约束**：规范、禁止事项。
- **输出**：期望产出与验收标准。

### Agent Prompt 与普通 Prompt 差异

- 面向多轮循环，而非单轮回答。
- 明确"如何观察、如何规划、如何反馈"。
- 强调执行闭环，而非一次给出答案。

### 提供示例与工具

- 给"对的样子"：既有代码、期望风格。
- 指明可用工具，帮助 Agent 高效行动。

### 用清单约束

- 委派末尾附验收清单，让 Agent 自检后交付。

## 3. Context 管理

### 足够且不过量

- 只给任务相关的文件与信息。
- 大项目优先用文件引用与检索，避免全量塞入。

### 上下文分层

- 全局规则（团队规范）常驻。
- 任务相关文件按需加载。
- 长会话注意摘要与裁剪。

### 观察优先

- 让 Agent 先读关键文件再动手。
- 判断基于真实代码，不做假设。

### 会话聚焦

- 一次会话聚焦一个目标，避免上下文污染。
- 完成一个目标后开启新会话。

## 4. Tool 设计

### 工具是 Agent 的手脚

- 工具决定 Agent 能做什么、做多好。
- 好工具让 Agent 高效可靠，坏工具引入混乱。

### 设计原则

- **单一职责**：一个工具做一件事，命名清晰。
- **输入明确**：参数定义清楚，校验严格。
- **输出可解析**：返回结构化结果，便于反馈。
- **错误可读**：失败信息明确，Agent 能据实调整。

### 工具分类

| 类型 | 示例 |
| --- | --- |
| 文件类 | 读写、搜索、检索 |
| 命令类 | 构建、测试、部署 |
| 服务类 | 数据库、API、内部系统 |
| 校验类 | 格式、规范、安全检查 |

### 工具治理

- 工具纳入版本库，随项目演进。
- 关键工具先小范围灰度，验证后再放开。
- 权限最小化，敏感操作受限。

## 5. MCP 集成

### 什么是 MCP

MCP（Model Context Protocol）是模型上下文协议：用统一标准接入外部工具与数据源，让 Agent 的能力可插拔扩展。

### 集成原则

- 按需接入，避免工具泛滥。
- 每个 MCP 服务职责单一，命名清晰。
- 接入前验证连通性与输出质量。

### 常见接入场景

- 代码托管（GitHub/Git）、文档、数据库。
- 设计工具、项目管理、内部服务。
- 图、表格、外部 API 数据源。

### 治理要点

- 权限最小化，敏感服务加限制。
- 记录调用行为，保留审计痕迹。
- 失败降级：服务不可用时不阻塞主流程。

## 6. Extension 扩展

### 什么是 Extension

Extension 是 Pi Agent 的能力扩展机制：通过插件方式定制 Agent，支撑"可组合、可扩展、可定制"的定位。

### 设计原则

- **可组合**：扩展小而独立，可自由搭配。
- **可复用**：跨项目沉淀，避免重复建设。
- **可维护**：版本管理、依赖清晰、文档齐全。

### 扩展场景

- 团队专属规则与 Prompt 封装。
- 内部系统接入与自定义工作流。
- 领域专用能力（UI、测试、审查）。

### 治理要点

- 扩展纳入版本库，随项目演进。
- 先小范围试点，验证稳定后推广。
- 记录扩展行为，便于审计与排障。

## 7. 企业内部 Agent 建设

### 建设路径

```text
试点 → 沉淀 → 推广 → 治理 → 演进
```

1. **试点**：选一个高价值场景验证。
2. **沉淀**：把工具、规则、工作流固化为资产。
3. **推广**：统一配置，培训团队。
4. **治理**：权限、审计、成本控制。
5. **演进**：定期复盘，持续优化。

### 治理体系

- **权限**：最小权限，敏感操作受限。
- **审计**：记录 Agent 执行行为，可追溯。
- **成本**：按任务路由模型，控制 Token 消耗。
- **规范**：产出符合团队 Rules，统一风格。

### 团队推广

- 试点项目验证效果，用数据说服团队。
- 统一配置写入 README，新成员一键接入。
- 分享成功案例，沉淀最佳实践文档。
- 用完成率、返工率、成本指标评估效果。

## 8. 常见错误

### 错误一：目标模糊

让 Agent 做"说不清楚"的任务，产出失控。

**修正**：明确目标、边界与验收标准。

### 错误二：不观察直接干

不给上下文，让 Agent 凭空猜测。

**修正**：观察优先，先读代码再规划。

### 错误三：一次塞太多

一个循环做太多事，质量失控难回滚。

**修正**：小步闭环，逐步验证。

### 错误四：忽略反馈

Agent 做完不管结果，错误一路带过。

**修正**：反馈驱动，失败回环修正。

### 错误五：工具一刀切

所有任务一套工具，或工具过多难管理。

**修正**：按任务设计工具，单一职责、治理规范。

### 错误六：权限过大

Agent 能改一切，出问题难挽回。

**修正**：最小权限，敏感操作人工确认。

### 错误七：无审计无沉淀

Agent 行为不可追踪，经验不留存。

**修正**：记录审计，沉淀规则与工具。

### 错误八：跳过验收

Agent 产出直接合入，绕过质量防线。

**修正**：多级验证，关键决策人工把关。

## 总结

- Agent 设计原则：目标明确、小步闭环、工具驱动、人机分工、可观测可回滚。
- Prompt 面向循环设计，强调观察、规划、反馈。
- Context 足够且不过量，观察优先，会话聚焦。
- Tool 是 Agent 的手脚，单一职责、输入明确、输出可解析、错误可读。
- MCP 用标准协议接入外部工具，按需接入、权限最小化。
- Extension 支撑可组合、可复用、可维护的定制扩展。
- 企业建设走"试点 → 沉淀 → 推广 → 治理 → 演进"路径。
- 避开常见错误，用工程手段保证 Agent 产出质量与可控性。
