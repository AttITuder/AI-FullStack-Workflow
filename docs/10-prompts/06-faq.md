# Prompt FAQ

> 常见问题速查。按概念、编写、使用、流程、资产管理五类组织。新问题在团队内被解答后，应回填到本文对应分类。

---

## 概念与定位

## Q1: Prompt 和 Rules 到底怎么区分？

### A

一句话：**Prompt 管一次任务，Rules 管长期行为**。本次任务的目标、上下文、输出要求写进 Prompt；对所有任务都成立的编码规范、禁止事项放进 Rules。判断技巧：这条内容换个任务还成立吗？成立就下沉到 Rules，Prompt 里引用规则编号即可。

## Q2: Prompt 和 MCP 有什么关系？

### A

分工不同。Prompt 描述任务和目标（"修复登录页崩溃并通过真机验证"），MCP 提供达成目标的工具通道（ADB 安装 APK、拉取日志）。写 Prompt 时可以假设工具可用，不必描述工具细节；工具使用的纪律由 Rules 约束。

## Q3: Prompt 和 Agent 是什么关系？

### A

Agent 是 Prompt 的宿主与放大器。Agent 的系统提示词承担角色设定和通用约束（长期不变），用户的任务 Prompt 只需交代具体委派内容。当某个任务 Prompt 高频重复手写时，就该考虑固化进 Agent 配置。

## Q4: Context 和 Prompt 是一回事吗？

### A

不是。Context 是模型可见的全部信息（代码库、会话历史、Rules、Prompt 本身），Prompt 只是其中人主动构造的部分。实用推论有两条：Prompt 要精炼，冗余内容挤占有用信息的注意力；高阶用法是在 Prompt 里指示 AI 自己去读相关文件，而不是全量粘贴代码。

## Q5: 有了好的模型，还需要花功夫写 Prompt 吗？

### A

需要。模型能力决定理解上限，但意图不清的输入依然导致方向性错误——垃圾进垃圾出。模型越强，对"把需求说清楚"的要求不是更低而是更高：它会严格执行你说的话，包括你没说清而它自由发挥的部分。

## Q6: Prompt 工程是不是就是背模板？

### A

不是。模板是形，方法是神。核心是八要素思维（目标、现状、约束、输出、验收等）和模式匹配（什么失败模式用什么策略应对）。换一个全新场景，模板可能都不适用，但思维方式直接迁移。

## Q7: 为什么本项目把 prompts/ 和 docs/10-prompts/ 分开？

### A

职责分离。`prompts/` 存放可直接复制使用的 Prompt 资产（单一事实源），`docs/10-prompts/` 讲解方法论与流程知识。文档可以引用资产做案例分析，但不复制正文，避免两处维护同一份内容造成版本漂移。

## Q8: prompts/ 目录为什么按技术栈和场景两个维度划分？

### A

覆盖两类复用诉求。"生成 Flutter 页面"只在 Flutter 项目有用，归技术栈维度（flutter/）；"代码审查"跨技术栈通用，归场景维度（review/）。归属判断：换一个技术栈这条 Prompt 还成立吗？

## 编写方法

## Q9: 一个 Prompt 必须包含全部八个要素吗？

### A

不必。八要素是完备性检查清单，按任务复杂度裁剪。改个命名两三句话足够；新功能开发至少要有 Goal、Task、Constraints、Output、Validation 五项；Role 在 Agent 场景由系统提示词承担。关键是缺失项是有意识省略而非无意识遗漏。

## Q10: Prompt 写多长合适？

### A

以信息完备为界，不以字数为界。删三类内容：重复的信息、模型常识能补的信息、与任务无关的背景。剩下的就是合适长度。臃肿的 Prompt 不仅浪费 Token，还会稀释关键约束的权重。

## Q11: 角色设定要写得多详细？

### A

一句专业角色名通常足够："你是一名资深 Flutter 工程师"。两个注意点：角色必须与任务匹配；不要堆砌夸张头衔，没有信息量。Agent 场景下角色已由 Agent 配置承担，用户 Prompt 无需重复。

## Q12: 占位符应该用什么格式？

### A

项目统一使用全角括号：【页面名称】【接口地址】。占位符内写名词性描述而不是示例值，同一 Prompt 中同一概念保持同名，使用说明中交代替换方法。

## Q13: 怎么写好约束部分？

### A

四个维度排查：技术约束（选型限制）、项目约束（架构约定）、文件约束（允许改动的范围）、风格约束。通用约束引用 Rules 不复述；禁止事项单独成段列出，"不要做 X"比含蓄的表述有效得多。

## Q14: 验收清单怎么写才不空洞？

### A

最好的来源是真实踩过的坑。每条验收项背后应有一个它防住的失败案例："路由注册正确"是因为 AI 生成的页面曾漏注册路由。空话式的"代码质量良好"无法核对，等于没写。

## Q15: Goal 和 Task 有区别吗？

### A

Task 是动作，Goal 是结果。"为登录页添加表单校验"是 Task；"用户提交前能收到明确的字段错误提示，减少无效请求"是 Goal。只写 Task 时 AI 机械完成动作，边界情况下不会向目的对齐；写出 Goal 后它会主动校准方案。

## Q16: 该贴代码还是让 AI 自己去读？

### A

优先让 AI 读。指示"先阅读 modules/login/ 下现有页面的分层实现"，Agent 用检索能力按需加载最新代码；粘贴的内容既占上下文又可能已过期。只有材料不在仓库里时（设计稿、外部报错日志）才需要粘贴，且要说明用途。

## 使用问题

## Q17: AI 生成的代码风格总跟项目不一致怎么办？

### A

这是默认风格漂移，最有效的对策是 Context Prompt：动手前明确指示"先阅读 modules/ 下现有同类模块的实现，遵循相同结构"。配合 Rules 中的编码规范长期生效，漂移问题基本消除。

## Q18: AI 执行到一半开始做计划外的事怎么办？

### A

两个手段预防：Constraint Prompt 锁定允许修改的目录范围；禁止事项单独列出。事后补救则显式叫停并声明"只保留 X 相关改动，其余撤销"。反复出现说明该任务的约束模板需要补充。

## Q19: 长对话进行到后期质量明显下降怎么办？

### A

上下文污染所致。对策是会话卫生：一个功能一个主会话；阶段完成即归档不再反复修改；开新会话用接力 Prompt 恢复认知（粘贴上一阶段产出摘要 + 本轮目标）；定期让 AI 复述当前整体进度以校准双方认知。

## Q20: 多轮迭代时需求范围越滚越大怎么办？

### A

每轮开头显式声明增量："基于上一步的结果继续，本轮只做 X，其他部分保持不动。"这一句是对抗范围蔓延最有效的单句。完成后要求 AI 简述本轮改动点，便于核对没有夹带。

## Q21: AI 说完成了但实际没完成怎么办？

### A

根因是没有客观的完成定义。对策是 Validation 先行：Prompt 末尾附验收清单并要求 AI 自检后随产出附上检查结果；人工最终验收用同一份清单逐项核对。"完成"由清单定义，不由 AI 宣布。

## Q22: 同样的 Prompt 有时好用有时不好用怎么办？

### A

先检查输入是否真的相同——多数波动源于隐含条件变化（仓库状态不同、会话历史不同）。若排除后仍不稳定，把任务从"一步到位"改为 Step-by-Step：先出方案确认再执行，用人工关卡吸收不确定性。

## Q23: AI 自由发挥改了不该改的公共文件怎么办？

### A

事前在 Constraints 中锁定文件范围："只允许修改 lib/modules/login/ 目录"。若已发生，通过变更清单核对出越界文件并要求还原；这类事故出现两次以上，就把对应禁令写入 Rules 长期生效。

## Q24: 怎么让 AI 输出能直接被脚本处理的格式？

### A

Output Format Prompt 明确规定结构与字段："以 JSON 格式输出，每个问题包含 file、line、severity、description 四个字段"。给一个最小示例比形容词描述可靠；产出后先用一条数据验证格式再批量执行。

## 流程协作

## Q25: 小任务也要走完整的六环节流程吗？

### A

不用。环节可合并省略，但两个关卡不建议跳过：方案确认（大中任务）和交付前审查。改一行文案的任务直接 Task Prompt 一轮完成；判断标准是影响面——跨模块改动就必须有方案关卡。

## Q26: 方案设计阶段要不要让 AI 直接写代码？

### A

不要。明确说"先出方案，不要写代码"。方案阶段的价值在于低成本纠偏——方案错了改几行字，代码错了返工整个实现。这也是整个工作流中性价比最高的人工确认点。

## Q27: 测试应该什么时候写？

### A

与实现同环节完成，不要攒到最后。上下文还在时写测试质量最高；攒批补测试往往沦为形式。Prompt 中同时给出覆盖要求与边界提示，AI 列举边界场景的能力通常比人全面。

## Q28: AI 初审能代替人工 Code Review 吗？

### A

不能替代，但能大幅提效。合理分工：AI 处理机械性检查（规范符合性、命名、明显 Bug、安全模式），人聚焦架构合理性与业务正确性。审查 Prompt 用固定维度防止漏检，并要求"无问题的维度明确说明已检查通过"。

## Q29: 审查发现的问题总是反复出现怎么办？

### A

启动问题上升机制：同类问题第二次在 Prompt 层补救时，固化为 Rules 条目长期生效，之后各 Prompt 引用规则即可。这是 Prompt 层与 Rules 层分工在维护期的体现，也是规则体系持续生长的主要路径。

## 资产管理

## Q30: 什么样的 Prompt 值得沉淀为资产？

### A

两个信号满足其一即沉淀：复用信号（同类任务手写过第二次）、质量信号（产出经验证效果好）。反例是一次性的临时探索——库里只放实测通过的资产，这是整个库信用的基础。

## Q31: 新 Prompt 入库前要做哪些事？

### A

三步：按标准四要素结构成文（适用场景 / 使用说明 / 期望输出 / 验收清单）；在真实项目中完整跑一遍并对照验收清单核对，不达标就改 Prompt 重测；放置到正确的目录并在该目录 README 的表格中登记。

## Q32: Prompt 资产的版本怎么管理？

### A

走 Git，不在文件名或文件内维护版本信息。变更提交 commit 说明动机，重要调整走 PR 让团队 Review，历史回溯靠 git log。文件名保持稳定的任务动作命名（generate_page.md），v2/final 之类的标记属于反模式。

## Q33: 过时的 Prompt 怎么处理？

### A

明确处理而非原地腐烂：技术栈演进导致失效的删除或归档；被 Agent 配置取代的标注去向；所属目录 README 的规划清单同步更新。判据是"新人浏览目录时会不会误用过期内容"。

## Q34: Prompt 资产里可以放真实的接口地址和密钥吗？

### A

不可以。资产会被大量复制传播，入库前必须脱敏：密钥、密码、内网地址一律换成占位符【接口地址】；涉及外部服务的在使用说明中提示数据安全要求。安全红线没有例外。
