# Prompt Patterns

> 本章节核心方法文章。Prompt Pattern 是经过验证的"任务形态 → 提示策略"的固定搭配。本文讲解 16 种模式各自的适用场景与预期效果，帮你建立"遇到什么场景用什么模式"的条件反射。

---

## 为什么需要了解

结构（八要素）解决"写完整"，模式（Pattern）解决"写对路"。同样是结构完整的 Prompt，用错了模式依然低效——比如让 Agent 自由发挥地做重构，或者用一段式指令驱动多步骤任务。每种 Pattern 背后是对一类任务失败模式的针对性设计。

使用本文的方式：先看场景描述，判断是否匹配你手头的任务，再采用对应的提示策略。示例均为骨架示意，完整的可复用 Prompt 以 `prompts/` 目录的实际资产为准。

## 基础模式（一至六）

前六种是构成一切 Prompt 的基础积木，对应八要素的单项强化。

## 1. Role Prompt

### 场景

任务需要特定专业视角：架构评审、安全审查、新人视角检查文档可读性。或模型默认身份与任务不匹配、输出风格不对味。

### 策略

在 Prompt 开头设定专业角色，必要时补充角色的关注倾向：

```text
你是一名资深 Flutter 工程师，重点关注状态管理的合理性与分层清晰度。
```

### 预期效果

输出自动带上该角色的专业框架与术语体系；多个角色视角可以分次获得多维意见。注意：Agent 场景下角色已由系统提示词承担，Role Prompt 更多用于临时切换视角。

## 2. Task Prompt

### 场景

目标明确的单一动作任务：改命名、加字段、生成一个函数。日常最高频的模式。

### 策略

动词开头 + 明确对象 + 最小必要约束：

```text
把 UserService 里的 getUserById 改为返回空对象而不是抛异常，
同步更新调用方处理逻辑。
```

### 预期效果

快速完成小改动，对话成本低。判断标准：如果你发现自己写了三句话还没说清，说明任务其实不是简单任务，应升级为其他模式。

## 3. Context Prompt

### 场景

任务的正确性高度依赖项目现状：新代码必须融入既有结构、修复必须理解历史设计。

### 策略

显式指示 AI 先获取上下文再动手：

```text
动手前先阅读 modules/order/ 的现有实现与 services/api.dart 的接口封装，
新代码遵循同样的组织方式。
```

### 预期效果

产出从"通用最佳实践风格"变为"贴合本项目风格"。这是对抗 AI 默认风格漂移最有效的单一手段。

## 4. Step-by-Step Prompt

### 场景

复杂任务直接执行容易失控：多文件改造、方案不确定的功能开发。

### 策略

要求 AI 先规划再执行，或按编号步骤推进：

```text
不要直接写代码。先分析现有实现，给出改造方案的分步计划，
每步标注影响范围与验证方式，等我确认后再开始第一步。
```

### 预期效果

把不可控的一次性大产出变成可控的多轮协作；人在关键节点有确认机会。这是大型任务的首选模式，也是 `04-workflow.md` 中分阶段工作流的基础。

## 5. Constraint Prompt

### 场景

任务处于强约束环境：不能引入依赖、只能改指定目录、必须兼容旧接口。

### 策略

约束集中成段，禁止事项独立列出：

```text
约束：
- 只允许修改 lib/modules/cart/ 目录
- 不引入新的第三方依赖
禁止：
- 不要修改路由注册以外的公共文件
```

### 预期效果

AI 的自由发挥被限制在安全范围内，"顺手优化"造成的意外波及显著减少。与 Rules 配合时，通用约束引用规则编号即可。

## 6. Output Format Prompt

### 场景

产出物要被程序处理或进入固定流程：生成配置文件、输出结构化审查意见、产出符合目录约定的代码。

### 策略

明确交付物的结构与格式：

```text
以 JSON 格式输出问题清单，每个问题包含：
file、line、severity、description 四个字段。
```

### 预期效果

产出可直接进入下一环节（脚本解析、清单核对），消除格式返工。代码类任务的等价形式是规定目录结构（参考 `prompts/flutter/generate_page.md` 的期望输出结构）。

## 任务类型模式（七至十三）

以下七种模式对应 `prompts/` 场景维度的典型分类，每种都是"基础模式的组合应用"。

## 7. Review Prompt

### 场景

PR 审查、AI 初审、提交前自查。

### 策略

设定审查者角色 + 固定检查维度 + 结构化输出：

```text
作为代码审查者，从规范、安全、性能、逻辑四个维度审查以下变更，
每个维度列出具体问题与严重级别，没有问题的维度明确说明已检查通过。
```

配合 `rules/review/` 使用效果更佳——规则定义通过标准，Prompt 定义本次审查的范围与输出格式。

### 预期效果

审查从"凭感觉扫一眼"变成维度化清单作业，漏检率下降，意见可直接转化为修复任务。

## 8. Debug Prompt

### 场景

崩溃排查、构建失败、行为异常。

### 策略

提供现象材料 + 要求根因先行 + 禁止盲改：

```text
以下是崩溃日志【粘贴日志】。
先定位根因并说明分析过程，给出修复思路，
确认后再给出最小化修复代码。
```

### 预期效果

避免"猜着改"的循环消耗。要求先给根因再给方案，人可以在方案环节纠偏，成本远低于在错误代码上反复拉扯。

## 9. Refactor Prompt

### 场景

结构优化、消除重复、统一命名。

### 策略

强调行为不变 + 范围限定 + 小步推进：

```text
重构 modules/search/ 模块：
- 目标：消除重复的请求封装逻辑
- 约束：外部行为完全不变，只改内部结构
- 方式：小步进行，每步说明改了什么、如何验证行为未变
```

### 预期效果

重构最大的风险是"顺便改了行为"。该模式通过三条防线（行为不变声明、范围锁定、步进验证）控制风险，配合测试基线使用。

## 10. Test Prompt

### 场景

为新代码补测试、提高覆盖率、生成边界用例。

### 策略

指明被测对象 + 覆盖要求 + 边界提示：

```text
为 CartService.calculateTotal 编写单元测试：
- 覆盖正常流程、空购物车、含折扣商品三类场景
- 特别注意金额精度与四舍五入的边界情况
- 测试文件放在 test/ 对应目录，遵循现有测试的写法
```

### 预期效果

测试从"覆盖主干路径"升级为"主干 + 边界"，且风格与既有测试一致。让 AI 列边界场景往往比人想得更全。

## 11. Architecture Prompt

### 场景

新模块的分层设计、技术选型评估、架构现状分析。对应 `prompts/architecture/` 的规划方向（Clean Architecture、分层设计、选型评估）。

### 策略

提供现状信息 + 要求多方案对比 + 明确决策依据：

```text
分析当前项目的网络层实现，评估是否需要引入仓库层。
给出两个方案的对比：维持现状 / 引入 Repository 层。
对比维度：改动成本、可维护性、对现有调用方的影响。
先出分析结论再谈实施。
```

### 预期效果

架构讨论从发散聊天变成结构化对比，产出可以直接进入团队评审。关键技巧是**限定决策维度**，否则对比容易失焦。

## 12. UI Prompt

### 场景

页面实现、样式还原、组件抽取。对应 `prompts/ui/` 分类。

### 策略

视觉信息源 + 还原优先级 + 适配要求：

```text
按 Figma 设计稿实现个人中心页：
- 设计稿：【链接/截图】
- 优先保证布局结构与间距还原
- 需适配深色模式，颜色使用主题中的语义色而非硬编码
```

### 预期效果

UI 产出的主要矛盾是"像不像设计稿"与"是否符合工程约定"。该模式把两者都变成显式要求，减少"功能对了但视觉走样"的返工。

## 13. Product Prompt

### 场景

需求理解辅助、需求拆解、验收标准制定。对应 `prompts/product/` 分类。

### 策略

输入原始需求 + 要求结构化拆解 + 输出工程视角产物：

```text
以下是产品需求原文【粘贴需求】。
请拆解为开发任务清单，每个任务包含：涉及模块、依赖关系、
预估复杂度、建议的验收标准。
标注你认为需求中模糊、需要与产品确认的点。
```

### 预期效果

原始需求转化为可执行的任务分解，同时暴露需求中的歧义点。"标注模糊点"这一句尤其有价值——它在开发前拦截了大量的返工。

## 组合模式（十四至十六）

最后三种是多阶段、大体量任务的高级模式。

## 14. Multi-step Agent Prompt

### 场景

委派给 Agent 的端到端任务：从需求到验证的完整闭环，中间包含多个工具调用。

### 策略

目标 + 关卡式确认 + 自主区间授权：

```text
完成登录功能的开发与验证：
1. 先读取现有页面结构，输出实施方案待我确认
2. 确认后自主完成编码、构建、真机安装验证
3. 全部通过后输出变更摘要，等待我的 Review
除第 2 步外，每个阶段结束暂停等待确认。
```

### 预期效果

在"人控关键决策"与"AI 自主执行"之间取得平衡。关卡设置的原则：方案确认和最终验收必须有人参与，机械性中间步骤放行给 Agent。

## 15. Repository Analysis Prompt

### 场景

接手陌生代码库、大规模改造前的摸底、技术债盘点。

### 策略

限定分析范围 + 规定产出框架 + 只读不写：

```text
分析 lib/ 目录的整体结构：
1. 输出模块划分与各模块职责
2. 标注层间依赖关系与疑似越界的调用
3. 列出你观察到的技术债风险点
本阶段只读不改，输出分析报告。
```

### 预期效果

快速建立对代码库的结构化认知，产出可作为后续改造的地图。"只读不改"的声明避免了分析过程中夹带修改。

## 16. Incremental Modification Prompt

### 场景

长会话中的持续迭代：同一个功能多轮调整、大任务分多步推进。

### 策略

锚定基线 + 显式增量 + 会话卫生：

```text
基于上一步的结果继续：
本轮只做 X，其他部分保持不动。
完成后简要说明本轮改动点。
```

### 长会话配套纪律

- 每轮聚焦一个改动点，说清"本轮做什么、什么不动"。
- 完成一个阶段后开新会话，携带上一阶段的产出摘要，避免上下文污染。
- 定期要求 AI 复述当前整体状态，校准双方认知。

### 预期效果

长任务不再随轮次增加而质量衰减。"本轮只做 X"一句是对抗范围蔓延最有效的单句。

## 模式选择速查

| 你的场景 | 推荐模式 |
| --- | --- |
| 快速小改动 | Task Prompt |
| 产出必须贴合项目现状 | Context Prompt |
| 大任务没把握 | Step-by-Step Prompt |
| 强约束环境 | Constraint Prompt |
| 产出进流程 / 被程序消费 | Output Format Prompt |
| PR 审查 / 自查 | Review Prompt |
| 排查崩溃 / 构建失败 | Debug Prompt |
| 结构优化 | Refactor Prompt |
| 补测试 | Test Prompt |
| 分层 / 选型讨论 | Architecture Prompt |
| 页面还原 | UI Prompt |
| 需求拆解 | Product Prompt |
| 端到端委派 Agent | Multi-step Agent Prompt |
| 陌生库摸底 | Repository Analysis Prompt |
| 多轮迭代 | Incremental Modification Prompt |

实际使用中这些模式几乎总是组合出现——一个成熟的开发任务 Prompt 往往是 Context + Step-by-Step + Constraint 的复合体。模式是视角不是格子，掌握"针对什么失败模式、采取什么策略"的思维才是根本。

## 本章总结

- 基础六模式强化单项要素：Role、Task、Context、Step-by-Step、Constraint、Output Format。
- 七种任务模式对应 prompts/ 场景分类：Review、Debug、Refactor、Test、Architecture、UI、Product。
- 三种组合模式应对复杂形态：Multi-step Agent、Repository Analysis、Incremental Modification。
- 每种模式的设计都针对一类失败模式：风格漂移用 Context、盲改用 Debug 的根因先行、范围蔓延用 Incremental 的单轮聚焦。
- 高频手写的 Prompt 应沉淀为 `prompts/` 资产或升级为 Agent 配置。
