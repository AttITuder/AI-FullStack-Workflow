# Prompt 结构设计

> Prompt 的基础方法论。掌握八要素结构，让任何任务都能被清晰表达——目标清晰、Context 足够、约束明确、输出明确、验证标准明确。

---

## 为什么需要了解

同一个任务，"帮我写个登录页"和一份结构完整的 Prompt，产出质量天差地别。差别不在文笔，而在信息完备度。本文给出一套 Prompt 结构设计方法：八个要素、各自的写法、以及如何按任务复杂度取舍。

## 1. 一个好的 Prompt 应该包含什么

一个结构完整的 Prompt 由八个要素组成：

```text
Role        角色设定    AI 以什么身份工作
Context     上下文      项目背景与现状
Goal        目标        最终要达成什么
Task        任务        具体执行什么动作
Constraints 约束        必须遵守哪些限制
Input       输入        可以使用哪些材料
Output      输出        交付物长什么样
Validation  验证        怎么判断做完了、做对了
```

不是每个 Prompt 都要包含全部八项（见第 10 节），但**缺失的每一项都要有意识地省略，而不是无意识地遗漏**。判断方法：把你的 Prompt 交给另一个工程师，如果他能不看代码就明白任务并知道怎么验收，结构就是完整的。

## 2. Role

Role 告诉模型以什么身份和专业水准工作。

### 作用

- **激活对应能力域**：模型在不同角色下的知识调用侧重不同。"资深 Flutter 工程师"会触发框架最佳实践相关的表达。
- **锚定输出风格**：角色隐含了专业术语水平、代码风格倾向。

### 写法

```text
你是一名资深 Flutter 工程师。
```

一句话即可。两个注意点：

1. **角色要与任务匹配**：让架构评审的 Prompt 扮演"初级开发者"是自相矛盾的设定。
2. **不要堆砌夸张头衔**："世界顶级天才专家"没有信息量，专业角色名就够了。

在 Agent 工作流中，Role 通常由 Agent 的系统提示词承担（见 `agents/` 各 Agent 配置），用户 Prompt 无需重复声明——这是 Role 从任务级输入上升为长期配置的典型场景。

## 3. Context

Context 提供理解任务所需的背景信息。

### 该放什么

- **项目技术栈**：Flutter 3.24 + GetX + Dio + Clean Architecture。
- **相关现状**：这个模块已有的实现方式、要对接的既有接口。
- **前置约定**：团队已确定的设计决策（如状态管理选型）。

### 不该放什么

- 模型常识能覆盖的内容（什么是 MVVM）。
- 与本次任务无关的项目历史。
- 大段贴入的无关代码（应该让 AI 自己去读，见下）。

### 关键技巧：指示获取而非全量粘贴

```text
动手前先阅读 modules/login/ 下现有页面的分层实现，
遵循同样的结构。
```

这比把三个文件的代码全部贴进 Prompt 更高效——Agent 有检索文件的能力，让它按需加载，上下文更精准也更省 Token。

## 4. Goal

Goal 说明任务的最终目的，是整个 Prompt 的方向锚点。

### Task 与 Goal 的区别

Task 是动作，Goal 是结果：

```text
Task:  为登录页添加表单校验
Goal:  用户提交前能收到明确的字段错误提示，减少无效请求打到服务端
```

只写 Task 时，AI 可能机械完成动作但不解决真问题；写出 Goal 后，AI 在边界情况下会向目的对齐——比如发现接口层已有校验时主动调整方案。

### 写法要点

- 一句话说清"做成之后什么样"。
- 能量化的量化："首屏加载时间不超过 2 秒"优于"性能要好"。

## 5. Task

Task 是要求 AI 执行的具体动作，Prompt 的核心段落。

### 写法要点

1. **动词开头、动作明确**："生成""修复""重构""审查"，避免"看看""处理一下"。
2. **复杂任务拆步骤编号**：

```text
请完成以下工作：
1. 分析 modules/cart/ 的现有分层结构
2. 新增优惠券模块，遵循相同分层
3. 补充单元测试覆盖核心逻辑
```

3. **一个 Task 只说一件事**：需要多件事时编号列出，或拆成多次委派（大任务拆分详见 `05-best-practice.md`）。

## 6. Constraints

Constraints 划定执行的边界，是防止 AI 自由发挥的关键段落。按四个维度组织：

| 维度 | 内容 | 示例 |
| --- | --- | --- |
| 技术约束 | 语言 / 框架 / 库的选型限制 | 使用 GetX，不引入新状态管理库 |
| 项目约束 | 项目既定的架构与流程约定 | 遵循 R-03 页面分层规则 |
| 文件约束 | 允许改动的范围 | 只修改 lib/modules/login/ 目录 |
| 风格约束 | 命名 / 注释 / 格式要求 | 遵循项目 Dart 风格规范 |

### 与 Rules 的配合

项目级约束不需要逐条复述——Rules 已经长期生效的部分用引用代替：

```text
约束：
- 遵循 rules/flutter/ 全部规范
- 本次只允许修改 login 模块目录
```

第一行引用了整组长期约束，第二行才是本任务特有的边界。**Prompt 中只写任务特有的约束，通用约束靠 Rules 承载。**

### 禁止事项单独列出

"不要做 X"比"要做 Y 但避免 X"更有效。禁止事项建议独立成段：

```text
禁止：
- 不要引入新的第三方依赖
- 不要修改路由注册以外的公共文件
```

## 7. Input

Input 声明 AI 可以使用哪些材料完成任务。

### 常见的 Input 类型

- **文件路径**："参考 services/api.dart 中现有的网络封装"。
- **设计稿**："按 Figma 稿【链接/截图】实现页面"。
- **需求文档**："需求描述如下：……"
- **报错信息**："崩溃日志如下：……"

### 要点

- 明确材料的**位置和用途**："以下是报错日志，用于定位崩溃原因"，而不是直接甩一段日志不说明。
- 材料多时标注优先级："先看崩溃堆栈，再看业务日志"。
- 引用路径优于粘贴内容——路径让 Agent 读到最新代码，粘贴的内容可能已过期。

## 8. Output

Output 规定交付物的形态，消除"完成了但不是我要的"。

### 该规定的维度

- **交付物类型**：完整可运行代码 / 修改方案 / 审查意见清单。
- **文件组织**：输出到哪些路径、按什么结构组织。
- **格式要求**：是否需要说明文档、变更列表。

### 示例

```text
输出要求：
1. 输出完整可运行的代码
2. 按以下目录结构组织：
   - modules/login/controller/
   - modules/login/binding/
   - modules/login/view/
   - modules/login/model/
3. 附变更文件清单
```

对照 `prompts/flutter/generate_page.md` 可以看到，它专门用"期望输出结构"一节给出了目标目录树——这让生成结果的验收变得一目了然。

## 9. Validation

Validation 规定怎么判断任务完成且正确，是八要素中最容易被忽略的一项。

### 为什么重要

没有验证标准的任务，"完成"由 AI 自行宣布；有验证标准的任务，"完成"可以被客观检验。这也是把人从逐行审查中解放出来的前提。

### 写法

```text
验收清单：
- [ ] 代码可编译运行
- [ ] 遵循 Clean Architecture 分层
- [ ] 网络层走统一封装
- [ ] 状态管理使用 GetX
- [ ] 路由注册正确
```

（引自 `prompts/flutter/generate_page.md`）

两种粒度：

1. **AI 自检型**：要求 AI 交付前对照清单自查，随产出附上检查结果。
2. **人工验收型**：作为 Reviewer 的核对清单，逐项通过才算完成。

工程上推荐两者结合：Prompt 末尾附清单要求 AI 自检，同一份清单用于最终人工验收。

## 10. Prompt 长度与复杂度

结构与长度无关。八要素是完备性检查清单，不是必填表单——**按任务复杂度裁剪**。

### 简单任务

改个命名、修个小 Bug、解释一段代码。两三句话足够：

```text
把 utils/date.dart 里的 formatTime 函数重命名为 formatDateTime，
同步更新所有引用，跑一遍测试确认无回归。
```

隐含了 Task（重命名）、Constraints（同步更新引用）、Validation（测试通过）。硬套八要素反而臃肿。

### 复杂任务

新功能开发、跨模块改造。核心五要素不可少：Goal、Task、Constraints、Output、Validation。Context 按需提供，Role 通常由 Agent 承担。

### 大型任务

一次对话装不下的大改造。策略不是写超长 Prompt，而是**拆分**：

```text
第一阶段 Prompt：分析现状，输出改造方案与分步计划（不写代码）
第二阶段 Prompt：确认方案后，执行第一步
后续阶段：逐步推进，每步带验证
```

大型任务的 Prompt 设计本质是把"一次性指令"变成"分阶段的工作流"，详见 `04-workflow.md`。

### 长度的真正标准

以信息完备为界，不以字数为界。删掉三类内容：重复的信息、模型常识能补全的信息、与任务无关的背景。剩下的就是合适的长度。

## 11. Prompt 中的信息优先级

当 Prompt 篇幅有限或信息庞杂时，按以下优先级取舍：

```text
1. 任务目标与具体动作     （缺了就跑偏）
2. 硬性约束与禁止事项     （缺了就违规）
3. 验收标准               （缺了就没法定义完成）
4. 关键上下文             （缺了就误解现状）
5. 输出格式细节           （缺了可以事后调整）
6. 背景解释与动机说明     （锦上添花）
```

排序逻辑：越靠近"决定 AI 做什么、做到什么程度"的信息优先级越高。实际写作时按此顺序组织段落——最重要的信息放在 Prompt 前部，也符合模型的注意力分布。

另一条实用原则：**冲突时后者胜**。如果 Prompt 里出现了相互矛盾的要求，模型倾向于以后出现的为准——所以修订 Prompt 时应删除旧说法而不是在末尾追加新说法，避免新旧并存造成混乱。

## 12. Prompt 结构模板

本项目的标准 Prompt 资产结构以 `templates/prompt-template.md` 与 `docs/00-roadmap/writing-style.md` 第 6 节为准：

- 每个 Prompt 独立成文。
- 正文包含四部分：**适用场景、使用说明、期望输出、验收清单**。
- Prompt 本体放在围栏代码块内，语言标识用 `text`。
- 占位符统一使用 `【】`，例如 `【页面名称】`。

### 对照实例

`prompts/flutter/generate_page.md` 是该结构的完整落地：

```text
# Flutter 页面生成            ← 标题
> 使用 AI 生成符合……          ← 适用场景（引言）
## Prompt                     ← 正文（text 代码块 + 【】占位符）
## 使用说明                   ← 占位符替换、按项目调整
## 期望输出结构               ← Output 要素的展开
## 验收清单                   ← Validation 要素的展开
```

可以看到，模板的四部分正是八要素中"对外交付最关键的三项"（Output、Validation、使用方式）的固化。**八要素指导你写好每一次 Prompt，模板结构保证沉淀下来的资产质量稳定**——前者是思维框架，后者是资产管理规范。

### 八要素自查法

写完 Prompt 后快速过一遍：

- [ ] Role：需要显式设定吗？（Agent 场景可省）
- [ ] Context：AI 缺了哪些背景会误解任务？
- [ ] Goal：做完之后什么样？
- [ ] Task：动词开头的明确动作？
- [ ] Constraints：技术 / 项目 / 文件 / 风格四个维度过一遍？
- [ ] Input：材料位置和用途说清了吗？
- [ ] Output：交付物形态规定了吗？
- [ ] Validation：有可核对的完成标准吗？

## 本章总结

- 八要素 = Role + Context + Goal + Task + Constraints + Input + Output + Validation，是完备性清单而非必填表单。
- Role 匹配任务即可，Agent 场景由系统提示词承担。
- Context 指示获取优于全量粘贴；Goal 写结果而非动作。
- Constraints 四维度排查，通用约束引用 Rules，禁止事项单独列出。
- Output 规定交付形态，Validation 给出可核对的完成定义——两者是最易缺失的两项。
- 长度按任务复杂度裁剪：简单两三句，复杂的五要素齐全，大型拆阶段。
- 信息优先级：目标动作 > 硬约束 > 验收 > 关键上下文 > 格式 > 背景。
- 资产化遵循模板四部分（适用场景 / 使用说明 / 期望输出 / 验收清单），占位符用 `【】`。
