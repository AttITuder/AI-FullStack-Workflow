# Prompt Workflow

> 本章节核心方法文章。单个 Prompt 写得好只是基础，真正的效率提升来自把 Prompt 组织成覆盖完整研发流程的序列。本文讲解 Prompt 如何驱动从需求分析到交付验证的每个环节。

---

## 为什么需要了解

很多团队对 AI Coding 的使用停留在"遇到问题问一下"，产出不稳定、无法沉淀。原因不是 Prompt 写得不好，而是**没有把 Prompt 当作流程的一环来设计**——每次都是孤立的一次性指令，而不是贯穿研发全流程的意图传递链。

本文给出一条以 Prompt 为驱动的研发工作流：六个环节、每个环节的 Prompt 要点、以及一个完整的功能开发实例。

## 1. Prompt 驱动开发的基本循环

无论任务大小，Prompt 驱动的协作都遵循同一个基本循环：

```text
明确意图
   ↓
构造 Prompt（意图 + 约束 + 验收标准）
   ↓
AI 执行
   ↓
对照验收清单验证
   ↓
通过 → 进入下一环节
   |
不通过 → 补充上下文 / 收紧约束，重新构造 Prompt
```

这个循环有两个不变量：

1. **人在循环内**：每个关键产出都经过人工验证才进入下一环节。
2. **验收先行**：Prompt 里先写清"怎么算完成"，执行后按此核对——而不是看到结果后再争论好不好。

各研发环节本质上是这个循环在不同任务类型上的重复应用。理解了循环，环节就只是换内容。

## 2. 工作流总览

一次典型的功能开发，Prompt 在六个环节中流转：

```text
需求分析 → 方案设计 → 编码实现 → 测试验证 → 代码审查 → 修复迭代
   │           │           │           │           │          │
 Product    Architecture  Task/      Test       Review     Debug/
 Prompt      Prompt      Context    Prompt      Prompt    Refactor
                          Prompt                          Prompt
```

两个原则贯穿全程：

- **前移**：能在需求阶段用 Prompt 澄清的模糊点，不要留到编码时才发现。
- **闭环**：每个环节的产出物是下一环节 Prompt 的 Input——需求拆解喂给方案设计，方案喂给编码，代码喂给测试和审查。

## 3. 环节一：需求分析

### 目标

把产品需求的自然语言描述，转化为结构清晰、歧义暴露的任务清单。

### Prompt 要点

使用 Product Prompt 模式（见 `03-prompt-patterns.md` 第 13 节）：

```text
以下是产品需求原文【粘贴需求】。
请拆解为开发任务清单，每个任务包含：涉及模块、依赖关系、
预估复杂度、建议的验收标准。
标注你认为需求中模糊、需要与产品确认的点。
```

### 关键动作

- **让 AI 标注模糊点**：这是本环节最有价值的一步。AI 以"外部人"视角读需求，发现的歧义往往正是开发中会返工的点。
- **人工确认拆解结果**：任务边界是否合理、依赖顺序是否符合实际，这一步必须人来判断。
- **产出物**：任务清单 + 待确认问题列表。前者直接成为后续环节的输入，后者拿去和产品对齐。

### 环节出口标准

任务清单中的每项都有明确的完成定义；模糊点全部得到澄清或标记为风险。

## 4. 环节二：方案设计

### 目标

为任务清单中的核心任务确定技术方案：分层结构、接口设计、影响范围。

### Prompt 要点

使用 Architecture Prompt 模式：

```text
基于以下任务【粘贴任务描述】，给出实现方案：
- 涉及哪些模块，各自职责是什么
- 新增/修改的文件清单与放置位置
- 对现有调用方的影响
先出方案，不要写代码。
```

### 关键动作

- **要求多方案对比**：有决策空间时限定决策维度（成本、可维护性、影响面），避免发散。
- **方案确认关卡**：这是整个工作流中最重要的人工确认点——方案错了后面全是无效功。
- **产出物**：文件变更清单 + 分层设计说明，作为编码 Prompt 的 Context。

### 环节出口标准

方案经人确认；影响范围明确；新文件的位置符合项目架构约定。

## 5. 环节三：编码实现

### 目标

按已确认的方案生成符合项目规范的代码。

### Prompt 要点

Task / Context / Constraint 三种模式的组合：

```text
按以下方案实现【功能名称】：
【粘贴方案要点或引用上轮讨论】

约束：
- 先阅读 modules/ 下现有同类模块的实现，遵循相同分层
- 遵循 rules/flutter/ 全部规范
- 只修改方案列出的文件

输出完整可运行的代码，附变更文件清单。
```

### 关键动作

- **Context 前置**："先阅读现有模块再动手"一句不可省略，它是对抗 AI 默认风格漂移最有效的手段。
- **大任务分批**：单次对话装不下的实现按模块拆分为多次委派，每次聚焦一个模块（参考第 11 节会话管理）。
- **产出物**：代码 + 变更清单。变更清单同时服务于后续的审查与回归评估。

### 环节出口标准

代码可编译运行；目录结构与方案一致；无越界文件改动。

## 6. 环节四：测试验证

### 目标

为核心逻辑建立自动化验证，并完成真机 / 构建层面的验证。

### Prompt 要点

Test Prompt 模式：

```text
为本次新增的【模块名】编写单元测试：
- 覆盖正常流程与边界场景
- 特别注意【业务上的关键边界】
- 遵循 test/ 下现有测试的写法
```

### 关键动作

- **测试与实现同环节完成**：不要攒到最后补测试——上下文还在时写测试质量最高。
- **构建级验证交给 Agent**："构建 APK 并安装到设备启动"这类动作委派给带 ADB / Gradle MCP 的 Agent 完成（详见 `docs/08-mcp/`），Prompt 只需描述目标状态。
- **产出物**：通过的测试套件 + 验证记录（构建产物、日志结论）。

### 环节出口标准

测试全部通过；目标平台实际运行验证通过。

## 7. 环节五：代码审查

### 目标

在提交前用 AI 完成第一轮结构化审查，人只做最终把关。

### Prompt 要点

Review Prompt 模式：

```text
作为代码审查者，审查以下变更【粘贴 diff 或指定文件】：
- 维度一：规范符合性（对照 rules/flutter/）
- 维度二：逻辑正确性与边界处理
- 维度三：性能隐患
- 维度四：安全问题
每个维度列出具体问题与严重级别；
没有问题的维度明确说明已检查通过。
最后输出一份修复优先级排序的问题清单。
```

### 关键动作

- **维度化检查**：固定四个维度防止漏检；"没有问题也要明说"防止 AI 用沉默蒙混。
- **AI 初审 + 人终审**：AI 处理机械性检查（规范、命名、明显 Bug），人聚焦架构合理性与业务正确性。
- **产出物**：分级问题清单，直接转化为修复任务进入下一环节。

### 环节出口标准

高优先级问题清零；遗留问题有明确记录。

## 8. 环节六：修复与迭代

### 目标

消化审查发现的问题，收敛到可交付状态。

### Prompt 要点

Debug / Refactor 模式按问题类型选用：

```text
针对审查发现的问题逐项修复：
1.【问题描述】→ 修复方式：【思路】
2.【问题描述】→ 修复方式：【思路】
约束：只改问题相关代码，不做额外重构。
每项修复后跑一遍相关测试确认无回归。
```

### 关键动作

- **逐项修复而非一把梭**：多项问题混合修改会让回归定位变得困难。
- **区分修复与重构**：审查中发现的结构性问题如果超出本次范围，记录到技术债清单而不是顺手改掉。
- **产出物**：全部问题关闭 + 回归测试通过。

### 环节出口标准

问题清单清零或降级为已记录的技术债；测试全绿；可以提交。

## 9. 完整示例：登录功能的 Prompt 序列

以 Flutter 登录页开发为例，展示六环节的 Prompt 如何串联（示意骨架，非完整 Prompt 正文）：

**环节一 · 需求分析**

```text
需求原文：用户可以用手机号和密码登录，登录成功进入首页。
请拆解为开发任务并标注需求中的模糊点。
```

→ 产出：任务清单（页面 UI / 表单校验 / 接口对接 / 路由跳转）+ 模糊点（错误提示样式未定义）。

**环节二 · 方案设计**

```text
基于登录页任务，给出实现方案：模块划分、文件清单、
对路由注册的影响。遵循 modules/ 下现有页面的分层方式。先出方案不写代码。
```

→ 人确认方案：login 模块按 controller / binding / view / model 四层组织。

**环节三 · 编码实现**

```text
按已确认方案实现登录页：
- 先阅读 modules/ 下现有页面，遵循同样分层
- 使用 GetX + Dio，网络走统一封装
- 输出 Controller / Binding / View / Model 完整代码
```

→ 产出：完整模块代码。（`prompts/flutter/generate_page.md` 即为此环节的固化资产。）

**环节四 · 测试验证**

```text
为登录逻辑编写单元测试：覆盖成功、密码错误、网络异常三类场景。
完成后构建并安装到设备，验证登录流程可用。
```

**环节五 · 代码审查**

```text
审查 login 模块变更：规范、逻辑、性能、安全四维度，
输出分级问题清单。
```

**环节六 · 修复迭代**

```text
逐项修复审查清单中的高优先级问题，每项修复后跑测试确认无回归。
```

注意观察这条链路的特点：**每个环节的 Prompt 都很短**——因为前一环节的产出已经把大量上下文固化了下来。这就是流程化的价值：单个 Prompt 不需要背负全部信息。

## 10. 与 Agent 的配合：委派词设计

当任务委派给 Agent（如 flutter-agent）时，Prompt 的形态从"详细说明书"变为"目标 + 关卡"的委派词：

```text
完成【功能名称】的开发与验证：
1. 先读取现有模块结构，输出实施方案待我确认
2. 确认后自主完成编码、测试、构建验证
3. 全部通过后输出变更摘要，等待我的 Review
除第 2 步外，每阶段结束暂停等待确认。
```

设计要点：

- **Agent 已携带角色与规范**：系统提示词承担了 Role 和通用 Constraints，委派词只需交代任务特有信息。
- **关卡前置**：方案确认放在自主执行之前，是性价比最高的纠偏点。
- **授权区间明确**："第 2 步自主完成"给了 Agent 连续执行的空间，避免每步都要人推。

## 11. 会话管理策略

长流程跨多个会话时的纪律：

### 会话粒度

- **一个功能一个主会话**：登录页的所有环节在一个会话内推进，保持上下文连续。
- **阶段完成即归档**：某环节产出定稿后，让它成为"既定事实"，后续不再反复修改。
- **新功能开新会话**：避免上一个功能的细节污染下一个任务的上下文。

### 跨会话衔接

新会话开场用一段"接力 Prompt"恢复认知：

```text
背景：【功能名称】已完成方案设计与主体编码，
方案要点如下：【粘贴方案摘要】。
本轮继续完成【剩余任务】。
```

### 上下文卫生

- 定期要求 AI 复述当前整体进度，校准双方认知。
- 发现 AI 引用了早已废弃的旧方案时，显式声明"之前的 X 方案已废弃，以 Y 为准"。

## 12. Prompt 序列模板

把上述流程固化为团队可复用的模板结构：

| 环节 | Prompt 类型 | 必备要素 | 出口标准 |
| --- | --- | --- | --- |
| 需求分析 | Product | 原始需求、拆解格式 | 任务清单 + 模糊点澄清 |
| 方案设计 | Architecture | 任务描述、对比维度 | 方案经人确认 |
| 编码实现 | Task + Context + Constraint | 方案引用、现有代码参照、范围约束 | 可编译、结构合规 |
| 测试验证 | Test | 被测对象、边界场景 | 测试与运行验证通过 |
| 代码审查 | Review | 固定四维度、分级输出 | 高优问题清零 |
| 修复迭代 | Debug / Refactor | 问题清单、逐项约束 | 全部关闭、回归通过 |

使用方式：小任务可以合并环节（如需求分析和方案设计一步完成），但**方案确认和审查两个关卡不建议省略**。

## 13. 常见流程问题与对策

| 现象 | 根因 | 对策 |
| --- | --- | --- |
| 每个环节都在重复解释背景 | 上一环节产出没有固化为下一环节输入 | 让每个环节的产出物可直接粘贴为下个 Prompt 的 Context |
| 编码阶段频繁推翻重来 | 方案确认关卡被跳过 | 强制"先出方案待确认，再写代码" |
| AI 改着改着超出范围 | 缺少文件级约束 | Constraint Prompt 中锁定允许修改的目录 |
| 长会话后期质量下降 | 上下文污染 | 阶段归档 + 接力 Prompt 开新会话 |
| 审查意见反复出现同类问题 | 问题没有反哺 Rules | 把重复出现的问题写入 `rules/`，Prompt 中引用规则编号 |
| 测试总是最后补不上 | 测试与实现割裂 | 测试纳入编码环节的同一委派 |

其中最后一条值得展开：**流程的持续优化靠的是"问题上升"机制**——某个问题在 Prompt 层面反复补救，就把它固化到 Rules 层面长期生效，这正是 `docs/09-rules/02-install.md` 所述规则体系的建设路径。

## 本章总结

- Prompt 驱动开发的基本循环：明确意图 → 构造 Prompt → 执行 → 对照验收清单验证，人在循环内、验收先行。
- 六环节链路：需求分析 → 方案设计 → 编码实现 → 测试验证 → 代码审查 → 修复迭代，前一环节产出是后一环节的输入。
- 两个不可省略的人工关卡：方案确认与最终审查。
- 流程化让单个 Prompt 变短：上下文由环节产出物承载，不必每次从头解释。
- Agent 场景下 Prompt 简化为"目标 + 关卡 + 授权区间"。
- 会话纪律：一功能一会话、阶段归档、接力 Prompt 衔接。
- 流程持续优化靠问题上升：Prompt 层反复补救的问题固化为 Rules。
