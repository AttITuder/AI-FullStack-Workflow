# 01 AI 模型概览

> 目标读者：具有软件开发经验，希望建立 AI 全栈开发能力的开发者。本文建立对 AI 模型的整体认知，不涉及 API、价格与安装。

---

## 为什么需要了解

AI Coding 工具的能力上限，本质上由背后的模型决定。无论你使用 OpenCode、Codex 还是 Claude Code，理解"模型能做什么、不能做什么、各有什么侧重"，才能正确选型、设计工作流、设定合理的预期。本章是全书的"模型认知基座"，后续所有工具章节都会引用这里的概念。

## 基本概念

### 什么是大语言模型（LLM）

大语言模型（Large Language Model，LLM）是一种基于海量文本数据训练的人工智能模型。它通过预测"下一个 Token"的方式学习语言的统计规律，从而能够理解、生成和转换文本。

用工程视角理解它的本质：

- **输入与输出**：接受文本（Token 序列），输出文本。Token 是模型处理文本的最小单位，一个汉字大约对应 1~2 个 Token。
- **概率生成**：模型不是"查库"，而是根据上下文计算下一个 Token 的概率分布，因此同一问题可能给出不同回答。
- **上下文窗口（Context Window）**：模型一次能"看到"的 Token 数量上限，决定了它能同时理解多少代码、多少文档。
- **参数规模**：模型权重中的参数数量，规模越大通常能力越强，但推理成本也越高。

LLM 本身只处理文本。为了让它能"看图片""用工具""写代码文件"，需要叠加额外的能力与协议（详见 `11-vision-and-toolcall.md`）。

## 核心能力

### 能力维度总览

在 AI Coding 场景，评估一个模型主要看六个维度：

| 能力 | 说明 | 典型用途 |
| --- | --- | --- |
| Coding | 代码生成、补全、理解、重构能力 | 核心开发任务 |
| Reasoning | 逻辑推理、数学、复杂问题拆解 | 疑难调试、架构分析 |
| Vision | 图像理解、OCR、UI 识别 | 设计稿转代码、截图排查 |
| Tool Calling | 按需调用外部函数/工具 | 函数调用、MCP 接入 |
| Long Context | 超长上下文处理能力 | 大型代码库理解 |
| MCP 支持 | 连接外部数据与工具的标准协议 | 打通真实开发环境 |

### Coding 能力

- 决定代码生成的质量、语法正确性与风格一致性。
- 强的 Coding 模型能理解项目上下文、遵循技术栈约束、生成可运行代码。

### Reasoning 能力

- 决定模型处理"需要多步思考"任务的能力：算法题、复杂 Bug 定位、架构权衡。
- 推理型模型（如推理系列）在长链条问题上显著优于普通模型。

### Vision 能力

- 决定模型能否理解图像：UI 设计稿、错误截图、手写图表、流程图。
- 是"设计稿转代码"工作流的前提能力。

### Tool Calling 能力

- 决定模型能否在执行任务时调用外部工具（执行命令、读写文件、查询数据库）。
- 是 Agent 化工作流（OpenCode、Codex）的基石。

### Long Context 能力

- 决定模型能否一次性消化大型代码库、多文件上下文或长文档。
- 长上下文不等于高质量，实际能力取决于"长上下文下的注意力保持"。

### MCP 支持

- MCP（Model Context Protocol）让模型通过标准协议访问外部工具与数据源。
- 有 MCP 支持的模型，可以构建更强的 Agent 工作流。

## 模型发展历程

主流模型按发展脉络可分为国际系与国产系：

### 国际系

- **GPT（OpenAI）**：ChatGPT 与 GPT-4 系列确立了"对话式 AI"的范式，后续 Codex 等面向编程场景。
- **Claude（Anthropic）**：强调长上下文、代码与写作质量，在工程场景口碑稳定。
- **Gemini（Google）**：深度整合 Google 生态，多模态能力突出，原生长上下文。

### 国产系

- **DeepSeek（深度求索）**：以高性价比与强推理能力著称，开源模型广受欢迎。
- **Qwen（通义千问，阿里）**：模型矩阵完整，覆盖多尺寸与多模态，开源生态活跃。
- **Kimi（月之暗面）**：以长文本处理见长，面向内容密集型场景。
- **GLM（智谱）**：面向企业级应用的中文模型，生态工具完善。
- **Llama（Meta）**：开源模型的标杆系列，催生大量本地部署与微调生态。

> 模型迭代速度极快，本节只描述各家"稳定的能力特征与定位"，不追逐版本号。具体型号更新见 `02-models/` 各分篇。

## 闭源模型与开源模型区别

### 闭源模型

- 通过 API 提供服务，能力由厂商持续更新。
- 优点：开箱即用、质量稳定、无需运维、安全补丁及时。
- 缺点：数据出境合规需评估、成本随用量增长、定制空间有限。

### 开源模型

- 权重公开，可下载、部署、微调。
- 优点：数据可控、可私有化部署、无 API 成本、可深度定制。
- 缺点：需要 GPU/服务器资源、需要工程维护、模型能力滞后于同代闭源旗舰。

### 选择视角

| 维度 | 闭源 API | 开源自部署 |
| --- | --- | --- |
| 上手成本 | 低 | 高（需部署） |
| 数据控制 | 受厂商政策 | 完全自主 |
| 成本结构 | 按量计费 | 固定硬件成本 |
| 定制能力 | 低 | 高 |
| 适用场景 | 快速交付、个人/中小团队 | 数据敏感、大规模稳态 |

## API 模型与本地模型区别

- **API 模型**：运行在厂商云端，通过网络调用。无需关心硬件，但要考虑延迟、网络、费用与数据安全。
- **本地模型**：运行在自己的机器或内网服务器上。完全自主，但受硬件（显存/内存）限制，通常只能跑较小参数的开源模型。

工程实践中常按"任务复杂度和敏感性"混合使用：敏感数据处理用本地模型，高质量生成用云端 API 模型。

## 企业为什么需要多个模型

单一模型无法在所有维度做到最优，企业级 AI 开发几乎必然走向**多模型协作**：

1. **不同任务用不同模型**：日常编码用平衡型模型，疑难推理用推理型模型，UI 分析用多模态模型。
2. **降低成本**：简单任务用廉价模型，复杂任务才用旗舰模型。
3. **规避单点风险**：避免依赖单一厂商的可用性、政策与价格变动。
4. **合规要求**：不同业务线的数据合规要求不同，需要差异化选型。

多模型协作的落地方式是通过统一接口层（如 OpenRouter、自建网关、MCP）屏蔽模型差异，让上层工作流无感切换模型。

## 企业实践

- **先定任务，再选模型**：不要让"哪个模型最强"主导决策，而要让"哪个任务需要什么能力"主导。
- **建立能力矩阵**：把六维能力与团队任务清单对齐，形成选型依据。
- **抽象模型层**：通过网关或 MCP 屏蔽模型差异，支持按任务路由。
- **保持可替换性**：避免工作流深度绑定单一模型的私有特性。

## 常见问题

**Q1：模型能力与工具能力如何区分？**

模型决定"智力"，工具（OpenCode、Codex 等）决定"执行力"。强模型 + 强工具 + 好工作流 = 最佳产出。

**Q2：开源模型一定不如闭源吗？**

不一定。开源模型在可控性、成本与定制上占优，部分场景（代码补全、简单问答）开源模型已足够。

**Q3：上下文越长越好吗？**

不是。长上下文增加成本与延迟，且超过一定长度后模型注意力会下降。关键是"够用即可，配合检索优化"。

## 本章总结

- LLM 本质是文本概率生成模型，能力由参数、训练数据与上下文窗口共同决定。
- 评估模型看六维能力：Coding、Reasoning、Vision、Tool Calling、Long Context、MCP 支持。
- 闭源与开源、API 与本地各有适用场景，企业级实践普遍采用多模型协作。
- 本知识库后续按"定位 + 工程 + 长期维护"的方式组织模型内容。
