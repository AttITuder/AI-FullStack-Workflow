# 企业如何选择 AI 模型

> 面向企业研发的模型选型指南。核心思路：先定任务，再定 Workflow，最后选模型。

---

## 为什么需要了解

模型选型是企业 AI 化落地中最容易走偏的一环。多数团队要么"追最新最强"，要么"全员统一用一个模型"，结果要么成本失控，要么能力错配。真正的企业级做法是：**让任务、工作流与模型形成匹配关系**，并用网关抽象掉底层差异。本文提供一套可执行的选型框架。

## 基本概念

### 选型三要素

1. **任务（Task）**：要解决什么问题（编码、推理、视觉、对话……）。
2. **工作流（Workflow）**：任务如何组织（Agent 化、补全、审查、批处理……）。
3. **模型（Model）**：在什么载体上跑（API、本地、开源）。

### 常见误区

- ❌ "哪个模型最火就用哪个"。
- ❌ "一个模型打天下"。
- ❌ "只看价格不看能力"。
- ❌ "本地一定比 API 安全/便宜"。

## 核心能力：按任务选模型

### 什么时候选择 GPT

- **通用与生态需求**：需要跨场景通用能力、成熟生态与工具集成。
- **与 Microsoft / OpenAI 生态整合**：Azure OpenAI 场景。
- **多模态通用需求**：图文混用的综合任务。
- **适合**：企业级通用助手、快速原型、综合类任务。

### 什么时候选择 Claude

- **代码质量优先**：复杂代码生成、长上下文代码理解。
- **工程文档**：技术方案、架构文档、代码审查。
- **需要强长上下文**：大代码库、长文档场景。
- **适合**：AI Coding 主力、代码密集型研发团队。

### 什么时候选择 DeepSeek

- **成本敏感**：海量 Token 消耗的批处理与补全场景。
- **可控与私有化**：需要自部署或数据不出境。
- **推理要求高但预算有限**：R1 系列解决复杂推理。
- **适合**：性价比优先、有合规要求的国内团队。

### 什么时候选择 Gemini

- **强多模态**：视频、图片、音频综合理解。
- **Google 生态**：与 GCP、Workspace 深度集成。
- **超长上下文**：海量资料一次性处理。
- **适合**：内容型产品、多模态应用、Google 技术栈团队。

### 什么时候选择 Qwen

- **中文优化**：中文场景质量与效率均衡。
- **开源可控**：阿里系开源模型支持本地部署。
- **国内云生态**：与阿里云整合的团队。
- **适合**：中文业务、国内云上部署、混合（云端 + 本地）场景。

### 什么时候选择 Kimi

- **长文本处理**：报告、协议、长文档分析。
- **内容密集型**：信息抽取、文档问答。
- **适合**：内容运营、文档密集型业务。

## 多模型协作：什么时候用

单一模型总有力所不及之处，成熟企业普遍采用多模型协作：

- **按任务路由**：日常编码用性价比模型，疑难推理用推理模型，视觉任务用多模态模型。
- **按成本路由**：简单任务走廉价模型，复杂任务走旗舰模型。
- **按数据路由**：敏感数据走私有化模型，通用数据走 API 模型。
- **按可用性路由**：主模型故障时自动降级到备用模型。

落地方式：

- 统一模型网关（OpenRouter、自建代理）暴露统一接口。
- 工作流层按规则选择模型，切换对上层透明。
- 定期复盘各模型性价比，动态调整路由规则。

## 本地模型 vs API：什么时候用

### 选择本地模型

- 数据敏感、合规要求严格（医疗、金融、政务）。
- 固定负载、规模稳定，长期成本低于 API。
- 需要深度定制（微调、私有知识注入）。
- 网络受限、无法依赖外部服务。

### 选择 API 模型

- 快速验证、原型开发、弹性需求。
- 追求最强能力（旗舰模型通常不提供开源等价物）。
- 团队无 AI 基础设施与运维能力。
- 用量波动大，不想承担固定硬件成本。

## Vision：什么时候用

- **设计稿转代码**：UI 设计稿解析成页面结构。
- **错误排查**：截图、报错图识别。
- **文档数字化**：扫描件、流程图、架构图转文本。
- **UI 自动化测试**：页面元素视觉校验。

> 只有任务"真的需要看图"时才用多模态模型；纯文本任务用多模态模型是浪费成本。

## Reasoning：什么时候用

- **疑难 Bug 定位**：复杂逻辑链、跨模块问题。
- **算法与复杂度问题**：需要多步推导。
- **架构权衡**：多方案比较、取舍分析。
- **数据与业务分析**：报表解读、因果推断。

> 推理模型速度慢、成本高，只在"确实需要深度思考"时启用，日常任务不要默认走推理模型。

## Coding：什么时候用

- **代码生成**：页面、CRUD、工具类（用平衡型模型）。
- **重构**：结构优化、命名规范（用代码专项模型）。
- **审查**：规范、安全、性能检查（用代码专项模型 + 人工复核）。
- **调试**：报错分析、修复建议（简单用常规模型，疑难用推理模型）。

## 企业实践：构建选型工作流

### Step 1：盘点任务清单

列出团队实际 AI 任务，按"复杂度、频率、数据敏感性"分类。

### Step 2：建立能力需求矩阵

| 任务 | 复杂度 | 频率 | 数据敏感性 | 需要的模型能力 |
| --- | --- | --- | --- | --- |
| 代码补全 | 低 | 极高 | 中 | Coding |
| 功能开发 | 中 | 高 | 中 | Coding + Tool |
| 疑难调试 | 高 | 低 | 低 | Reasoning |
| 设计稿转码 | 中 | 中 | 低 | Vision + Coding |

### Step 3：匹配模型池

为每类任务匹配 1~2 个候选模型，形成"默认 + 备选"。

### Step 4：接入网关统一管理

通过统一接口路由，支持按任务、按成本、按可用性切换。

### Step 5：定期复盘

按月复盘各模型的任务完成率、成本与反馈，动态调整路由。

### 验收标准

- 每类任务都有明确的模型与备用模型。
- 成本可控且可预估。
- 模型切换不阻塞工作流。
- 数据合规风险已评估。

## 最佳实践

1. **先任务后模型**：选型始于任务清单，而非模型榜单。
2. **默认性价比，关键任务旗舰**：避免全员全程用旗舰模型。
3. **推理与视觉按需启用**：不把昂贵能力设为默认。
4. **抽象模型层**：让工作流与具体模型解耦。
5. **留退路**：任何模型选择都应有替代方案。

## 常见问题

**Q1：能不能只用一个模型？**

可以起步，但成本与能力平衡难；规模团队建议至少"轻快 + 旗舰"双模型。

**Q2：开源模型能承担核心开发吗？**

部分可以，取决于任务复杂度与数据要求；旗舰级能力仍是闭源优势。

**Q3：多模型协作会增加复杂度吗？**

会增加接口复杂度，但通过网关统一抽象后可把复杂度收敛到一处。

**Q4：价格变化快，文档会不会过时？**

本文只讲选型框架与 Workflow，不讲具体价格；价格信息在工具章节动态更新。

## 本章总结

- 企业选型的关键是"任务 → 工作流 → 模型"三层匹配。
- 不同厂商各有优势场景：GPT 通用、Claude 代码、DeepSeek 性价比、Gemini 多模态、Qwen 中文开源、Kimi 长文本。
- 成熟企业普遍多模型协作，通过网关统一路由。
- 本地 vs API、Vision、Reasoning、Coding 都有明确的启用时机。
