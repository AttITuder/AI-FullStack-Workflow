# Android AI 开发最佳实践

> 本文把散落在各章节的经验沉淀为可执行的团队实践。重点是 **Android 工程实践**，而非 AI 理论——每条都对应真实项目里"该怎么做"。

---

## 1. 项目上下文管理

AI 辅助开发前，先让 AI 理解项目现状，避免"盲写"。

### 1.1 建立项目快照

向 AI 提供：模块结构、`build.gradle`（依赖与配置）、Manifest（权限 / 组件）、关键代码。输出项目概览：技术栈、模块划分、架构方式、既有风格。

### 1.2 让 AI 对齐现有风格

生成的代码应符合项目既有的 Kotlin / Java、XML / Compose、MVVM / 其他、命名与封装方式，而非另起炉灶。

### 1.3 保持快照可更新

项目演进后快照要同步刷新。建议"改动前快速喂入相关模块，而非整个项目"，避免 Context 过载与漂移。

## 2. Prompt 设计

高质量 Prompt 是高质量产出的前提。

### 2.1 必备要素

- 角色设定（资深 Android 工程师）。
- 技术栈约束（Kotlin / Java、XML / Compose、MVVM / 状态、网络方案）。
- 明确任务与范围。
- 输出要求（文件结构、验收清单）。

### 2.2 用占位符复用模板

`prompts/android/` 用 `【】` 占位符（如 `【页面名称】`），改需求即可复用页面 / Compose / 联调等模板。

### 2.3 明确验收标准

告诉 AI "什么是完成"：可编译、结构合规、行为正确、错误处理完整、线程正确。这与 Android Agent 的自检清单一致。

### 2.4 负面约束

明确"不要做什么"：不要散落新建网络实例、不要在主线程做耗时操作、不要硬编码敏感信息、不要破坏分层。

## 3. Rules 管理

Rules 决定产出风格与质量的上限。

### 3.1 建立可执行的 Rules

`rules/android/` 应沉淀可检查的规则：

- Kotlin / Java 命名与风格。
- 分层与职责（UI / ViewModel / Domain / Data）。
- 网络层与数据层统一封装。
- 线程与生命周期约定。
- 禁止项（硬编码、重复代码、未处理错误、敏感信息）。

### 3.2 让 AI 遵守 Rules

- 在 Agent 系统提示词中引用 Rules。
- 在 Prompt 中要求对照 Rules 生成。
- 在 Review 阶段按 Rules 核对。

### 3.3 规则维护

规则随项目演进与团队反馈迭代，并与 Prompt、Agent 引用保持同步。

## 4. Agent 使用

`agents/android-agent` 让 Android + AI 协作稳定可复现。

### 4.1 一次配置、长期复用

加载 Agent 配置到 AI 工具，享受一致的协作体验，不必每次重新描述。

### 4.2 场景化委派

按任务类型使用：生成页面、修 Bug / Crash、Review、重构——Agent 有对应的动作约定。

### 4.3 保留关键人工介入

- 重构 / 架构变更：先看方案再确认。
- 最终 Review：人拍板。
- 发布 / 敏感变更：谨慎放权。

## 5. MCP 使用

MCP 让 AI 连接外部工具与数据（见 `mcp/` 与 `docs/08-mcp/`）。

### 5.1 常用接入点

- **ADB / 设备**：运行、查看 Logcat、调试。
- **Gradle / 构建**：构建反馈。
- **GitHub / Git**：版本与变更管理。
- **Figma**：设计稿读取，辅助 UI / Compose 还原。
- **文档 / 接口**：作为生成 Context。

### 5.2 使用原则

- 密钥走环境变量，不写进仓库。
- 按需启用，避免信息过载。
- 与 Prompt / Agent 配合：MCP 提供数据，Prompt 提供任务。

## 6. Kotlin 最佳实践

### 6.1 代码质量

- 用 `data class`、`val`、空安全（`?.` / `?:` / `!!` 谨慎使用）。
- 用协程（`suspend` / `flow`）表达异步，正确处理调度器（`Dispatchers.Main` / `IO`）。
- 避免过度使用 `!!`，优先空安全处理。
- 遵循官方 Kotlin 风格（`dart` / `lint` 一致的 `ktlint` / Android Lint）。

### 6.2 让 AI 产出合格 Kotlin

- 在 Prompt / Rules 中声明 Kotlin 风格约束。
- 生成后跑 `./gradlew lint` 与构建。
- Review 时检查协程与线程使用是否合理。

## 7. Java 维护

存量项目含 Java 代码，AI 需能维护与渐进迁移。

### 7.1 维护要点

- 尊重既有 Java 风格，不破坏兼容。
- 新增代码优先用 Kotlin（如项目已支持混编）。
- 渐进迁移：先低风险模块，再核心模块。

### 7.2 让 AI 维护 Java

- 明确哪些模块是 Java、哪些是 Kotlin。
- 迁移时保持行为不变，依托测试兜底。
- 混编项目注意类型交互（`@JvmStatic`、可空性标注）。

## 8. Compose 开发

### 8.1 Compose 最佳实践

- 用 `@Composable` 表达 UI，状态用 `StateFlow` / `collectAsState()` 收集。
- 保持组件可组合、可复用，拆分为小函数。
- 状态提升（State Hoisting）让组件无状态、易测试。
- 用 `remember` / `rememberSaveable` 正确管理局部状态。

### 8.2 让 AI 产出合格 Compose

- 在 Prompt 中提供页面描述与数据结构。
- 生成后构建 + 预览 / 真机验证。
- Review 时检查状态管理与重组性能（避免频繁重组）。

## 9. XML 维护

### 9.1 XML 最佳实践

- 控制布局层级深度，避免过度嵌套。
- 用 `ConstraintLayout` 合理组织约束。
- 资源（颜色 / 尺寸 / 字符串）放入 `res/`，不硬编码。

### 9.2 让 AI 维护 XML

- 提供现有布局作为风格参考。
- 明确适配要求（不同屏幕）。
- 生成后检查资源引用与 lint。

## 10. Code Review

AI 辅助审查能显著降低成本，但与人工结合。

### 10.1 AI 审查维度

- 命名与风格是否符合 `rules`。
- 分层与职责是否清晰。
- 线程与生命周期处理是否正确。
- 是否复用统一封装（网络、数据、依赖注入）。
- 性能隐患与安全风险。

### 10.2 审查流程

```text
提交变更 → AI 对照 Rules 审查 → 输出结构化意见 → 人工复核采纳
```

### 10.3 重点审查点

- 硬编码敏感信息（Token / 密钥 / 密钥文件）。
- 主线程耗时操作与未处理异步。
- 内存泄漏（静态引用、Listener 未解绑）。
- 权限是否存在缺失或过度申请。

## 11. 测试

测试是保证 AI 产出质量的关键闭环。

### 11.1 建立分层测试

- 单元测试：ViewModel、Repository、用例、Model 逻辑。
- Instrumented 测试：依赖 Android 环境的集成 / UI 测试。

### 11.2 让 AI 生成测试

AI 能生成覆盖关键分支的测试，尤其适合：

- ViewModel 的加载 / 成功 / 失败三态。
- Repository 的数据来源与缓存。
- Model 的转换逻辑。

### 11.3 测试作为验证标准

AI 改代码后，跑 `./gradlew test` 确认行为不变（尤其重构时）。测试体系是"信任 AI 产出"的前提。

## 12. 发布

发布链路涉及安全与合规，需谨慎处理。

### 12.1 发布检查

- 版本号与 `versionCode` / `versionName` 正确。
- 签名证书与密钥安全管理（不提交仓库）。
- 混淆（R8 / ProGuard）规则完整，避免运行时问题。
- 多渠道与构建变体正确。

### 12.2 AI 在发布中的角色

- AI 辅助生成构建配置、检查项与文档。
- 关键发布决定（签名、上架、合规）由人掌控。
- 涉及密钥 / 证书的配置严格安全处理。

## 13. 安全

安全红线是 AI 开发的底线。

### 13.1 敏感信息

- 禁止把 Token、密钥、证书写进代码或提交仓库。
- 密钥走环境变量或安全配置（BuildConfig 注意混淆）。
- Review 时重点排查硬编码敏感信息。

### 13.2 权限与数据

- 最小权限原则：只申请必要权限。
- 存储与传输安全：敏感数据加密、HTTPS。
- 输入校验，防注入与恶意数据。

### 13.3 AI 的边界

涉及安全敏感代码要谨慎，必要时由安全人员复核。安全规则纳入 `rules/android/`。

## 总结

- 最佳实践的核心是"**Android 工程实践**"：上下文、Prompt、Rules、Agent、MCP 协同，落到 Kotlin / Java / Compose / XML、测试、发布、安全。
- 统一原则：先理解再写、先方案后动手、可验证、遵循 Rules、重视线程 / 生命周期 / 兼容性、人工关键介入。
- 团队沉淀统一资产（Prompt / Rules / Agent / MCP），让 AI 产出"可复制"的高质量。
