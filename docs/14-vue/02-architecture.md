# Vue 工程架构

> 本文讲解 Vue 前端工程的典型分层与组织方式，以及 AI / Agent 如何理解并利用这套架构高效产出代码。它不绑定某一技术方案为唯一方案——状态管理、UI 库、CSS 方案都取决于项目实际，选择权在项目。

---

## 1. Vue 应用整体架构

一个可维护的 Vue 应用，通常由多层职责清晰的代码组成。分层的目标是**降低耦合、提高可测性、让 AI 与团队成员能在明确边界内工作**。

典型的分层视图：

```text
页面层（路由对应的页面组件）
   ↓
UI 层（基础组件 / 业务组件）
   ↓
状态管理层（Pinia / 组件局部状态）
   ↓
数据层（API / Service / Repository）
```

对应到典型文件结构：

```text
src/
├── main.ts            # 应用入口
├── router/            # 路由配置
├── stores/            # Pinia 状态
├── views/             # 页面组件
├── components/        # 通用 / 业务组件
├── composables/       # 可复用逻辑
├── api/               # API 请求封装
├── services/          # 业务服务
├── types/             # TypeScript 类型定义
└── styles/            # 全局样式
```

> 注意：这是**常见**的组织方式，不是唯一标准。不同项目可以采用不同结构。只要分层清晰、职责单一、AI 能读懂其意图，不必照搬。

架构设计的根本问题是：**如何让每一行代码，既容易被人维护，也容易被 AI 正确理解与扩展。**

## 2. 页面层

页面层是路由对应的顶层组件，负责把一个"路由路径"渲染成完整界面。

### 2.1 页面职责

- 组合基础组件与业务组件。
- 作为该路由的数据入口配置（可配合 `beforeRouteEnter` 数据预取或页面内初始化）。
- 保持页面内逻辑清晰，把可复用部分下沉到组件或 composables。

### 2.2 AI 视角下的页面层

对 Agent 而言，页面是"目标最明确"的部分——需求往往描述的是页面。AI 生成页面时需同时考虑模板、逻辑、样式与路由注册，保持与项目其他页面一致的风格。

### 2.3 页面组件划分

一个页面不应过度膨胀。若页面承载多个独立区域，可拆为多个业务组件，页面组件负责编排。

## 3. 状态管理

状态管理决定"数据变化如何驱动视图更新"。

### 3.1 Pinia

Pinia 是 Vue 3 推荐的状态管理方案，基于 Composition API，简约、类型安全：

```ts
// stores/user.ts
export const useUserStore = defineStore('user', {
  state: () => ({ name: '', loading: false }),
  getters: { upperName: (s) => s.name.toUpperCase() },
  actions: { async fetch() { /* ... */ } },
})
```

### 3.2 Vuex

Vuex 是 Vue 2 时代的经典方案，在 Vue 3 项目中常被 Pinia 取代。存量 Vuex 项目升级时 AI 可辅助迁移。

### 3.3 全局状态 vs 局部状态

- **局部状态**：仅属于单个组件或页面的状态，用 `ref` / `reactive` 即可。
- **全局状态**：被多个组件 / 页面共享的状态（用户、权限、主题），放入 Pinia。
- 原则：**能用局部就不用全局**，避免滥用 store 增加复杂度。

### 3.4 AI 视角下的状态管理

Agent 生成代码时需正确区分局部与全局状态：跨组件共享才用 Pinia，单组件内部用 `ref`。同时处理好异步状态（加载 / 成功 / 失败）。

## 4. 路由层

路由层负责页面导航与 URL 映射。

### 4.1 Vue Router

Vue Router 通过路由表把路径映射到页面组件，支持嵌套路由、懒加载、路由守卫。

```ts
const routes = [
  { path: '/', component: () => import('@/views/Home.vue') },
  { path: '/login', component: () => import('@/views/Login.vue') },
]
```

### 4.2 关键关注点

- 页面懒加载（`() => import(...)`）以优化首屏，是 AI 生成页面时的重要约定。
- 路由守卫（`beforeEach` 等）做鉴权与权限控制。
- 嵌套路由与布局（Layout）组织清晰。

### 4.3 AI 视角下的路由

AI 生成新页面时应同步产出路由配置，否则页面无法被访问。Review 时重点核对路由注册与懒加载。

## 5. 数据层

数据层负责与后端交互与数据获取，向上供给页面与状态管理。

### 5.1 API

API 层封装后端请求，通常基于 `axios` / `fetch` 建立统一客户端（BaseURL、拦截器、错误统一处理）：

```ts
// api/http.ts
export const http = axios.create({ baseURL: import.meta.env.VITE_API_BASE })
```

### 5.2 Service

Service 把多个 API 调用组织成"业务操作"，屏蔽具体请求细节。它对上层暴露语义化方法（如 `fetchUserList`）。

### 5.3 Repository

Repository 模式把"数据从哪来"（网络 / 缓存）抽象到一门面，让上层不关心数据来源。中小项目可用 API + Service 替代；数据来源复杂时引入 Repository。

| 层 | 职责 |
| --- | --- |
| API | 原始请求，封装 HTTP 细节 |
| Service | 业务级数据操作 |
| Repository | 数据来源抽象（网络 / 缓存） |

## 6. 组件设计

组件是 Vue 的核心复用单元，分为不同层级。

### 6.1 基础组件

与业务无关的通用 UI（按钮、表单、弹窗），通常来自 UI 组件库或项目自建。接口（`props` / `emits`）清晰、可配置、可复用。

### 6.2 业务组件

与特定业务相关的组合组件（如"用户卡片"），由基础组件与业务逻辑组成，跨页面复用。

### 6.3 页面组件

与路由对应的顶层组件，负责组织页面结构，组合业务组件。

### 6.4 组件设计原则

- 单一职责：一个组件只做一件事。
- 接口清晰：用 `props` 传入、`emits` 传出，避免组件间直接操作对方状态。
- 可复用下沉：复用度高的逻辑提取到 composables。
- 命名规范：组件文件名 / 组件名与用途对应。

### 6.5 AI 视角下的组件

AI 生成组件时应判断其层级（基础 / 业务 / 页面），设计清晰的 props / emits，并按项目命名与文件组织方式产出。

## 7. 前端工程化

工程化是 Vue 项目可长期维护的基础。

### 7.1 Vite

Vite 是 Vue 3 的构建工具，`vite.config.ts` 管理插件、代理（dev server proxy 解决跨域）、路径别名等。AI 涉及构建配置时需理解 Vite 语法。

### 7.2 TypeScript

TS 提供类型安全。AI 生成代码时应产出类型定义（接口、泛型），避免 `any` 泛滥；`tsconfig.json` 是配置中心。

### 7.3 ESLint / Prettier

ESLint 检查代码质量与规范，Prettier 统一格式。AI 生成代码后应跑 lint 校验，遵循项目 `eslintrc` 规则。

### 7.4 构建流程

依赖安装（`npm install`）、类型检查、lint、测试、构建（`npm run build`）、产物发布。这是 AI 生成代码后最先得到的验证闭环。

## 8. 大型 Vue 项目架构

大型项目在基础分层之上，还需考虑：

### 8.1 架构演进路径

不追求一步到位，随规模渐进：

```text
单页面 + 组件堆积
   ↓
按业务拆分 views / components（组件化）
   ↓
引入 Pinia 状态 + API / Service 分层
   ↓
模块化（按业务域组织）+ 路由分组 + 规范工程化
```

### 8.2 大型项目的关注点

- **模块化**：按业务域组织代码（views / stores / api 对应模块），降低耦合。
- **组件体系**：基础组件、业务组件、页面组件分层清晰。
- **可复用逻辑**：用 composables 沉淀跨模块复用逻辑。
- **工程化**：TS、ESLint、测试、CI 全链路一致。
- **多人协作**：目录结构稳定、命名规范，减少合并冲突。

### 8.3 AI 在架构演进中的角色

AI 可以分析现有组织方式、发现组件过度膨胀或状态混乱、给出拆分与模块化建议、辅助迁移重构。但重大架构变更必须**先出方案让团队确认**。

## 9. AI 辅助架构分析

AI 可以作为"架构顾问"来使用。

### 9.1 分析输入

给 AI 提供目录结构、路由配置、关键组件、`package.json` 等，让它输出：

- 当前架构的分层与组件体系是否清晰。
- 职责是否单一，耦合是否过高。
- 状态管理是否合理（局部 / 全局）。
- 潜在的重构点与新功能的最佳落点。

### 9.2 分析输出格式

结构化输出：**现状**、**问题**、**建议**（按优先级）、**不强制**（尊重项目现状）。

### 9.3 可信度控制

AI 的架构判断需人工校验。把 AI 当作"假设生成器"，由团队用真实代码验证——"AI 分析 → 人决策"。

## 10. Agent 如何理解 Vue 项目

Agent 作为执行层，必须能"读懂"Vue 项目后再动手。

### 10.1 先读再写

Agent 在"分析"阶段应理解：目录结构、技术栈（Vue3 / TS / Vite / Pinia / UI 库 / CSS 方案）、路由、状态管理、API 封装方式、既有组件风格。

### 10.2 对齐项目技术栈

Agent 生成代码时对齐项目既有方案，不另起炉灶。通过 `rules/vue/` 的规范进一步保证一致性。

### 10.3 场景化响应

Agent 针对不同任务采取不同动作：生成页面按项目结构与模板产出、修 Bug 先定位根因、重构先出方案确认。对不熟悉的架构"不瞎猜"。

### 10.4 帮助 Agent 理解的最佳实践

- 保持目录结构与命名一致。
- 用简洁注释说明模块 / 组件职责。
- `rules/vue/` 明确规范，给 Agent 可检查的约束。
- 大改动前，让 AI 先生成"理解后的改造方案"再做。

## 总结

- Vue 架构核心是**分层清晰、职责单一**：页面层、UI 组件、状态管理、数据层各司其职。
- **不绑定某一技术方案为唯一方案**——Pinia / Vuex、UI 库、CSS 方案都取决于项目实际。
- 组件设计（基础 / 业务 / 页面）、路由、工程化是大型 Vue 项目组织与 AI 安全协作的基础。
- Agent 的价值在于**先理解项目再动手**，在明确边界内生成与修改代码。
