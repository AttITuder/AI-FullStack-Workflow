# Vue AI 开发最佳实践

> 本文把散落在各章节的经验沉淀为可执行的团队实践。重点是 **Vue 工程实践**，而非 AI 理论——每条都对应真实前端项目里"该怎么做"。

---

## 1. 项目 Context 管理

AI 辅助开发前，先让 AI 理解项目现状，避免"盲写"。

### 1.1 建立项目快照

向 AI 提供：目录结构、路由配置、关键组件、`package.json`（依赖与脚本）。输出项目概览：技术栈、模块划分、组件组织、既有风格。

### 1.2 让 AI 对齐现有风格

生成的代码应符合项目既有的 Vue3 / Composition API、TS、UI 库、CSS 方案与命名，而非另起炉灶。

### 1.3 保持快照可更新

项目演进后快照要同步刷新。建议"改动前快速喂入相关模块，而非整个项目"，避免 Context 过载与漂移。

## 2. Prompt 设计

高质量 Prompt 是高质量产出的前提。

### 2.1 必备要素

- 角色设定（资深 Vue 前端工程师）。
- 技术栈约束（Vue3 / Composition API / TS / Vite / Pinia / UI 库 / CSS 方案）。
- 明确任务与范围。
- 输出要求（文件、结构、验收清单）。

### 2.2 用占位符复用模板

`prompts/vue/` 用 `【】` 占位符（如 `【页面名称】`），改需求即可复用页面 / 组件 / UI 还原等模板。

### 2.3 明确验收标准

告诉 AI "什么是完成"：可编译、组件结构合理、行为正确、类型严谨、样式符合方案。

### 2.4 负面约束

明确"不要做什么"：不要散落新建 API 实例、不要滥用 any、不要硬编码敏感信息、不要破坏组件边界。

## 3. Rules 管理

Rules 决定产出风格与质量的上限。

### 3.1 建立可执行的 Rules

`rules/vue/` 应沉淀可检查的规则：

- Vue3 / Composition API 写法规范。
- TypeScript 类型约束。
- 组件命名、文件结构、props / emits 约定。
- 状态管理使用方式（何时用全局 / 局部）。
- 禁止项（硬编码、重复代码、未处理错误、敏感信息）。

### 3.2 让 AI 遵守 Rules

- 在 Agent 系统提示词中引用 Rules。
- 在 Prompt 中要求对照 Rules 生成。
- 在 Review 阶段按 Rules 核对。

### 3.3 规则维护

规则随项目演进与团队反馈迭代，并与 Prompt、Agent 引用保持同步。

## 4. Agent 使用

`agents/` 中的架构 / Review / Test 等 Agent 让 Vue + AI 协作稳定可复现。

### 4.1 一次配置、长期复用

加载 Agent 配置到 AI 工具，享受一致的协作体验，不必每次重新描述。

### 4.2 场景化委派

按任务类型使用：架构 Agent 理清项目结构、Review Agent 审查代码、Test Agent 辅助测试。

### 4.3 保留关键人工介入

- 重构 / 架构变更：先看方案再确认。
- 最终 Review：人拍板。
- 发布 / 敏感变更：谨慎放权。

## 5. MCP 使用

MCP 让 AI 连接外部工具与数据（见 `mcp/` 与 `docs/08-mcp/`）。

### 5.1 常用接入点

- **Figma**：设计稿读取，辅助 UI / 组件还原。
- **文档 / 接口**：规范与接口文档作为生成 Context。
- **GitHub / Git**：版本与变更管理。
- **数据库 / 数据**：联调数据参考。

### 5.2 使用原则

- 密钥走环境变量，不写进仓库。
- 按需启用，避免信息过载。
- 与 Prompt / Agent 配合：MCP 提供数据，Prompt 提供任务。

## 6. 组件设计

组件是 Vue 的核心，好设计是 AI 高质量协作的基础。

### 6.1 分层与职责

- 基础组件、业务组件、页面组件分层清晰。
- 单一职责，一个组件只做一件事。
- 接口（props / emits）清晰，避免组件间直接操作对方状态。

### 6.2 可复用逻辑

复用度高的逻辑提取到 `composables`，让组件更薄、更可测。

### 6.3 让 AI 产出好组件

- 在 Prompt 中明确组件层级与接口。
- 生成后检查命名、结构、样式是否一致。
- Review 时核对职责是否单一。

## 7. 状态管理

状态管理决定数据流是否清晰。

### 7.1 划分局部 / 全局

- 组件局部状态用 `ref` / `reactive`。
- 跨组件共享用 Pinia，避免滥用全局 store。
- 异步状态用统一的 loading / data / error 三态。

### 7.2 让 AI 产出合理状态

- 明确"什么状态放哪"给 AI。
- 避免响应式丢失（解构、赋值后失去响应性）。
- Review 时检查状态边界是否合理。

## 8. 性能优化

性能优化是测量驱动的。

### 8.1 常见优化手段

- 路由与组件懒加载，减小首屏包体积。
- 合理用 `computed` 与缓存，避免多余渲染。
- 列表用 `key`、虚拟滚动处理大列表。
- 请求并发 / 缓存 / 分页优化。

### 8.2 让 AI 参与优化

- AI 基于测量数据（DevTools / Lighthouse）给方案。
- 让 AI 改造后复测，确认有收益。
- 避免"为了优化而优化"增加复杂度。

### 8.3 性能验收

首屏时间、交互流畅度、包体积达标才交付。

## 9. TypeScript 规范

TS 是 Vue 项目质量的重要保障。

### 9.1 规范要点

- 为组件 props / emits 定义类型。
- 为接口数据定义类型，避免 `any` 泛滥。
- 合理使用泛型与工具类型。
- `tsconfig.json` 严格配置（`strict` 开启）。

### 9.2 让 AI 产出合格 TS

- 在 Prompt / Rules 中声明 TS 约束。
- 生成后跑类型检查（`vue-tsc` / `tsc`）。
- Review 时检查类型是否严谨。

## 10. Code Review

AI 辅助审查能显著降低成本，但与人工结合。

### 10.1 AI 审查维度

- 组件命名、结构、props / emits 是否清晰。
- 状态管理是否合理（局部 / 全局）。
- TypeScript 类型是否严谨。
- 是否复用统一封装（API、样式、组件）。
- 性能隐患与安全风险。

### 10.2 审查流程

```text
提交变更 → Agent 对照 Rules 审查 → 输出结构化意见 → 人工复核采纳
```

### 10.3 重点审查点

- 硬编码敏感信息（Token / 密钥）。
- 响应式丢失与异步未处理。
- 组件过度膨胀与耦合。
- 未遵循 Rules 与项目规范。

## 11. 测试

测试是保证 AI 产出质量的关键闭环。

### 11.1 建立分层测试

- 单元测试：composables、状态逻辑（Pinia）、工具函数。
- 组件测试：组件渲染、事件、props / emits。
- E2E 测试：关键用户流程（可选，如 Playwright / Cypress）。

### 11.2 让 AI 生成测试

AI 能生成覆盖关键分支的测试，尤其适合：

- composables 与 store 的三态。
- 组件 props / emits 与渲染结果。
- API 方法的数据处理。

### 11.3 测试作为验证标准

AI 改代码后，跑 `npm run test` 确认行为不变（尤其重构时）。测试体系是"信任 AI 产出"的前提。

## 12. 发布

发布链路涉及构建与部署，需谨慎处理。

### 12.1 发布检查

- 环境变量（dev / prod）正确。
- 构建产物（`npm run build`）通过。
- 版本管理与变更日志。
- 部署与环境配置正确。

### 12.2 AI 在发布中的角色

- AI 辅助生成构建配置与发布检查项。
- 关键发布决定由人掌控。
- 涉及密钥 / 配置的严格安全处理。

## 总结

- 最佳实践的核心是"**Vue 工程实践**"：Context、Prompt、Rules、Agent、MCP 协同，落到组件设计、状态管理、性能优化、TS 规范、测试、发布。
- 统一原则：先理解再写、先方案后动手、可验证、遵循 Rules、重视组件与状态边界、人工关键介入。
- 团队沉淀统一资产（Prompt / Rules / Agent / MCP），让 AI 产出"可复制"的高质量。
