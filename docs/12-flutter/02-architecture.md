# Flutter 工程架构

> 本文讲解 Flutter 工程的典型分层与组织方式，以及 AI / Agent 如何理解并利用这套架构高效产出代码。它不绑定单一架构方案——GetX、Bloc、Provider 都只是选项，选择权在项目实际。

---

## 1. Flutter 应用整体架构

一个可维护的 Flutter 应用，通常由多层职责清晰的代码组成。分层的目标是**降低耦合、提高可测性、让 AI 与团队成员能在明确边界内工作**。

典型的分层视图：

```text
UI 层（页面 / Widget / 组件）
   ↓
状态管理层（State Management，连接 UI 与数据）
   ↓
数据层（Repository / Model / 本地存储）
   ↓
网络层（API 客户端 / 统一请求封装）
```

对应到文件结构，常见的组织方式（以本项目 `prompts/flutter/generate_page.md` 的期望结构为例）：

```text
lib/
├── app/
│   ├── routes/        # 统一路由
│   └── theme/         # 主题
├── modules/           # 业务模块，按页面划分
│   └── login/
│       ├── controller/
│       ├── binding/
│       ├── view/
│       └── model/
├── services/
│   └── api/           # 网络 / 接口封装
└── shared/            # 通用组件、工具、常量
```

> 注意：这是**一种**参考组织方式，不是唯一标准。只要分层清晰、职责单一、AI 能读懂其意图，不必照搬。

架构设计的根本问题是：**如何让每一行代码，既容易被人维护，也容易被 AI 正确理解与扩展。**

## 2. 页面层

页面层（UI 层）负责把数据渲染成界面、接收用户交互。它是 Flutter 中最"显性"的一层。

### 2.1 Widget 组织原则

- 优先**组合**与**复用**：把可复用的 UI 拆成独立 Widget，而不是把所有内容堆进一个巨型 Widget。
- 用 `StatelessWidget` 表达纯展示，用 `StatefulWidget` 管理局部可变状态。
- 保持 Widget 职责单一，一个 Widget 只做一件事。

### 2.2 页面与业务逻辑分离

页面层不应直接耦合数据逻辑。理想情况下，页面读取状态管理层的状态、调用其方法，由状态管理层处理业务。这让 AI 在"改界面"时不易破坏"数据逻辑"。

### 2.3 AI 视角下的页面层

对 Agent 而言，页面层是"目标最明确"的部分——需求往往描述的是界面。`flutter-agent` 生成页面时会按 `view` 目录产出组件代码，并把交互事件交给 Controller（状态管理层）处理。

## 3. 状态管理层

状态管理层是 Flutter 工程的复杂度核心，决定"数据变化如何驱动界面更新"。

### 3.1 状态粒度的选择

- **局部状态**：仅属于单个 Widget 的状态，可用 `setState` 或轻量状态对象。
- **共享状态**：被多个页面 / 模块共享的状态，需要全局或作用域化的状态管理方案。
- 选择原则：**能用小方案不用大方案**，避免为简单场景引入重型框架。

### 3.2 常见方案对比

| 方案 | 特点 | 适用场景 |
| --- | --- | --- |
| `setState` | Flutter 内置，简单直接 | 局部、低频状态 |
| `Provider` | 轻量、官方推荐路径，依赖注入 | 中小型项目 |
| `Riverpod` | 编译安全、可组合、易测试 | 中大型、追求类型安全 |
| `GetX` | 一体化，含路由 / 依赖注入 / 状态管理，写起来简洁 | 追求开发效率、全功能框架 |
| `Bloc` | 事件驱动、单向数据流、高可测试性 | 复杂业务、严格分层 |

> 本项目资产（`prompts/flutter/`、`agents/flutter-agent/`）以 **GetX** 为示例技术栈，但 **本章不把任何方案设为唯一答案**。选择依据应是项目规模、团队熟练度与维护成本。

### 3.3 AI 视角下的状态管理

Agent 在生成代码时，需要正确理解状态流转：加载中、成功、失败三态如何表示，异步数据如何呈现，跨页面状态如何共享。`03-development-workflow.md` 有专门的状态管理 Workflow。

## 4. 数据层

数据层负责把"领域数据"组织起来，向上供给状态管理层。

### 4.1 Model

Model 是数据的结构化表示。AI 生成 Model 时要注意：字段与后端 / 业务对应、JSON 序列化正确、类型合理。Dart 中可用手写 `fromJson` / `toJson`，或引入 `json_serializable` 等代码生成工具。

```dart
class User {
  final String name;
  final int age;

  User({required this.name, required this.age});

  factory User.fromJson(Map<String, dynamic> json) {
    return User(name: json['name'], age: json['age']);
  }
}
```

### 4.2 Repository

Repository 是数据来源的抽象，屏蔽"来自网络还是本地缓存"。它让上层不关心数据从哪来，也让本地化 / 缓存策略可以独立演进。这是 AI 重构与测试时的重要边界。

### 4.3 本地存储

按需引入 `shared_preferences`（轻量键值）、`sqflite`（SQLite）、`hive`（NoSQL）等。本地存储应封装在数据层，避免在页面层散落。

## 5. 网络层

网络层负责与后端通信，并做统一封装，避免每个页面各自写请求。

### 5.1 统一客户端

以 `dio` 为例，统一封装通常包含：

- 基础配置：BaseUrl、超时、Header。
- 拦截器：Token 注入、日志、错误统一处理。
- 返回解析：统一响应结构、错误码映射。

```dart
final dio = Dio(BaseOptions(
  baseUrl: 'https://api.example.com',
  connectTimeout: Duration(seconds: 10),
));
```

### 5.2 AI 生成网络代码的注意点

- 复用统一客户端，不散落新建 `Dio` 实例。
- 正确处理异常与超时，给出用户可理解的错误提示。
- 涉及环境差异（dev / prod）时，BaseUrl 由配置控制而非硬编码。

`rules/flutter/` 的"网络层走统一封装"正是为了约束这一点。

## 6. 模块化设计

模块化是按业务边界分割代码，使大型项目可并行开发、独立演进。

### 6.1 按业务模块划分

以业务功能为边界（如 `login`、`home`、`profile`），每个模块内部再按科技分层（controller / view / model）。模块之间通过明确接口交互，尽量降低互相依赖。

### 6.2 模块化带来的 AI 协作价值

- 模块边界清晰后，Agent 可以在"一个模块"内安全地生成与修改代码，不污染其他模块。
- 新增功能时，AI 能顺着模块结构快速定位"应该动哪里，不该动哪里"。
- 依赖关系明确，重构时的风险面可控。

## 7. Flutter Package 管理

依赖管理是 Flutter 工程的基石，由 `pubspec.yaml` 声明。

### 7.1 依赖组织

```yaml
dependencies:
  flutter:
    sdk: flutter
  dio: ^5.7.0
  get: ^4.6.6

dev_dependencies:
  flutter_lints: ^5.0.0
  test: ^1.25.0
```

- `dependencies`：运行时依赖。
- `dev_dependencies`：仅开发 / 测试用，如 lint 与测试库。
- 版本约束使用 `^` 语义化版本。

### 7.2 依赖管理要点

- 保持依赖精简，不随意引入。
- 新增依赖后需同步 `pub get` 并跑构建验证。
- 涉及平台插件时，注意 iOS / Android 的原生配置。
- AI 生成代码新增依赖时，应同步说明需要执行的命令（`agents/flutter-agent` 的输出要求）。

### 7.3 多 Package 与 Monorepo

大型项目可拆分为多个本地 Package（业务包、通用组件包、基础库包），用 `path` 依赖相互引用。复杂团队可用 Melos 等工具管理。AI 在这种结构下工作时，应先理解 Package 边界。

## 8. 大型 Flutter 项目架构

大型项目在基础分层之上，还需考虑：

### 8.1 架构演进路径

不追求一步到位。从简单到复杂渐进：

```text
单模块 + setState
   ↓
按业务拆模块 + Provider / Riverpod
   ↓
完整分层（UI / 状态 / 数据 / 网络）+ 统一路由 + 依赖注入
   ↓
多 Package / Monorepo + 代码生成 + 完整测试体系
```

架构是**随着规模增长而演进**的，而不是开局就上最重型方案。这一点直接约束 AI 的建议：Agent 应根据项目现状给"适当超前但不脱离现实"的方案，而非一律推重型架构。

### 8.2 大型项目的关注点

- **分层与职责**：每个模块的依赖方向清晰。
- **可测性**：状态管理、数据层可被单元测试覆盖。
- **一致性**：路由、错误处理、命名全局统一（这是 Rules 的作用）。
- **性能**：避免不必要的重建、合理使用不可变数据。
- **多人协作**：模块边界清晰，减少合并冲突。

### 8.3 AI 在架构演进中的角色

AI 可以：分析现有代码的组织方式、发现职责不清或依赖倒置、给出拆分建议、辅助迁移重构。但重大架构变更必须**先出方案让团队确认**，不能直接改动。

## 9. AI 辅助架构分析

AI 可以作为一个"架构顾问"来使用：

### 9.1 分析输入

给 AI 提供项目结构、关键代码、`pubspec.yaml`、路由配置等，让它输出：

- 当前架构的分层是否清晰。
- 职责是否单一，耦合是否过高。
- 潜在的重构点与新功能的最佳落点。

### 9.2 分析输出格式

好的架构分析应结构化输出：

- **现状**：各层现状与依赖关系。
- **问题**：职责不清、循环依赖、过度耦合等。
- **建议**：按优先级给出可执行的重构步骤。
- **不强制**：尊重项目现状，不推翻既有设计。

### 9.3 分析的可信度控制

AI 的架构判断需要人工校验。关键是把 AI 当作**假设生成器**，由团队用真实代码验证。这也是"AI 分析 → 人决策"协作模式的体现。

## 10. Agent 如何理解 Flutter 架构

`agents/flutter-agent` 作为执行层，必须能"读懂"项目架构后再动手，否则容易生成与现状不符的代码。它的理解路径：

### 10.1 先读再写

Agent 工作流的 `分析 → 设计` 阶段，就是在理解架构：

- 读取目录结构与分层。
- 读懂 `pubspec.yaml` 确定技术栈。
- 参考既有模块的组织方式与命名风格。
- 理解既有状态管理、路由、网络的使用方式。

### 10.2 对齐系统提示词约束

`agents/flutter-agent/prompt.md` 明确技术栈约束（Flutter 3.24+ / GetX / Dio / Clean Architecture）。Agent 生成代码时会依此对齐，并在 `自检` 阶段对照验收清单检查分层是否正确。

### 10.3 场景化响应

`workflow.md` 的场景响应约定让 Agent 在不同任务下采取不同动作：生成页面按模板流程、修 Bug 先定位根因、重构先出方案确认。这让 Agent 对架构的处理"保守而可控"——**不熟悉时先问，不确定时不动大改**。

### 10.4 帮助 Agent 理解架构的最佳实践

- 保持目录结构与命名一致，降低 AI 理解成本。
- 用简洁注释说明模块职责。
- `rules/flutter/` 明确规范，给 Agent 可检查的约束。
- 大改动前，让 AI 先生成"理解后的改造方案"再做。

## 总结

- Flutter 架构核心是**分层清晰、职责单一**：UI / 状态管理 / 数据 / 网络各司其职。
- **不绑定单一架构方案**——状态管理选型取决于项目规模与团队，GetX、Bloc、Provider 都只是选项。
- 模块化与 Package 管理是大型项目组织与 AI 安全协作的基础。
- Agent 的价值在于**先理解架构再动手**，在明确边界内生成与修改代码。
