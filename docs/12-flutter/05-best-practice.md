# Flutter AI 开发最佳实践

> 本文把散落在各章节的经验沉淀为可执行的团队实践。重点是 **Flutter 工程实践**，而非 AI 理论——每条都对应真实项目里"该怎么做"。

---

## 1. 项目分析

AI 辅助开发前，先让 AI 理解项目现状，避免"盲写"。

### 1.1 建立项目快照

向 AI 提供：目录结构、`pubspec.yaml`、路由配置、关键模块代码。输出项目概览：技术栈、模块划分、既有实现风格。

### 1.2 让 AI 对齐现有风格

生成的代码应符合项目既有的命名、分层、封装方式，而非另起炉灶。

### 1.3 保持快照可更新

项目演进后，快照要同步刷新，否则 AI 基于过时 Context 产出漂移。建议"改动前快速喂入相关模块，而非整个项目"。

## 2. Context 管理

Context 是影响 AI 产出的关键变量。

### 2.1 精准投喂

不是塞越多越好，而是投喂**与任务相关**的代码与文档：

- 改某页面前，喂该模块 + 依赖的网络层 + 路由。
- 改状态管理前，喂状态定义与消费方。
- 多余 Context 会引入干扰，甚至让 AI 过度引用。

### 2.2 结构化组织

提供注释清晰、命名一致的代码，AI 更容易理解意图。混乱的代码会让 AI 产出同样混乱。

### 2.3 关键信息前置

技术栈、架构、规范这类"必须遵守"的信息放在 Prompt 前部，减少被遗漏。

## 3. Prompt 编写

高质量 Prompt 是高质量产出的前提。

### 3.1 必备要素

- 角色设定（资深 Flutter 工程师）。
- 技术栈约束（Flutter 版本 / 状态管理 / 网络 / 架构）。
- 明确任务与范围。
- 输出要求（文件结构、验收清单）。

### 3.2 用占位符复用模板

`prompts/flutter/` 用 `【】` 占位符（如 `【页面名称】`），改需求即可复用 `generate_page.md`。

### 3.3 明确验收标准

告诉 AI "什么是完成"：可编译、结构合规、行为正确、错误处理完整。这与 `flutter-agent` 的自检清单一致。

### 3.4 负面约束

明确"不要做什么"：不要散落新建 Dio 实例、不要硬编码、不要破坏分层。

## 4. Rules 管理

Rules 决定产出风格与质量的上限。

### 4.1 建立可执行的 Rules

`rules/flutter/` 应沉淀可检查的规则：

- 命名（文件 / 类 / 方法 / 变量）。
- 分层与职责。
- 网络层统一封装。
- 状态管理方式。
- 禁止项（硬编码、重复代码、未处理错误）。

### 4.2 让 AI 遵守 Rules

- 在 Agent 系统提示词中引用 Rules。
- 在 Prompt 中要求对照 Rules 生成。
- 在 Review 阶段按 Rules 核对。

### 4.3 规则维护

规则不是"写一次就完"，需随项目演进与团队反馈迭代。规则与 Prompt、Agent 引用保持同步。

## 5. Agent 使用

`flutter-agent` 让 Flutter + AI 协作稳定可复现。

### 5.1 一次配置、长期复用

将 `agents/flutter-agent/prompt.md` 加载到 AI 工具，享受一致的协作体验，不必每次重新描述。

### 5.2 场景化委派

按任务类型使用：生成页面、修 Bug、Review、重构——Agent 有不同的动作约定（`workflow.md` 的场景响应）。

### 5.3 保留关键人工介入

- 重构 / 架构变更：先看方案再确认。
- 最终 Review：人拍板。
- 敏感变更：谨慎放权。

## 6. MCP 使用

MCP 让 AI 连接外部工具与数据（见 `mcp/` 与 `docs/08-mcp/`）。

### 6.1 常用接入点

- **Figma**：读取设计稿，辅助 UI 还原。
- **GitHub / Git**：版本管理、变更查看、辅助 Review。
- **ADB / 构建**：构建与调试反馈。
- **文档 / 接口**：作为生成 Context。

### 6.2 使用原则

- 密钥走环境变量，不写进仓库。
- 按需启用，避免信息过载。
- 与 Prompt / Agent 配合：MCP 提供数据，Prompt 提供任务。

## 7. Code Review

AI 辅助审查能显著降低成本，但要与人工结合。

### 7.1 AI 审查维度

- 命名与风格是否符合 `rules`。
- 分层与职责是否清晰。
- 错误处理与异常路径是否完整。
- 是否复用统一封装。
- 性能隐患与安全风险。

### 7.2 审查流程

```text
提交变更 → AI 对照 Rules 审查 → 输出结构化意见 → 人工复核采纳
```

### 7.3 重点审查点

- 硬编码敏感信息（Token / 密钥）。
- 未处理的异步错误。
- 页面耦合了不该有的业务逻辑。
- 验证后行为是否符合需求。

## 8. 测试

测试是保证 AI 产出质量的关键闭环。

### 8.1 建立分层测试

- 单元测试：状态管理、Model 序列化、工具函数。
- Widget 测试：关键 UI 与交互。
- 集成测试：核心流程（可选）。

### 8.2 让 AI 生成测试

AI 能生成覆盖关键分支的测试，尤其适合：

- Model 的 `fromJson` / `toJson` 边界。
- 状态管理的加载 / 成功 / 失败三态。
- 交互逻辑的触发与期望结果。

### 8.3 测试作为验证标准

AI 改代码后，跑 `flutter test` 确认行为不变（尤其重构时）。测试体系是"信任 AI 产出"的前提。

## 9. 重构

安全的重构让 AI 能持续改善代码质量。

### 9.1 原则

- 先方案、后动手（Agent 默认行为）。
- 重构不改变行为，只改变结构。
- 小步迭代，每步验证。

### 9.2 让 AI 有效重构

- 明确目标（拆巨型 Widget / 提取组件 / 统一命名）。
- 依托测试验证行为不变。
- 控制范围，避免牵连无关代码。

## 10. 安全

安全红线是 AI 开发的底线。

### 10.1 敏感信息

- 禁止把 Token、密钥、私钥写进代码。
- 密钥走环境变量或安全存储（如 `flutter_secure_storage`）。
- Review 时重点排查硬编码敏感信息。

### 10.2 输入与异常

- 校验输入，防注入与恶意数据。
- 完善错误处理，避免崩溃与数据泄露。
- 涉及外部存储 / 网络时注意安全传输。

### 10.3 AI 的边界

AI 生成涉及安全敏感的代码时要谨慎，必要时由安全人员复核。项目应把安全规则纳入 `rules/flutter/`。

## 11. 性能

性能优化是测量驱动的，而非凭感觉。

### 11.1 常见优化手段

- `const` 构造器减少重建。
- `ListView.builder` 懒加载大列表。
- `RepaintBoundary` 隔离重绘。
- 大图压缩 / 缓存。
- 耗时操作移出主线程（`compute` / `isolate`）。

### 11.2 让 AI 参与优化

- AI 基于测量数据（DevTools / Profile）给方案。
- 让 AI 改造后复测，确认有收益。
- 避免"为了优化而优化"增加复杂度。

### 11.3 性能验收

启动时间、滚动流畅度、内存占用达标才交付。

## 总结

- 最佳实践的核心是"**Flutter 工程实践**"：项目分析、Context、Prompt、Rules、Agent、MCP 协同，落到代码质量、测试、安全、性能。
- 统一原则：先理解再写、先方案后动手、可验证、遵循 Rules、人工关键介入。
- 团队沉淀统一资产（Prompt / Rules / Agent / MCP），让 AI 购出"可复制"的高质量。
