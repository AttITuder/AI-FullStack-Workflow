# Agent 最佳实践

> 本章节核心方法文章。Agent 要可靠落地，靠的是工程化设计而非调参技巧。以下二十条原则覆盖设计、安全、成本与长期维护。

---

## 1. Agent 单一职责

一个 Agent 只解决一类问题。flutter-agent 专注 Flutter 开发，review-agent 专注审查，不要造"全能 Agent"。单一职责带来三点好处：提示词更聚焦、能力更专业、出错面更小。Multi-Agent 用职责串联替代单 Agent 包揽（见 `04-workflow.md` 第 13 节）。

## 2. Agent 边界设计

明确"Agent 做什么、不做什么、能碰什么"：

- **能力边界**：支持哪些任务类型（如 flutter-agent：分析 / 生成 / 修 Bug / Review / 重构）。
- **文件边界**：允许改动的目录范围。
- **环境边界**：可读 / 可写 / 可部署的区分。

边界写进 `prompt.md` 与 `workflow.md`，是安全与可控的前提。

## 3. Context 控制

Context 是 Agent 的"视野"，过宽则噪、过窄则盲：

- **按需加载**：指示 Agent 先读相关模块，而非全量粘贴（见 `02-agent-architecture.md` 第 4 节）。
- **控制窗口**：删冗余、保关键，关键约束靠前放。
- **阶段归档**：长任务每阶段定稿后固化事实，避免后期污染。
- **接力恢复**：跨会话用工件摘要重注 Context。

## 4. Prompt 设计

Agent 的 Prompt 分两层设计：

- **系统提示词（prompt.md）**：角色、职责、技术栈约束、工作原则——稳定、长期。
- **任务提示词**：本次目标、范围、验收——灵活、单次。

设计纪律：复用成熟的任务 Prompt 沉淀到 `prompts/`；模糊任务先澄清（任务级 HITL）；占位符统一 `【】`（见 `docs/10-prompts/02-prompt-structure.md`）。

## 5. Rules 设计

Rules 是 Agent 的"长期纪律"，设计原则：

- **可执行可检查**：每条规则避免模糊表述，带验收口径（见 `docs/09-rules/`）。
- **下沉而非重复**：多个 Agent 都要遵守的约束写进 `rules/`，Agent 引用。
- **问题上升**：某约束反复出现在 Prompt 中 → 固化为 Rule。
- **同步更新**：Rule 变更后通知相关 Agent 引用方。

## 6. Tool 设计

Tool 是 Agent 的"动作单元"，设计粒度：

- **有界**：一个 Tool 做一件明确的事（"运行测试套件"优于"处理测试"）。
- **可观察**：必须返回明确结果（含错误信息）。
- **可恢复**：失败返回结构化错误，支持重试 / 回退。
- **最小集合**：只暴露任务必需的 Tools，减少风险与决策负担。

## 7. MCP 集成

MCP 是 Tool 的标准化供给层（见 `docs/08-mcp/`）：

- 优先用成熟 MCP Server（GitHub / ADB / Gradle / 数据库）而非临时脚本。
- 写 workflow 时假设工具可用，不描述实现。
- 密钥走环境变量，禁止入库。
- 工具调用安全由 Rules + 权限边界兜底。

## 8. 权限控制

权限是落地安全的底线：

- **最小权限**：默认无权限，按需开放。
- **四层边界**：文件 / 命令 / 环境 / 数据（见 `02-agent-architecture.md` 第 8 节）。
- **危险操作确认**：删除、push、部署、reset --hard 必须 HITL。
- **与 Rules 互补**：权限管"能不能"，Rules 管"该不该"。

## 9. Human-in-the-loop

HITL 是可控性的根本，在四类节点介入：

- **目标级**：任务模糊时确认意图。
- **方案级**：执行前确认计划（吸收最大不确定性）。
- **风险级**：危险操作前确认。
- **验收级**：最终交付前 Review。

设计原则：把 HITL 放在"代价最低、收益最高"的节点——方案确认优于事后返工。

## 10. Agent 错误恢复

Agent 必然失败，关键在恢复机制（见 `02-agent-architecture.md` 第 9 节）：

- 每步动作可回滚。
- Observation 返回失败信息供修正。
- 重试 / 回退 / 换路径 / 求助 / 终止五策略按需选用。
- **连续失败升级为人**，避免无限重试烧成本。

## 11. Agent 输出验证

"完成"必须由验证定义，不由 Agent 宣布：

- 验收清单来自真实踩坑（见 `docs/10-prompts/05-best-practice.md`）。
- Validator 组件对照清单逐项核对，AI 自检 + 人终审双重使用。
- 高风险产出（如涉及资金 / 生产的改动）必须人工验收通过才放行。

## 12. Agent 日志

可观测才能可控：

- 记录每步动作、调用了哪个 Tool、参数与结果。
- 关键状态节点留存，支持回放与复盘。
- 变更清单随交付输出（新增 / 修改文件、执行命令）。
- 日志是错误恢复与成本分析的数据基础。

## 13. Agent 成本控制

Agent 的多步自主执行 Token 消耗远高于单次问答：

- **控上下文**：删冗余、按需加载，减少每次输入 Token。
- **控循环**：限制 Agent Loop 最大步数，连续失败即止。
- **选模型**：重任务用强模型，轻任务用小模型。
- **批处理**：相似子任务合并执行，减少重复 Context 构建。
- **设预算**：对长任务预设成本上限，超限告警。

## 14. Multi-Agent 设计

多 Agent 协作原则：

- **职责单一、产出即 Context**：上一 Agent 交付物是下一环输入。
- **明确交接协议**：定义每个 Agent 的输入输出格式，避免衔接歧义。
- **避免环形依赖**：流程应是 DAG，不是互相调用死循环。
- **Developer 角色概念示例**：本项目中开发职责由具体技术栈 Agent 承担，勿虚构独立 `developer-agent`（见 `04-workflow.md` 第 13 节）。

## 15. Agent 与 Git 协作

Agent 应成为 Git 流程的参与者而非破坏者：

- 提交信息遵循 `rules/git/` 规范，Agent 生成、人确认。
- 分支策略由 workflow 规定，避免 Agent 随意切分支。
- 危险 Git 命令（push / force / reset）一律 HITL。
- 每次 Agent 改动建议独立提交，便于回滚与 Review。

## 16. Agent 与 Code Review

推荐"AI 初审 + 人终审"分工：

- Review Agent 承担机械检查（规范、命名、明显 Bug、安全模式）。
- 人聚焦架构合理性与业务正确性。
- 审查 Prompt 用固定维度防漏检（规范 / 逻辑 / 性能 / 安全）。
- 高优问题清零才放行，遗留项记录为技术债。

## 17. Agent 测试

Agent 本身也需测试：

- **资产测试**：新 `prompt.md` / `workflow.md` 必须在真实任务跑通再入库（见 `docs/10-prompts/05-best-practice.md` 实测原则）。
- **回归测试**：Agent 改动后，用固定任务验证产出未退化。
- **边界测试**：给模糊 / 异常输入，验证 Agent 是否触发 HITL 而非瞎做。
- **Tool 测试**：每个 Tool 单独验证可观察、可恢复。

## 18. Agent 版本管理

Agent 配置与代码同库同流程：

- 变更走 Git commit，message 说明动机（遵循项目 Git 规范）。
- 重要调整开 PR 让团队 Review。
- 历史靠 git log，不在文件内写版本记录。
- 命名稳定（flutter-agent / review-agent），v2 / final 属反模式。

## 19. Agent 长期维护

Agent 是活资产，需持续打磨：

- **反馈驱动**：使用中发现不好用，小步改、勤提交。
- **问题上升**：反复补救的约束下沉为 Rules。
- **资产同步**：技术栈演进时同步更新 prompt.md 与引用。
- **废弃仪式**：过时 Agent 明确删除或归档，README 规划清单同步。

## 20. 常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 造全能 Agent | 提示词臃肿、能力稀释 | 单一职责、Multi-Agent 串联 |
| 不给边界 | 越界改动、误删文件 | 文件 / 命令 / 环境边界写进配置 |
| 无 HITL | 危险操作无人拦 | 方案级 + 风险级人工确认 |
| 无验收清单 | "完成"由 AI 宣布 | Validator 对照清单核对 |
| 全量粘贴上下文 | 窗口爆炸、成本失控 | 按需加载、阶段归档 |
| 把 Agent 当聊天 | 只问答不执行 | 用 Tools / MCP 驱动环境改变 |
| 忽略错误恢复 | 一步错全盘崩 | 每步可回滚、连续失败升级为人 |
| 重复内联规则 | 规则更新不同步 | 引用 rules/，问题上升 |

## 总结

- 设计原则：单一职责、明确边界、Context 控制、Prompt/Rules 分层。
- 安全原则：最小权限、四层边界、HITL 四节点、错误恢复五策略。
- 质量原则：验证清单化、日志可观测、输出可回滚。
- 成本原则：控上下文、控循环、选模型、设预算。
- 协作原则：Multi-Agent 产出即 Context、Git 受控、AI 初审 + 人终审。
- 维护原则：实测入库、反馈驱动、问题上升、版本走 Git、废弃有仪式。
- 根因：Agent 不是聊天机器人，是需工程化设计的执行系统。
