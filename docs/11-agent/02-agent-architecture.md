# Agent 架构

> 本章节核心理论文章之一。从工程架构视角拆解 Agent：它由哪些部件构成、如何运转、如何决策、如何管理上下文与状态，以及它与传统应用架构的根本区别。

---

## 1. Agent 的基本架构

一个典型的 Agent 系统由以下参与方与部件组成：

```text
User（用户）
   │ 目标 / 反馈
   ↓
Agent（智能体）
   ├── Prompt      任务意图（系统提示词 + 本次任务）
   ├── Rules       行为约束（长期纪律）
   ├── Context     当前上下文（代码库、会话、文档）
   ├── Memory      长期记忆（跨会话沉淀）
   ├── Model       推理引擎（理解、规划、生成）
   ├── Tools       可执行动作（读写文件、跑命令）
   └── MCP         工具通道（连接外部系统）
   ↓
Environment（环境：代码库、仓库、CI、设备）
```

各部件职责：

| 部件 | 职责 | 来源 |
| --- | --- | --- |
| User | 给定目标、关键节点确认、最终验收 | 人 |
| Agent | 编排上述部件，驱动闭环执行 | 本章主题 |
| Model | 理解意图、推理、规划、生成文本 | `docs/02-models/` |
| Prompt | 系统提示词（角色/职责）+ 任务说明 | `docs/10-prompts/` |
| Rules | 编码/审查/提交规范等长期约束 | `rules/` |
| Context | 本次任务可见的全部信息 | 代码库 + 会话 |
| Memory | 跨会话沉淀的经验与偏好 | Agent 配置 |
| Tools | 具体动作单元（文件/命令/API） | Agent 宿主或 MCP |
| MCP | 标准化暴露外部 Tools 的协议 | `docs/08-mcp/` |
| Environment | Agent 施加油响的真实世界 | 本地 / 远端 |

> 这是**概念模型**，不是某个具体产品的实现图。不同 Coding Agent 工具（OpenCode、Claude Code 等）的内部实现各异，但都包含上述角色。本项目 `agents/` 下的配置对应其中 Prompt / Rules / Workflow 部分。

## 2. Agent Loop

Agent 的运行时是一个持续循环，把第 1 节的静态架构动起来：

```text
Input（用户输入目标）
   ↓
Context（加载相关上下文）
   ↓
Reasoning（模型推理：理解目标）
   ↓
Planning（制定执行计划）
   ↓
Tool Calling（调用工具执行动作）
   ↓
Observation（观察执行结果）
   ↓
Next Action（决定下一步：继续 / 修正 / 完成）
   ↓
（回到 Reasoning 或终止）
```

要点：

- **Context 先加载**：行动前先把相关代码 / 文档纳入视野，避免"盲改"。
- **Reasoning → Planning** 是关键决策段：模型把目标翻译成可执行的步骤序列；好的 Agent 会先出方案再动手（呼应 flutter-agent `workflow.md` 的"分析 → 设计 → 生成"）。
- **Observation 决定走向**：每步动作后必须观察结果，再决定下一步——这是 Agent 区别于脚本的根本（脚本不观察）。
- **终止条件**：目标达成、通过验证、需人工决策、或不可恢复错误。

## 3. Agent 的决策过程

Agent 在三个层级做决策：

### 目标级决策

"这个任务是否在我能力范围内？是否需要澄清？"——对应 HITL 入口。模糊任务应在这一步与人确认，而非直接动手。

### 规划级决策

"分几步完成？每步做什么？"——把目标拆成 Tool Calling 序列。规划质量决定后续执行是否走偏。工程上常用"先出方案待确认"吸收不确定性。

### 执行级决策

"这一步调用哪个 Tool？参数怎么填？结果说明什么？"——每步动作都是一次小决策，依赖 Observation 反馈。

决策的风险在于：模型是概率生成，可能给出看似合理实则错误的步骤。对策是**验证闭环 + 关键点人工确认**，不让 Agent 在无人监督下连续做高风险决策。

## 4. Agent 的上下文管理

Context 是模型在单次运行中"能看到"的全部信息。Agent 的上下文管理是工程成败的关键之一。

### 上下文的构成

- **任务上下文**：本次目标、约束、验收标准（来自 Prompt / Rules）。
- **代码上下文**：相关文件内容、仓库结构。
- **会话上下文**：本会话历史、已做的决策。
- **检索上下文**：Agent 按需从代码库检索得到的内容。

### 管理原则

1. **按需加载，而非全量搬运**：指示 Agent "先读相关模块"比把整个仓库粘贴进 Prompt 更高效、更省 Token（见 `docs/10-prompts/02-prompt-structure.md` Context 一节）。
2. **控制窗口占用**：冗长废话稀释关键约束的注意力权重。
3. **阶段归档**：长任务每阶段定稿后即"固化事实"，避免后期上下文污染（见 `04-workflow.md` 会话管理）。
4. **接力恢复**：跨会话时用工件摘要重新注入上下文，而非依赖模型"记得"。

## 5. Agent 的工具调用

Tool Calling 是 Agent "动手"的能力，也是它区别于 Chat AI 的基石（`docs/02-models/11-vision-and-toolcall.md`）。

### 调用过程

```text
模型决定调用 Tool X，参数 {a, b}
   ↓
宿主执行 Tool X
   ↓
返回结果（成功 / 失败 / 数据）
   ↓
模型观察结果，决定下一步
```

### 设计要点

- **工具粒度适中**：过粗难以组合，过细增加决策负担。理想粒度 = 一个"有界、可验证"的动作（"运行测试套件"而非"做测试相关的事"）。
- **结果可观察**：每个 Tool 必须返回明确结果（含错误信息），否则 Agent 无法进入 Observation 环节。
- **失败可恢复**：Tool 调用失败应返回结构化错误，让 Agent 修正参数或换路径，而非直接崩溃。
- **来源清晰**：Tools 可由 Agent 宿主原生提供，或由 MCP Server 提供（见第 11 节）。

## 6. Agent 的状态管理

Agent 在运行中维护两类状态：

### 会话内状态

单次任务执行到某一步时的"进度"：已完成步骤、当前目标、待办、已知约束。这类状态存活于本次会话上下文，任务结束即消散。

### 跨会话状态

需要长期保留的信息：用户偏好、项目约定、历史决策。这类状态应沉淀到 Memory 或 Rules，而非依赖"下次还记得"。

### 状态管理的工程意义

- **可恢复性**：任务中断后能基于状态续跑，而非从头开始。
- **可观测性**：状态清晰，人才看得懂 Agent "做到哪了、为什么卡住"。
- **可回放**：关键状态节点记录后，问题可定位、可复盘。

## 7. Agent 的记忆机制

Memory 是 Agent 的"长期记忆"，解决"下次还认得你 / 这个项目"的问题。

### 记忆的类型

| 类型 | 内容 | 实现方式 |
| --- | --- | --- |
| 语义记忆 | 项目约定、技术栈偏好 | 写入 Rules / Agent 配置 |
| 情节记忆 | 某次任务的决策与结果 | 会话归档 / 案例库 |
| 程序记忆 | "这类任务怎么做最快" | 沉淀为 Prompt / workflow |

### 与 Rules / Prompts 的关系

记忆机制不需要另起炉灶——本项目的工程做法是：

- 稳定的偏好 → 写进 `rules/` 或 Agent 的 `prompt.md`（长期生效）。
- 可复用的任务做法 → 沉淀到 `prompts/` 或 `workflow.md`。
- 一次性经验 → 留在会话，复盘后择优上升。

> 概念上 Memory 是一个部件；工程上本项目用 Rules / Prompts / Agents 三件套承担记忆职责，避免引入额外存储复杂度。

## 8. Agent 的权限边界

权限边界决定 Agent"能碰什么、不能碰什么"，是落地安全的底线。

### 边界的层次

1. **文件边界**：只允许改动指定目录（如 `lib/modules/login/`）。
2. **命令边界**：允许执行的命令白名单（如 `flutter test`，禁止 `rm -rf`）。
3. **环境边界**：只读生产、可写开发；禁止触达敏感系统。
4. **数据边界**：不读取密钥、不向外泄露代码（脱敏）。

### 设计原则

- **最小权限**：默认什么都不给，按需开放。
- **危险操作确认**：删除、推送、部署等动作必须人工确认。
- **与 Rules 配合**：权限是"能不能"，Rules 是"该不该"——两者互补（见 `05-best-practice.md` 权限控制）。

## 9. Agent 的错误恢复

Agent 必然会在某步失败——错误的 Tool 参数、误解的约束、环境异常。错误恢复能力决定它是"脆弱脚本"还是"可靠执行者"。

### 恢复策略

| 策略 | 说明 |
| --- | --- |
| 重试 | 用不同参数重试同一 Tool |
| 回退 | 撤销上一步改动，回到稳定状态 |
| 换路径 | 原计划行不通时重新规划 |
| 求助 | 进入 HITL，请人决策 |
| 终止 | 不可恢复时安全停止并报告 |

### 工程要点

- 每步动作可回滚，是错误恢复的前提。
- Observation 必须包含失败信息，恢复才有依据。
- 连续失败应升级为人介入，而非无限重试（避免成本失控）。

## 10. Agent Architecture 与传统应用 Architecture 的区别

这是理解 Agent 的关键。

| 维度 | 传统应用架构 | Agent 架构 |
| --- | --- | --- |
| 控制流 | 确定性、代码写死 | 概率性、由模型运行时决定 |
| 正确性 | 逻辑对错可穷举测试 | 输出"合理"但不保证正确 |
| 输入 | 结构化参数 | 自然语言目标 |
| 流程 | 固定分支 | 动态规划、可自我修正 |
| 边界 | 类型与接口约束 | 提示词、规则、权限约束 |
| 失败 | 异常可预测 | 可能"看似成功实则错" |
| 可维护性 | 重构代码 | 迭代 Prompt / Rules / workflow |

核心差异：**传统架构的"正确"由控制流保证，Agent 架构的"正确"由验证闭环 + 人工把关保证。** 因此 Agent 系统必须把"验证"和"人"当作一等公民，而不是事后补救。

## 11. Agent 与 MCP / Rules / Prompt 的组合

Agent 本身是空壳，真正的能力来自与下层的组合：

### Agent + Prompt

- 系统提示词（prompt.md）赋予 Agent 角色与职责——"你是资深 Flutter 工程师，遵循 Clean Architecture"。
- 任务提示词赋予本次目标——"生成登录页"。
- 组合效果：Agent 在稳定角色下处理多变任务。

### Agent + Rules

- Rules 是 Agent 长期遵守的纪律，Agent 引用而非重复实现。
- 组合效果：规范更新后所有 Agent 自动受益，无需改每个 prompt.md。
- 示例：flutter-agent 的 prompt.md 要求"遵循项目中 `rules/` 下的编码规范"。

### Agent + MCP

- MCP 为 Agent 提供 Tools 通道——构建、查询、部署、连数据库。
- 组合效果：Agent 从"只能改本地文件"变成"能驱动整个研发环境"。
- 设计要点：写 workflow 时假设工具可用，工具调用的安全由 Rules 与权限边界约束。

### 三者协同的完整画面

```text
Prompt（意图）  ┐
Rules（纪律）   ├─→ Agent（编排）─→ Model（推理）─→ MCP/Tools（执行）─→ 验证
MCP（能力）     ┘
```

这正是 `01-overview.md` 端到端链路的架构展开。Agent 章节的本质，就是讲清这一组合如何稳定、可控、可复现地运转。

## 总结

- Agent 架构含 User / Agent / Model / Prompt / Rules / Context / Memory / Tools / MCP / Environment 十类角色，是概念模型而非具体实现。
- Agent Loop：Input→Context→Reasoning→Planning→Tool Calling→Observation→Next Action，Observation 决定走向。
- 决策分三级：目标级（是否做）、规划级（怎么做）、执行级（调哪个 Tool）；风险靠验证闭环 + HITL 控制。
- 上下文管理：按需加载、控制窗口、阶段归档、接力恢复。
- 工具调用：粒度适中、结果可观察、失败可恢复；Memory 由 Rules/Prompts/Agents 工程化承担。
- 权限边界四层（文件/命令/环境/数据）+ 最小权限 + 危险操作确认。
- 错误恢复：重试/回退/换路径/求助/终止，连续失败升级为人。
- 与传统架构根本区别：正确由验证闭环 + 人保证，而非控制流。
- Agent 能力来自组合：Prompt 给意图、Rules 给纪律、MCP 给手脚。
