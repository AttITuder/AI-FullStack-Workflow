# MCP 最佳实践

> 面向企业工程实践的 MCP 使用经验总结。围绕安全、权限、配置、Context、调试与团队协作，沉淀可直接落地的做法。

---

## 为什么需要了解

单次使用 MCP 连接外部工具很容易，但让 MCP 在**长期维护的企业项目**中安全、稳定、高效地运行，需要一套成熟的方法。本章把实战中验证过的经验固化为最佳实践，帮助团队少踩坑、提效率。

## 1. MCP Server 最小权限原则

### 原则

每个 MCP Server 只暴露完成其职责所必需的最小工具集。

### 落地方式

- GitHub MCP 只暴露仓库读取、Issue 管理、PR 操作，不暴露组织管理、权限设置等高危操作。
- MySQL MCP 只暴露查询和只读操作，生产环境不暴露写入操作。
- 按环境区分权限：开发环境可以有写入权限，生产环境只读。

### 检查清单

- [ ] 每个 MCP Server 的工具列表是否最小化？
- [ ] 写入工具是否有确认机制？
- [ ] 生产环境是否限制了高危操作？

## 2. Tool 最小能力原则

### 原则

每个 Tool 只完成一个明确的任务，不做超出范围的操作。

### 落地方式

- `create_issue` 只创建 Issue，不顺带修改其他内容。
- `query_database` 只执行查询，不修改数据。
- Tool 的参数也应最小化，只暴露必要参数。

### 好处

- 降低 Agent 误用工具的风险。
- 减少工具执行的副作用。
- 便于调试和审计。

## 3. 凭证安全

### 原则

所有 MCP Server 的认证凭证（API Key、Token、密码）必须安全存储和传递。

### 落地方式

- 凭证一律通过环境变量传递，禁止写入配置文件。
- `.env` 文件加入 `.gitignore`，禁止提交到代码仓库。
- 企业环境使用密钥管理系统（Vault、AWS Secrets Manager）统一托管。
- 定期轮换凭证，过期凭证及时吊销。

### 禁止事项

- 禁止将 API Key 写入 MCP 配置文件。
- 禁止将凭证提交到 Git 仓库。
- 禁止在日志中输出凭证信息。
- 禁止团队成员共享同一套凭证。

## 4. 敏感数据保护

### 原则

MCP Server 访问的数据可能包含敏感信息，必须在传输和存储环节保护。

### 落地方式

- 远程 MCP Server 使用 HTTPS 加密传输。
- Agent 上下文中的敏感数据用脱敏或摘要方式处理。
- 审计日志中不记录敏感数据的原始值。
- 按数据敏感度分级管理 MCP 访问权限。

## 5. MCP Server 分类管理

### 原则

按功能和风险等级对 MCP Server 进行分类管理。

### 分类方式

| 类别 | 示例 | 风险等级 | 管理要求 |
| --- | --- | --- | --- |
| 代码管理 | Git、GitHub | 中 | 标准管理 |
| 项目管理 | Jira | 低 | 标准管理 |
| 数据库 | MySQL、SQLite | 高 | 严格管控 |
| 设计工具 | Figma | 低 | 标准管理 |
| 文档平台 | Confluence、ShowDoc | 低 | 标准管理 |
| 设备调试 | ADB | 中 | 标准管理 |
| 构建工具 | Gradle | 中 | 标准管理 |

### 管理要求

- 高风险类别：额外的权限控制、审计日志、人工确认机制。
- 中风险类别：标准权限控制、基本审计。
- 低风险类别：基本配置管理。

## 6. 开发环境与生产环境隔离

### 原则

不同环境使用不同的 MCP Server 配置和权限。

### 落地方式

- **开发环境**：可以使用写入工具、查询真实数据库、访问所有 MCP Server。
- **测试环境**：使用脱敏数据，限制高危操作。
- **生产环境**：只读权限，写入操作需要人工审批。

### 配置管理

- 环境配置通过环境变量区分（如 `MCP_ENV=development`）。
- 不同环境的 MCP Server 配置文件独立管理。
- 生产环境的 MCP Server 部署在独立的网络区域。

## 7. MCP 工具数量控制

### 原则

控制 Agent 可用的 MCP 工具总数，避免上下文膨胀。

### 落地方式

- 只接入团队真正需要的 MCP Server。
- 每个 MCP Server 只暴露必要的工具。
- 定期审查工具使用情况，清理无用工具。

### 参考值

- 单个 MCP Server 工具数：5-15 个为宜。
- Agent 可用工具总数：控制在 30-50 个以内。
- 超过建议值时，按任务场景分组管理。

### 好处

- 减少 Agent 选择工具的认知负担。
- 降低上下文长度，提高响应速度。
- 减少误用工具的风险。

## 8. Context 管理

### 原则

MCP 返回的数据进入 Agent 上下文后，需要管理上下文质量和大小。

### 落地方式

- MCP 返回的数据按需加载，不要一次性全量获取。
- 大数据量的 MCP 调用结果做摘要或分页处理。
- 会话聚焦单一任务，避免多个 MCP 调用结果混杂。
- 定期清理过期的上下文信息。

### 注意事项

- MCP 返回的原始数据可能很长，Agent 需要做筛选和摘要。
- 避免让 MCP 数据淹没 Agent 的主要任务上下文。
- 重要数据可以持久化到文件，而非一直保留在上下文中。

## 9. Tool Calling 风险控制

### 原则

控制 Agent 调用工具的行为，防止误操作和恶意调用。

### 落地方式

- **写操作确认**：写入类工具调用前要求人工确认。
- **频率限制**：限制单位时间内工具调用次数，防止无限循环。
- **目标验证**：调用前验证目标对象是否在预期范围内。
- **操作审计**：记录所有工具调用日志，便于事后审查。

### 具体措施

| 风险 | 控制措施 |
| --- | --- |
| 误删数据 | 写操作前确认 + 审计日志 |
| 无限循环 | 频率限制 + 超时控制 |
| 越权操作 | 最小权限 + 目标验证 |
| 数据泄露 | 敏感数据脱敏 + 传输加密 |

## 10. 企业内部 MCP

### 原则

企业内部系统（审批流、监控平台、内部知识库）通过 MCP 接入时，需要额外的安全管控。

### 落地方式

- 内部 MCP Server 部署在企业内网，不暴露到公网。
- 认证使用企业 SSO 或内部凭证体系。
- 访问日志接入企业审计系统。
- 定期安全评估，确认无越权风险。

### 注意事项

- 内部 MCP 的权限需要与企业权限体系对齐。
- 敏感操作需要多级审批。
- 数据传输使用企业内部加密通道。

## 11. MCP 与 Agent Rules 配合

### 原则

MCP 工具的使用应该受到 Agent Rules 的约束。

### 落地方式

- 在 Rules 中明确哪些 MCP 工具可以自动调用，哪些需要人工确认。
- 用 Rules 约束 Agent 的工具选择策略。
- 通过 Rules 定义 MCP 工具调用后的验证流程。

### 示例

```text
规则：数据库写操作必须经过人工确认
规则：GitHub PR 创建前必须完成本地测试
规则：Jira 状态更新前必须验证代码已提交
```

## 12. MCP 与 Prompt 配合

### 原则

MCP 工具调用的 Prompt 应该清晰、具体、有约束。

### 落地方式

- 在 Prompt 中说明需要调用哪个 MCP 工具、传什么参数。
- 提供工具调用的示例，减少 Agent 猜测。
- 在 Prompt 中明确工具调用后的验证标准。

### 好处

- 减少 Agent 误用工具的风险。
- 提高工具调用的成功率。
- 让团队成员的使用方式一致。

## 13. MCP 与多 Agent 协作

### 原则

多个 Agent 共享 MCP Server 时，需要协调和管理。

### 落地方式

- 每个 Agent 的 MCP 权限独立配置。
- 共享 MCP Server 时设置并发控制。
- 不同 Agent 按职责分配不同的 MCP 工具集。
- 通过日志追踪每个 Agent 的工具调用行为。

### 场景示例

- 编码 Agent 只能调用 Git、Gradle、ADB。
- 项目管理 Agent 只能调用 Jira、Confluence。
- 数据库 Agent 只能调用 MySQL、SQLite。

## 14. MCP 调试与日志

### 原则

MCP 的调试和日志是排查问题的关键手段。

### 落地方式

- 记录每次 MCP 工具调用的输入、输出、耗时、状态。
- 错误信息包含足够的上下文（哪个 Server、哪个工具、什么参数）。
- 使用 MCP Inspector 测试工具行为。
- 日志接入团队的监控体系。

### 调试流程

1. 查看 MCP Server 启动日志，确认工具注册正常。
2. 查看工具调用日志，定位失败环节。
3. 使用 MCP Inspector 手动测试工具。
4. 检查环境变量和网络连接。

## 15. MCP 长期维护

### 原则

MCP Server 和配置需要长期维护，跟上工具和团队的变化。

### 落地方式

- 定期更新 MCP Server 版本，修复安全漏洞。
- 团队工具链变化时，同步更新 MCP 配置。
- 定期审查 MCP 使用情况，清理不再需要的 Server。
- 维护 MCP 使用文档，新成员快速上手。

### 维护清单

- [ ] MCP Server 版本是否最新？
- [ ] 凭证是否定期轮换？
- [ ] 不再使用的 MCP Server 是否已清理？
- [ ] 新成员是否能按文档独立配置 MCP？
- [ ] MCP 使用日志是否定期审查？

## 本章总结

- 最小权限原则：Server 和 Tool 只暴露必要能力。
- 凭证安全：环境变量传递，禁止硬编码，定期轮换。
- 敏感数据：传输加密，存储脱敏，审计追踪。
- 分类管理：按风险等级差异化管控。
- 环境隔离：开发 / 测试 / 生产使用不同配置。
- 工具数量控制：只接入真正需要的 MCP Server。
- Context 管理：按需加载，避免上下文膨胀。
- 风险控制：写操作确认，频率限制，操作审计。
- 与 Rules / Prompt 配合：约束 Agent 的工具使用行为。
- 调试与日志：记录调用日志，使用 Inspector 测试。
- 长期维护：定期更新、审查、清理。
