# OpenCode Provider 配置

> 面向企业开发场景的 Provider 配置指南，结合 AI FullStack Workflow 的模型选型原则，讲解如何为不同任务配置不同模型。

---

## 为什么需要了解

Provider（模型提供方）是 OpenCode 能力的源头。正确的 Provider 配置能让 AI 在合适成本下产出高质量代码；错误的配置则要么浪费预算、要么能力不足。本文结合 `docs/02-models/` 的选型框架，给出可落地的配置策略。

## 1. Provider 是什么

Provider 是 OpenCode 中**模型提供方的抽象**。OpenCode 本身不绑定某家模型，而是通过 Provider 接入不同的模型来源：

- 商业 API（OpenAI、Anthropic、DeepSeek、Qwen……）。
- 本地模型（Ollama、LM Studio 等本地推理服务）。
- 自建网关（聚合多家模型的统一入口）。

每个 Provider 声明了"模型从哪来、如何鉴权、使用哪个模型"。

## 2. 为什么需要 Provider

1. **解耦模型与工具**：工具（OpenCode）与模型（Provider）分离，模型可随时更换。
2. **按任务选模型**：不同任务需要不同模型，Provider 机制支持按场景路由。
3. **控制成本**：简单任务用廉价 Provider，复杂任务用旗舰 Provider。
4. **规避厂商锁定**：不依赖单一厂商，可灵活迁移。
5. **满足合规**：敏感数据可路由到本地或合规 Provider。

## 3. OpenAI Provider

### 定位

通用能力主力，代码、推理、多模态均衡，适合作为团队默认选项之一。

### 配置要点

- 需要 OpenAI API Key，通过环境变量注入。
- 按任务选择模型档位：轻快模型用于日常，推理模型用于疑难问题。
- 企业合规场景可改用 Azure OpenAI 端点。

### 适用场景

- 通用开发任务、跨场景综合需求。
- 需要多模态或与 OpenAI 生态整合的团队。

## 4. Anthropic Provider

### 定位

代码质量主力，长上下文与代码审查能力突出，适合代码密集型团队。

### 配置要点

- 需要 Anthropic API Key。
- Claude Code 之外，也可通过 OpenCode 接入 Claude 系列。
- 长上下文任务充分发挥其优势。

### 适用场景

- 复杂代码生成、重构、审查。
- 长文档与大型代码库场景。

## 5. DeepSeek Provider

### 定位

性价比主力，推理能力强，适合成本敏感与批处理场景。

### 配置要点

- 需要 DeepSeek API Key。
- 支持分档：轻快模型打底、旗舰模型兜底、推理模型解决疑难。
- 国产模型在中文场景体验良好。

### 适用场景

- 日常开发、批量任务、成本优化。
- 中文业务与合规要求较高的团队。

## 6. Qwen Provider

### 定位

中文主力，开源生态完善，适合中文业务与私有化需求。

### 配置要点

- 需要阿里云百炼平台 Key 或开源本地部署服务。
- 中文需求与中文文档场景表现优秀。
- 开源权重支持本地部署。

### 适用场景

- 中文业务系统、国内云部署。
- 需要私有化部署的团队。

## 7. 本地模型 Provider

### 定位

数据可控、无 API 成本，适合敏感数据与离线环境。

### 配置要点

- 通过本地推理服务（如 Ollama、LM Studio）暴露标准接口。
- 选择合适尺寸的开源模型（如 Qwen、Llama、DeepSeek 蒸馏版）。
- 需要评估硬件（显存/内存）是否满足模型需求。

### 适用场景

- 数据敏感、无法出网的环境。
- 固定负载、规模化后成本更优的场景。

## 8. 多模型组合策略

单一 Provider 无法覆盖所有任务，企业实践普遍采用**多 Provider 组合**：

| 任务类型 | 推荐 Provider | 理由 |
| --- | --- | --- |
| Coding | Codex / Claude | 代码质量高，工程能力强 |
| 快速生成 | DeepSeek | 响应快、成本低 |
| 中文场景 | Qwen | 中文能力优秀 |
| 成本优化 | 国产模型 / 轻快档 | 批量任务省钱 |
| 疑难推理 | 推理模型（o 系 / R1） | 复杂问题能力最强 |

### 路由原则

- **按复杂度**：简单任务走廉价模型，复杂任务走旗舰模型。
- **按成本**：高 Token 消耗任务优先性价比模型。
- **按语言**：中文任务优先中文优化模型。
- **按合规**：敏感数据走本地或合规 Provider。

### 配置建议

- 通过模型网关统一管理多个 Provider，OpenCode 只对接网关。
- 设置"默认 + 兜底"：默认模型故障时自动降级。
- 定期复盘各 Provider 的性价比，动态调整路由。

## 9. 企业模型选择建议

### 配置前评估

1. **盘点任务**：列出团队主要 AI 任务类型（编码、推理、中文、视觉……）。
2. **明确合规**：确定数据敏感度，决定是否使用本地或特定区域 Provider。
3. **设定预算**：预估 Token 消耗，选择成本合适的模型组合。

### 推荐配置模板

| 角色 | 推荐 | 说明 |
| --- | --- | --- |
| 默认编码 | Claude / Codex | 质量优先 |
| 日常低成本 | DeepSeek | 性价比 |
| 中文业务 | Qwen | 中文优化 |
| 敏感数据 | 本地模型 | 数据可控 |
| 疑难推理 | 推理模型 | 能力兜底 |

### 长期维护

- Provider 配置纳入版本库管理（不含密钥）。
- 密钥统一走环境变量或密钥管理系统。
- 模型更新时先小范围验证，再全团队切换。
- 与 `docs/02-models/10-model-selection.md` 保持联动。

## 最佳实践

1. 密钥绝不写进配置文件，统一环境变量。
2. 先配一个 Provider 跑通，再逐步扩展多模型。
3. 用网关抽象多个 Provider，切换对工作流透明。
4. 建立模型评测样本，切换模型前先验证。

## 常见问题

**Q1：可以不配 Provider 直接用吗？**

不可以。Provider 是模型来源，必须至少配置一个可用 Provider。

**Q2：多个 Provider 会冲突吗？**

不会，按任务路由即可。建议通过网关统一管理。

**Q3：本地模型效果够用吗？**

取决于任务复杂度与硬件，简单任务够用，复杂任务建议用 API 旗舰。

**Q4：API Key 泄露怎么办？**

立即在厂商后台吊销，并通过密钥管理系统轮换。

## 本章总结

- Provider 是 OpenCode 的模型来源抽象，实现模型与工具解耦。
- 主流 Provider 各有定位：OpenAI 通用、Claude 代码、DeepSeek 性价比、Qwen 中文、本地可控。
- 企业实践采用多 Provider 组合，按任务/成本/语言/合规路由。
- 配置遵循"密钥环境变量化、配置入库、网关统一、定期复盘"。
