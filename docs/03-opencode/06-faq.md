# OpenCode FAQ

> OpenCode 使用中的常见问题整理。按安装、模型、Provider、Token、上下文、代码质量、Agent、MCP、企业使用分类。

---

## 安装问题

## Q1: OpenCode 安装失败怎么办？

### A:

先按顺序排查三类最常见原因：

1. **权限问题**：全局安装报 `EACCES`，配置 npm 全局目录为用户可写路径，避免使用 `sudo`。
2. **网络问题**：检查代理与镜像配置，必要时切换 npm 镜像源后重试。
3. **环境问题**：确认 Node 版本符合要求，清理缓存后重装。

详细处理见 `02-install.md` 的常见安装问题章节。

## Q2: 命令找不到怎么办？

### A:

- 确认安装成功且命令在 `PATH` 中。
- 修改 `shell` 配置后需重新加载（`source` 或重开终端）。
- Windows 建议使用 WSL 获得完整终端体验。

## Q3: 升级后行为异常怎么办？

### A:

- 确认 Node 版本与工具版本兼容。
- 查看更新说明，评估变更影响。
- 清理旧缓存后重新安装。

## 模型问题

## Q4: 为什么 AI 回答质量不稳定？

### A:

质量波动通常来自：

- **上下文不足**：没给够项目信息。
- **模型选择**：任务复杂度与模型能力不匹配。
- **Prompt 不清**：意图模糊导致输出发散。

先检查上下文与 Prompt，再考虑换模型。

## Q5: 不同模型的代码风格不一致怎么办？

### A:

通过团队 Rules 统一约束产出风格。Rules 前置到 Prompt 或 Agent 配置，让任何模型都按同一标准输出。

## Q6: 本地模型效果不好怎么办？

### A:

- 确认任务复杂度与模型规模匹配。
- 考虑换用更大模型或切换 API 旗舰模型。
- 优化上下文与 Prompt，补偿模型能力差距。

## Provider 问题

## Q7: Provider 配置后不生效怎么办？

### A:

- 检查配置语法与文件路径是否正确。
- 确认 API Key 环境变量已导出。
- 重启会话让配置生效。
- 查看日志中的 Provider 报错信息。

## Q8: 多个 Provider 如何切换？

### A:

OpenCode 支持按任务配置不同 Provider。企业建议通过模型网关统一管理，路由规则对工作流透明。

## Q9: API Key 会泄露吗？如何防护？

### A:

- 密钥一律走环境变量，禁止写入配置文件与仓库。
- 使用密钥管理系统统一托管。
- 疑似泄露立即在厂商后台吊销并轮换。

## Q10: 可以只用一个 Provider 吗？

### A:

可以起步，但不同任务能力侧重不同。建议至少"日常 + 兜底"双模型，复杂任务用旗舰模型。

## Token 问题

## Q11: Token 消耗太快，成本高怎么办？

### A:

- 简单任务用廉价模型，复杂任务才用旗舰。
- 控制上下文大小，避免全量塞入。
- 利用缓存机制减少重复 Token 消耗。
- 通过网关设定配额与告警。

## Q12: 上下文超长报错怎么办？

### A:

- 裁剪输入，只保留任务相关文件。
- 用检索定位相关代码，替代全量加载。
- 分拆任务，一次处理一个模块。

## Q13: Token 不够用怎么办？

### A:

- 检查模型上下文上限，确认未超限。
- 精简 Prompt 与上下文。
- 复杂任务分步执行，避免一次对话过长。

## 上下文问题

## Q14: AI 不了解我的项目怎么办？

### A:

- 让 AI 先读关键文件（入口、配置、数据模型）。
- 提供项目结构说明与技术栈信息。
- 把 Rules 与模块文档纳入上下文。

## Q15: 上下文太大导致效果变差怎么办？

### A:

- 只加载任务相关文件，避免噪声稀释注意力。
- 优先使用文件引用与检索。
- 会话聚焦单一任务，完成后开新会话。

## Q16: 如何让 AI 记住项目约定？

### A:

- 把约定写成 Rules 与模块文档。
- 在每次 Prompt 中引用或自动加载。
- 通过 Agent 配置固化常用约定。

## 代码质量问题

## Q17: AI 生成的代码不靠谱怎么办？

### A:

- 让 AI 先给方案，人确认后再生成。
- 用测试验证行为，不盲信输出。
- 审查时关注安全、性能与边界条件。

## Q18: 如何提高生成代码的准确性？

### A:

- 提供现有代码示例作为风格参照。
- 明确技术栈、架构与约束。
- 用验收清单约束输出，让 AI 自检。

## Q19: AI 引入了安全隐患怎么办？

### A:

- 审查环节增加安全维度检查。
- 不信任 AI 对敏感操作的自主处理。
- 通过 Rules 约束安全编码规范。

## Agent 问题

## Q20: Agent 会乱执行命令吗？

### A:

存在风险。工程上通过权限限制、命令白名单、人工确认机制控制。遵循最小权限原则。

## Q21: Agent 任务失败怎么办？

### A:

- 查看失败日志，定位卡住的环节。
- 提供更明确的指令或上下文。
- 拆分子任务，分步验证。

## Q22: 如何让 Agent 更高效？

### A:

- 给 Agent 明确的目标与边界。
- 配置专用 Agent（如 flutter-agent）固化能力。
- 建立验收清单，减少无效返工。

## Q23: 多个 Agent 如何协作？

### A:

- 明确分工与交接物。
- 通过工作流编排（详见 `docs/16-case-study/`）。
- 每个 Agent 产出独立可验证。

## MCP 问题

## Q24: MCP 连接失败怎么办？

### A:

- 检查配置与网络。
- 确认密钥与权限正确。
- 查看 MCP 服务端日志。

## Q25: 如何选择合适的 MCP？

### A:

- 按团队工具链选择（GitHub、数据库、设计稿、文档平台）。
- 参考 `mcp/` 目录与 `docs/08-mcp/`。
- 只接入真正需要的，减少风险面。

## Q26: MCP 的写操作安全吗？

### A:

- 对写操作保持谨慎，必要时人工确认。
- 控制 MCP 权限边界。
- 记录操作日志便于审计。

## 企业使用问题

## Q27: 企业如何统一团队配置？

### A:

- Provider、Rules、Prompt、Agent 配置纳入版本库。
- 新成员按 README 一键配置。
- 密钥用环境变量或密钥管理统一托管。

## Q28: 数据安全如何保障？

### A:

- 敏感数据走本地或合规 Provider。
- 配置权限策略与命令白名单。
- 记录 AI 执行行为，保留审计痕迹。

## Q29: AI 产出风格不统一怎么办？

### A:

- 团队 Rules 前置到 AI 产出环节。
- 统一 Prompt 模板与 Agent 配置。
- 建立"自动化检查 + 人工审查"防线。

## Q30: 如何评估 AI 使用效果？

### A:

- 建立任务完成率、返工率、成本等指标。
- 定期复盘各模型性价比。
- 用真实任务评测集评估模型切换影响。

## Q31: 新成员如何快速上手？

### A:

- 提供项目 README 与使用指引。
- 配置好默认 Provider 与 Rules。
- 从简单任务开始，逐步接触高级工作流。

## Q32: 遇到问题在哪找帮助？

### A:

- 先查本文档与章节其他文档。
- 查看官方文档与社区。
- 沉淀踩坑经验回补到本文档。

## 总结

- 安装问题优先查权限、网络、环境。
- 模型问题看上下文、Prompt 与选型。
- Provider 配置走环境变量，多模型通过网关管理。
- Token 与上下文核心是"够用即可、按需加载"。
- 代码质量靠测试、审查与 Rules 保障。
- Agent 与 MCP 强调权限控制与人工验收。
- 企业使用统一配置资产、守住安全、持续复盘。
