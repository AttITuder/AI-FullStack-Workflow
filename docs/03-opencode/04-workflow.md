# OpenCode 开发工作流

> 本章节核心。围绕真实研发流程，讲解如何把 OpenCode 组织成稳定可复现的开发工作流。

---

## 为什么需要了解

工具会用与用得好是两回事。OpenCode 真正的价值不在单次对话，而在于把它组织进"需求 → 编码 → 测试 → 审查"的完整研发流程。本文给出不同场景下的标准工作流，让团队产出稳定、可复制、可验收。

## 1. 日常开发流程

日常开发遵循一个稳定的主循环：

```text
需求
 ↓
分析
 ↓
Prompt
 ↓
Agent
 ↓
修改代码
 ↓
测试
 ↓
Review
```

### 步骤详解

1. **需求**：明确要做什么，写出可验收的目标。
2. **分析**：让 AI 先读代码库，确认影响范围与技术方案。
3. **Prompt**：把需求转化为清晰指令（参考 `prompts/` 目录与 `05-best-practice.md`）。
4. **Agent**：委派 OpenCode 执行，读取上下文、规划任务。
5. **修改代码**：AI 生成/修改代码，必要时分步确认。
6. **测试**：运行构建与测试，根据结果迭代修复。
7. **Review**：AI 自检 + 人类审查，确认质量后合并。

### 核心原则

- **小步快跑**：一次任务聚焦一个改动，便于审查与回滚。
- **先分析后动手**：让 AI 先说明方案，人确认后再执行。
- **测试兜底**：AI 改动必须通过测试验证。

## 2. 新功能开发 Workflow

### 适用

在现有项目中新增页面、模块、接口或能力。

### 流程

```text
1. 需求说明 → 让 AI 拆解为任务清单
2. 确认技术方案 → 技术选型与文件结构
3. 逐模块生成 → 每模块生成后快速自检
4. 集成验证 → 运行构建、跑通主流程
5. 补齐测试 → 单元测试 + 边界用例
6. 审查合并 → AI 自检 + 人工 Review
```

### 关键提示词要点

- 说明现有架构与技术栈。
- 指定遵循的项目规范（引用 `rules/`）。
- 要求"分步实现、逐步确认"。

## 3. Bug 修复 Workflow

### 适用

处理线上问题、测试失败、逻辑错误。

### 流程

```text
1. 提供现象 → 报错信息、复现步骤
2. 定位根因 → 让 AI 读相关代码找原因
3. 确认方案 → 说明修复思路后再动手
4. 最小修改 → 只改必要代码，避免波及
5. 验证修复 → 复现场景 + 相关测试
6. 补充说明 → 记录根因与修复逻辑
```

### 关键原则

- **先定位根因，再修复**：禁止"猜着改"。
- **最小改动**：避免修复引入新问题。
- **验证闭环**：必须能证明问题已解决。

## 4. 重构 Workflow

### 适用

优化代码结构、消除重复、统一命名、提升可维护性。

### 流程

```text
1. 明确目标 → 重构范围与预期收益
2. 建立基线 → 确保现有测试通过
3. 分步重构 → 小步提交，每步可验证
4. 依赖更新 → 同步更新引用与文档
5. 回归测试 → 确认行为未变
6. 审查合并 → 关注可读性与一致性
```

### 关键原则

- **行为不变**：重构不改变外部行为，只改内部结构。
- **测试保护**：重构前必须有测试兜底。
- **小步提交**：避免大规模一次性重构。

## 5. Code Review Workflow

### 适用

审查 AI 或团队产出的代码。

### 流程

```text
1. 提供上下文 → 变更范围、目的、关联需求
2. AI 审查 → 规范、安全、性能、逻辑
3. 输出意见 → 结构化问题清单 + 建议
4. 人工复核 → 判断意见合理性
5. 修复迭代 → 按意见修改并验证
6. 最终确认 → 通过标准
```

### 审查维度

- **规范**：命名、格式、项目 Rules 符合度。
- **安全**：敏感信息、输入校验、越权风险。
- **性能**：算法复杂度、资源消耗、热点路径。
- **逻辑**：边界条件、错误处理、并发安全。

## 6. Flutter 项目 Workflow

### 特点

- 技术栈：Flutter、Dart、状态管理（GetX 等）、Clean Architecture。
- 页面密集、UI 与状态管理耦合。

### 流程

```text
1. 需求 → 页面/功能拆解
2. 架构对齐 → Controller / Binding / View / Model 分层
3. 生成代码 → 按分层生成页面组件
4. 依赖处理 → pub get / 新依赖说明
5. 运行验证 → flutter analyze + flutter test
6. Review → 状态管理、命名、错误处理
```

### 关键要点

- 严格遵循项目分层（参考 `rules/flutter/` 与 `agents/flutter-agent/`）。
- 每个页面交付 Controller / Binding / View / Route 完整配套。

## 7. Android 项目 Workflow

### 特点

- 技术栈：Kotlin、Jetpack Compose、MVVM。
- 构建链较长，验证成本高。

### 流程

```text
1. 需求 → 界面/逻辑拆解
2. 架构对齐 → ViewModel / Repository / Data
3. 生成代码 → Compose UI + 业务逻辑
4. 依赖处理 → Gradle 依赖同步
5. 运行验证 → 单元测试 + 构建
6. Review → 生命周期、协程、资源管理
```

### 关键要点

- 关注生命周期与协程安全。
- 资源（字符串、样式）统一管理。

## 8. 企业项目 Workflow

### 特点

- 多人协作、规范严格、流程复杂。
- 强调可控、可审计、可追溯。

### 流程

```text
1. 需求 → 工单/需求文档
2. 任务拆分 → 关联规范与验收标准
3. AI 执行 → 遵循团队 Rules 与模板
4. 多级验证 → 自动化测试 + AI 审查 + 人工审查
5. 提交合并 → 规范提交信息 + PR 流程
6. 知识回流 → 沉淀 Prompt / Rules / 经验
```

### 关键要点

- **规则前置**：AI 产出必须符合团队 Rules。
- **人工验收**：关键决策由人把控。
- **知识沉淀**：每次成功实践回流到知识库。
- **可追溯**：需求、任务、代码、提交全程关联。

## 总结

- 日常开发遵循"需求 → 分析 → Prompt → Agent → 改码 → 测试 → Review"主循环。
- 新功能、Bug、重构、Review 各有专门流程，核心是"小步、验证、可回滚"。
- Flutter 与 Android 项目按技术栈调整流程细节。
- 企业项目强调规则、验收、可追溯与知识回流。
